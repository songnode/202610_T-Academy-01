# TMS 프로젝트 데이터 설계 및 머신러닝 학습 데이터 점검

## 1\. 멘토링 목적

이번 멘토링에서는 교육생들이 설계한 `tw_cems_ml_ready`를 중심으로 데이터가 실제 머신러닝 학습에 적합하게 구성되었는지 점검합니다.

주요 점검 항목은 다음과 같습니다.

1. 학습 데이터 규모와 데이터 적격 조건 확인
2. ML-ready 컬럼 및 Feature 구성 검토
3. 분류(Classification)와 회귀(Regression) 학습 데이터 구성 검토
4. LSTM 학습을 위한 시계열 Sequence 구성 검토
5. 데이터 누수(Data Leakage) 및 학습·평가 데이터 분리 검토

# 2\. 학습 데이터 규모 점검

## 2.1 전체 데이터 규모

대만 CEMS 36개월 데이터를 기준으로 집계한 v2 데이터 규모입니다.

| 구분 | NOx | SO₂ | 합계 |
| --- | ---: | ---: | ---: |
| ML-ready 행 | 9,806,850 | 7,836,511 | 17,643,361 |
| 분류 학습 가능 | 5,477,394 | 4,380,490 | 9,857,884 |
| 그중 양성 | 106,931 | 26,785 | 133,716 |
| 회귀 학습 가능 | 5,960,021 | 4,727,123 | 10,687,144 |

### 데이터 규모 해석

**① ML-ready 행**

- 총 17,643,361행입니다.
- 한 행은 굴뚝 × 측정 물질 × 30분 슬롯을 의미합니다.
- NOx와 SO₂ 데이터가 각각 독립적인 시계열로 구성됩니다.

**② 분류 학습 가능 데이터**

- 총 9,857,884행입니다.
- 전체 ML-ready 데이터 중 약 55.9%입니다.
- 분류 정답인 `label_entry_60m`이 유효하고 Feature 조건을 만족하는 데이터입니다.

**③ 회귀 학습 가능 데이터**

- 총 10,687,144행입니다.
- 전체 ML-ready 데이터 중 약 60.6%입니다.
- 정확히 60분 뒤의 기준 대비율을 정답으로 사용할 수 있는 데이터입니다.

**④ 양성 데이터**

| 구분 | 양성 건수 | 양성 비율 |
| --- | ---: | ---: |
| NOx | 106,931 | 약 1.95% |
| SO₂ | 26,785 | 약 0.61% |
| 전체 | 133,716 | 약 1.36% |

분류 데이터에서 양성 비율이 상당히 낮습니다.

따라서 모델이 대부분을 음성으로 예측하더라도 정확도(Accuracy)가 높게 나올 수 있습니다.

분류 모델은 다음 평가 지표를 함께 확인해야 합니다.

- Precision: 위험이라고 예측한 데이터 중 실제 위험의 비율
- Recall: 실제 위험 데이터 중 모델이 찾아낸 비율
- F1-score: Precision과 Recall의 조화평균
- PR-AUC: 불균형 데이터에서 양성 탐지 성능을 평가하는 지표
- Confusion Matrix: 실제와 예측 결과의 건수 비교

특히 이번 프로젝트는 위험 진입을 사전에 탐지하는 것이 목적이므로 Recall을 중요하게 살펴볼 필요가 있습니다.

## 2.2 v1과 v2 데이터 규모 비교

| 구분 | v1 | v2 | 증감 |
| --- | ---: | ---: | ---: |
| ML-ready 행 | 17,643,361 | 17,643,361 | 동일 |
| 분류 학습 가능 | 9,858,569 | 9,857,884 | -685 |
| 양성 | 133,726 | 133,716 | -10 |
| 회귀 학습 가능 | 10,532,709 | 10,687,144 | +154,435 |

### 멘토링 점검 사항

분류 학습 가능 데이터는 685건 감소했지만 회귀 학습 가능 데이터는 154,435건 증가했습니다.

이 차이가 발생한 이유를 교육생들이 설명할 수 있어야 합니다.

분류와 회귀는 정답을 만드는 조건이 다르기 때문입니다.

- 분류: T+30분 또는 T+60분의 위험 진입 여부를 판정합니다.
- 회귀: 정확히 T+60분의 기준 대비율을 예측합니다.

따라서 두 Label의 미래 데이터 유효성 조건이 다르면 학습 가능 데이터 수도 달라집니다.

**확인할 질문**

1. v2에서 분류 학습 가능 데이터가 감소한 원인은 무엇인가요?
2. 회귀 학습 가능 데이터가 증가한 원인은 무엇인가요?
3. 변경된 Label 생성 로직이 실제로 의도한 대로 적용되었나요?
4. v1과 v2의 차이를 데이터 샘플 단위로 추적할 수 있나요?

단순히 건수가 변경되었다는 설명보다는 변경 전후의 Label 생성 조건과 NULL 발생 원인을 비교하는 것이 좋습니다.

# 3\. ML-ready 데이터 구조 점검

## 3.1 ML-ready 데이터의 기본 구조

테이블: `tw_cems_ml_ready`

| 항목 | 설계 내용 |
| --- | --- |
| 전체 컬럼 | 35개 |
| 데이터 단위 | 굴뚝 × 물질 × 30분 슬롯 |
| 시계열 분리 기준 | `stack_code + item_code` |
| 측정 주기 | 30분 |
| Feature 개수 | 24개 |
| Label 개수 | 2개 |
| 적격 및 버전 관리 | 6개 |

35개 컬럼은 다음과 같이 구성됩니다.

| 구분 | 컬럼 수 | 설명 |
| --- | ---: | --- |
| 식별 및 현재 상태 | 7 | 식별 정보 3개 + 수치 Feature 4개 |
| 과거 값 및 추세 | 15 | Lag, 변화량, Rolling |
| 시간 Feature | 5 | 시간 및 계절 정보 |
| Label | 2 | 분류 및 회귀 정답 |
| 적격 및 버전 관리 | 6 | 학습 가능 여부 및 버전 |
| **합계** | **35** |  |

여기서 중요한 점은 **35개 컬럼 전체가 모델 입력으로 사용되는 것은 아니라는 것**입니다.

모델 입력으로 사용하는 Feature는 다음과 같습니다.

- 현재 상태 Feature 4개
- 과거 값 및 추세 Feature 15개
- 시간 Feature 5개

따라서 모델 입력 Feature는 총 24개입니다.

## 3.2 식별 컬럼과 모델 입력 Feature 구분

예를 들어 다음과 같은 데이터가 있다고 가정하겠습니다.

| stack\_code | item\_code | measured\_at | ratio\_pct | ratio\_diff\_30m | hour\_sin |
| --- | --- | --- | ---: | ---: | ---: |
| STACK\_001 | nox | 09:00 | 65 | 2 | 0.707 |
| STACK\_001 | nox | 09:30 | 68 | 3 | 0.383 |
| STACK\_001 | nox | 10:00 | 72 | 4 | 0.000 |
| STACK\_002 | nox | 09:00 | 55 | -1 | 0.707 |

각 컬럼의 역할은 다음과 같습니다.

| 컬럼 | 역할 |
| --- | --- |
| `stack_code` | 어느 굴뚝의 데이터인지 식별 |
| `item_code` | 어떤 측정 물질인지 식별 |
| `measured_at` | 측정 시점 식별 |
| `ratio_pct` | 모델 입력 Feature |
| `ratio_diff_30m` | 모델 입력 Feature |
| `hour_sin` | 모델 입력 Feature |

`stack_code`, `item_code`, `measured_at`는 데이터 식별 및 시계열 구성에 사용합니다.

반면 `ratio_pct`, `ratio_diff_30m`, `hour_sin` 등 24개 Feature가 실제 모델에 입력됩니다.

**멘토링 질문**

- 굴뚝 번호와 측정 물질을 모델 입력에서 제외하는 이유는 무엇인가요?
- `stack_code`가 다르면 Lag와 Rolling 계산을 어떻게 처리하나요?
- NOx와 SO₂의 Feature를 하나의 시계열로 합치면 어떤 문제가 발생하나요?

핵심은 서로 다른 굴뚝이나 물질의 과거 값이 섞이지 않도록 하는 것입니다.

# 4\. Feature Engineering 점검

## 4.1 현재 상태 Feature 4개

| Feature | 의미 |
| --- | --- |
| `ratio_pct` | 현재 배출기준 대비율 |
| `headroom_pct` | 90% 위험 진입선까지 남은 여유 |
| `measure_value` | 현재 측정 농도 |
| `standard_value` | 현재 적용 배출기준 |

계산식:

``` python
ratio_pct = ratio * 100

headroom_pct = 90 - ratio_pct
```

예를 들어 현재 기준 대비율이 65%라면 다음과 같습니다.

``` text
ratio_pct    = 65
headroom_pct = 25
```

즉, 위험 진입 기준인 90%까지 25%p의 여유가 있다는 의미입니다.

### 점검 사항

- `ratio_pct`와 `measure_value / standard_value`의 계산 결과가 일치하는가?
- 기준값이 변경되었을 때 과거 데이터와 현재 데이터의 기준이 정확하게 관리되는가?
- `standard_value`의 단위가 측정값과 일치하는가?
- `ratio_pct`가 100%를 초과하는 데이터도 정상적으로 보존하는가?

특히 기준값과 측정값의 단위가 다르면 잘못된 비율이 계산될 수 있으므로 확인해야 합니다.

## 4.2 Lag Feature 5개

Lag는 과거 특정 시점의 값을 현재 행에 가져오는 Feature입니다.

| Feature | 의미 |
| --- | --- |
| `ratio_lag_30m` | 30분 전 |
| `ratio_lag_60m` | 60분 전 |
| `ratio_lag_90m` | 90분 전 |
| `ratio_lag_120m` | 120분 전 |
| `ratio_lag_150m` | 150분 전 |

예를 들어 현재 시점이 10:00이라면 다음과 같습니다.

| 시간 | ratio\_pct |
| --- | ---: |
| 07:30 | 50 |
| 08:00 | 52 |
| 08:30 | 55 |
| 09:00 | 58 |
| 09:30 | 62 |
| 10:00 | 65 |

10:00 행의 Lag Feature는 다음과 같습니다.

| Feature | 값 |
| --- | ---: |
| `ratio_lag_30m` | 62 |
| `ratio_lag_60m` | 58 |
| `ratio_lag_90m` | 55 |
| `ratio_lag_120m` | 52 |
| `ratio_lag_150m` | 50 |

### 점검 사항

- `stack_code + item_code`별로 독립 계산하는가?
- 정확히 30분 전 데이터가 없으면 NULL로 처리하는가?
- 중간 데이터가 누락된 경우 다음 정상 데이터로 건너뛰지 않는가?

예를 들어 09:30 데이터가 없는데 09:00 데이터를 30분 전 값으로 사용하면 안 됩니다.

## 4.3 변화량 및 추세 Feature 3개

| Feature | 의미 |
| --- | --- |
| `ratio_diff_30m` | 현재와 30분 전의 차이 |
| `ratio_diff_60m` | 현재와 60분 전의 차이 |
| `ratio_acceleration` | 변화량의 변화 |

예를 들어 다음과 같습니다.

| 시간 | ratio\_pct | 30분 변화량 |
| --- | ---: | ---: |
| 09:00 | 55 | \- |
| 09:30 | 60 | +5 |
| 10:00 | 68 | +8 |

10:00 시점의 가속도는 다음과 같이 계산할 수 있습니다.

``` python
ratio_acceleration = 8 - 5
# 결과: +3
```

이는 배출기준 대비율의 상승 속도가 빨라지고 있다는 의미입니다.

### 점검 사항

- 변화량의 단위가 %p로 일관되게 관리되는가?
- 가속도 계산 시 필요한 과거 값이 모두 존재하는가?
- 결측이 있는 경우 잘못된 가속도 값이 생성되지 않는가?

## 4.4 Rolling Feature 7개

Rolling은 일정한 시간 구간의 데이터를 묶어서 통계값을 계산하는 방법입니다.

| Feature | 의미 |
| --- | --- |
| `ratio_rolling_mean_1h` | 최근 1시간 평균 |
| `ratio_rolling_mean_3h` | 최근 3시간 평균 |
| `ratio_rolling_std_3h` | 최근 3시간 표준편차 |
| `ratio_rolling_max_3h` | 최근 3시간 최댓값 |
| `ratio_range_3h` | 최근 3시간 최대-최소 |
| `ratio_slope_3h` | 최근 3시간 추세 기울기 |
| `rise_count_3h` | 최근 5번의 변화 중 상승 횟수 |

예를 들어 다음과 같은 값이 있다고 가정하겠습니다.

``` text
55, 57, 60, 62, 65, 68
```

현재 시점을 포함한 최근 6개 슬롯을 이용하여 평균, 표준편차, 최댓값 등을 계산합니다.

### 중요한 점: 3시간 Rolling의 시간 범위

30분 간격 데이터 6개는 다음과 같습니다.

``` text
T-150분
T-120분
T-90분
T-60분
T-30분
T
```

첫 번째 시점과 마지막 시점 사이의 경과 시간은 150분, 즉 2시간 30분입니다.

다만 각 행이 30분 구간을 대표하는 데이터라면 6개 슬롯이 포함하는 측정 구간은 총 3시간입니다.

따라서 교육생들은 다음 두 가지를 구분해야 합니다.

- 6개 시점 사이의 경과 시간: 2시간 30분
- 6개의 30분 측정 구간이 포함하는 시간: 3시간

`feature_valid`의 3시간 이력 조건도 이 정의에 맞게 문서화해야 합니다.

### 점검 사항

- 현재 시점의 데이터를 포함하는가?
- 최근 6개 슬롯이 모두 존재하는가?
- 표준편차 계산 시 모집단 기준(ddof=0)인지 표본 기준(ddof=1)인지 통일했는가?
- `ratio_slope_3h`의 단위가 30분당 %p로 정의되어 있는가?
- `rise_count_3h`가 최근 5개 변화량을 기준으로 계산되는가?

# 5\. Label 설계 점검

머신러닝에서는 Feature와 Label을 명확하게 구분해야 합니다.

- Feature: 모델에 입력하는 데이터
- Label: 모델이 예측해야 하는 정답

이번 프로젝트는 분류와 회귀 두 가지 모델을 구성합니다.

## 5.1 분류 Label

컬럼: `label_entry_60m`

목표는 현재 시점 이후 60분 이내에 배출기준 대비율 90% 이상에 새롭게 진입하는지 예측하는 것입니다.

예시:

| 현재 | T+30분 | T+60분 | Label |
| ---: | ---: | ---: | ---: |
| 65 | 70 | 85 | 0 |
| 65 | 92 | 95 | 1 |
| 65 | 75 | 93 | 1 |
| 65 | 75 | 80 | 0 |
| 65 | NULL | 80 | NULL |

단, 위 예시의 마지막 행처럼 미래 데이터가 일부 누락된 경우에는 판정 정책을 명확하게 정의해야 합니다.

한 시점이라도 90% 이상이 확인되면 양성으로 판정할 수 있지만, 두 시점 모두 90% 미만이라는 음성 판정은 두 시점이 모두 유효해야 가능합니다.

현재 이미 90% 이상인 경우는 신규 위험 진입 예측 대상에서 제외합니다.

### 점검 사항

- 현재 시점이 90% 이상인 행은 NULL로 처리하는가?
- T+30분과 T+60분 중 하나라도 90% 이상이면 1인가?
- 두 시점 모두 유효하고 90% 미만일 때만 0인가?
- 미래 데이터가 누락된 경우 NULL 처리 기준이 명확한가?

## 5.2 회귀 Label

컬럼: `label_ratio_60m`

목표는 정확히 60분 후의 배출기준 대비율을 예측하는 것입니다.

예시:

| 현재 시각 | 현재 ratio\_pct | 60분 후 | Label |
| --- | ---: | ---: | ---: |
| 09:00 | 65 | 09:30 = 70 | \- |
| 09:00 | 65 | 10:00 = 82 | 82 |
| 09:30 | 70 | 10:30 = 88 | 88 |
| 10:00 | 82 | 11:00 = 95 | 95 |

회귀 모델은 60분 후의 실제 수치를 예측합니다.

예측 결과가 다음과 같다면,

``` text
실제값: 95
예측값: 91
```

예측 오차는 4%p입니다.

### 점검 사항

- 정확히 T+60분의 데이터를 사용하는가?
- 미래 데이터가 없으면 NULL로 처리하는가?
- 100%를 초과한 값도 그대로 보존하는가?
- 분류 Label과 회귀 Label을 혼동하지 않는가?

# 6\. 머신러닝 관점의 학습 데이터 구성

## 6.1 RF와 XGBoost 입력 데이터

Random Forest와 XGBoost는 현재 시점의 Feature를 하나의 행으로 입력받습니다.

입력 데이터 구조는 다음과 같습니다.

``` text
X_train: (N, 24)
y_train: (N,)
```

여기서 N은 학습에 사용할 행의 개수입니다.

예를 들어 다음과 같습니다.

``` text
X_train.shape = (100000, 24)
y_train.shape = (100000,)
```

의미는 다음과 같습니다.

- 학습 데이터 100,000건
- 각 데이터는 24개 Feature로 구성
- 각 데이터에 대응하는 정답 Label 1개

### 분류와 회귀의 입력 및 정답

| 모델 | 입력 Feature | 정답 Label |
| --- | --- | --- |
| RF 분류 | 24개 | `label_entry_60m` |
| XGBoost 분류 | 24개 | `label_entry_60m` |
| RF 회귀 | 24개 | `label_ratio_60m` |
| XGBoost 회귀 | 24개 | `label_ratio_60m` |

분류와 회귀는 Feature 구조는 동일하지만 정답 Label과 평가 방법이 다릅니다.

## 6.2 모델 학습 전에 확인할 사항

**① 학습 데이터 필터링**

분류 모델:

``` python
classification_df = df[
    df["classification_eligible"] == True
]
```

회귀 모델:

``` python
regression_df = df[
    df["regression_eligible"] == True
]
```

**② 모델 입력 컬럼 선택**

``` python
feature_columns = [
    "ratio_pct",
    "headroom_pct",
    "measure_value",
    "standard_value",
    "ratio_lag_30m",

    "ratio_acceleration",

    "ratio_rolling_std_3h",

    "hour_sin",
```


# 7\. LSTM 관점의 학습 데이터 구성

LSTM은 일반적인 머신러닝 모델과 달리 시간의 흐름을 반영한 데이터를 입력받습니다.

RF와 XGBoost가 현재 시점의 Feature 24개를 입력받는다면 LSTM은 과거 여러 시점의 Feature를 함께 입력받습니다.

## 7.1 LSTM Window 구성

이번 프로젝트는 다음과 같이 설계되어 있습니다.

- 측정 간격: 30분
- Window Size: 6
- Feature 개수: 24개

따라서 LSTM 입력 구조는 다음과 같습니다.

``` text
(N, 6, 24)
```

각 차원의 의미는 다음과 같습니다.

| 차원 | 의미 |
| --- | --- |
| N | 학습 Sequence 개수 |
| 6 | 시간 순서에 따른 6개 시점 |
| 24 | 각 시점의 Feature 개수 |

## 7.2 실제 데이터 예시

다음은 하나의 굴뚝과 하나의 측정 물질에 대한 데이터입니다.

| 시간 | ratio\_pct |
| --- | ---: |
| 09:00 | 50 |
| 09:30 | 53 |
| 10:00 | 55 |
| 10:30 | 58 |
| 11:00 | 62 |
| 11:30 | 65 |
| 12:00 | 70 |

Window Size가 6이면 다음과 같이 구성됩니다.

**Sequence 1**

``` text
09:00
09:30
10:00
10:30
11:00
11:30
```

**Sequence 2**

``` text
09:30
10:00
10:30
11:00
11:30
12:00
```

이처럼 한 시점씩 이동하면서 Sequence를 생성하는 방식을 Sliding Window라고 합니다.

각 시점에는 `ratio_pct`뿐 아니라 24개 Feature가 모두 포함됩니다.

따라서 실제 데이터는 다음과 같은 구조입니다.

``` text
Sequence 1
[
  [09:00의 Feature 24개],
  [09:30의 Feature 24개],
  [10:00의 Feature 24개],
  [10:30의 Feature 24개],
  [11:00의 Feature 24개],
  [11:30의 Feature 24개]
]
```

최종 입력 형태는 다음과 같습니다.

``` text
(Sequence 개수, 6, 24)
```

## 7.3 LSTM의 정답 Label 연결

중요한 점은 하나의 Sequence에 정답 Label 하나가 연결된다는 것입니다.

예를 들어 다음과 같습니다.

| Sequence | 입력 구간 | 예측 기준 시점 | 정답 |
| --- | --- | --- | --- |
| 1 | 09:00\~11:30 | 11:30 | 12:30의 값 또는 위험 여부 |
| 2 | 09:30\~12:00 | 12:00 | 13:00의 값 또는 위험 여부 |

Sequence의 마지막 시점을 기준으로 정답을 연결합니다.

분류 모델:

``` text
X_train: (N, 6, 24)
y_train: (N,)
```

정답은 `label_entry_60m`입니다.

회귀 모델:

``` text
X_train: (N, 6, 24)
y_train: (N,)
```

정답은 `label_ratio_60m`입니다.

분류와 회귀는 입력 구조는 같지만 정답이 다릅니다.

## 7.4 LSTM Sequence 생성 시 반드시 확인할 사항

**① 동일한 굴뚝과 측정 물질만 사용**

다음 데이터는 서로 다른 시계열입니다.

``` text
STACK_001 + NOx
STACK_001 + SO2
STACK_002 + NOx
```

따라서 Sequence 생성 시 반드시 다음 기준으로 그룹화해야 합니다.

``` python
groupby(["stack_code", "item_code"])
```

**② 정확히 30분 간격인지 확인**

중간 데이터가 누락된 경우 잘못된 Sequence를 만들면 안 됩니다.

예를 들어 다음과 같은 데이터가 있다면,

``` text
09:00
09:30
10:00
11:00
11:30
12:00
```

10:30 데이터가 없으므로 6개 시점을 연속된 30분 간격 Sequence로 취급하면 안 됩니다.

**③ Feature 결측 확인**

6개 시점의 24개 Feature가 모두 유효한지 확인해야 합니다.

**④ 마지막 시점의 Label 연결**

Sequence의 마지막 시점에 해당하는 Label을 정답으로 사용해야 합니다.

**⑤ 분류와 회귀의 Sequence 개수 확인**

분류와 회귀는 Label 유효성 조건이 다르므로 생성되는 Sequence 개수도 다를 수 있습니다.

# 8\. 학습 및 평가 데이터 분리

머신러닝에서 중요한 문제 중 하나는 데이터 누수입니다.

이번 프로젝트는 시계열 예측이므로 무작위 분할보다 시간 기준 분할을 권장합니다.

## 8.1 잘못된 데이터 분리

전체 데이터를 먼저 무작위로 섞은 다음 Train과 Test로 나누면 문제가 발생할 수 있습니다.

예를 들어,

``` text
09:00 데이터 → Train
09:30 데이터 → Test
10:00 데이터 → Train
10:30 데이터 → Test
```

인접한 시점의 데이터가 서로 다른 집합에 들어가게 됩니다.

LSTM은 Sliding Window 특성상 입력 데이터가 상당 부분 중복되기 때문에 평가 결과가 실제보다 좋게 나올 위험이 있습니다.

## 8.2 권장 데이터 분리

시간 순서에 따라 분리합니다.

예시:

``` text
Train       : 2023년 ~ 2025년
Validation  : 2026년 1월 ~ 3월
Test        : 2026년 4월 ~ 6월
```

실제 데이터 기간에 맞게 경계는 조정해야 합니다.

데이터 분리 후 각 구간의 역할은 다음과 같습니다.

| 구분 | 목적 |
| --- | --- |
| Train | 모델 학습 |
| Validation | 하이퍼파라미터 및 모델 선택 |
| Test | 최종 성능 평가 |

### LSTM에서 추가로 주의할 점

Train과 Test를 시간 기준으로 나눈 후 Sequence를 생성해야 합니다.

다만 Test 구간의 첫 번째 Sequence를 만들 때 이전 시점의 과거 데이터가 필요할 수 있습니다.

이 경우 과거 Train 구간의 Feature를 입력 이력으로 사용하는 것은 실제 운영 상황과 동일하므로 허용할 수 있습니다.

단, 예측 기준 시점은 Test 구간에 속해야 하며 정답 Label이 다른 구간의 미래 데이터를 참조하지 않도록 해야 합니다.

예를 들어 Test 구간의 마지막 시점에서 T+60분이 Test 기간 밖이라면 해당 행은 평가에서 제외하거나 별도 정책으로 처리해야 합니다.

# 9\. Scaler 적용 점검

Scaler는 Feature별 값의 범위를 조정하는 전처리 방법입니다.

이번 프로젝트에서는 모델별로 적용 여부를 구분하는 것이 좋습니다.

| 모델 | Scaler 적용 |
| --- | --- |
| Random Forest | 일반적으로 불필요 |
| XGBoost | 일반적으로 불필요 |
| LSTM | 권장 |

LSTM은 Feature별 숫자 범위 차이가 학습에 영향을 줄 수 있으므로 StandardScaler를 우선 검토할 수 있습니다.

예를 들어 다음과 같은 Feature가 있다고 가정하겠습니다.

| Feature | 값의 범위 |
| --- | --- |
| `ratio_pct` | 0\~150 |
| `measure_value` | 0\~수백 |
| `hour_sin` | -1\~1 |
| `day_of_week` | 0\~6 |

StandardScaler는 학습 데이터의 평균과 표준편차를 이용해 변환합니다.

\[
X\_{scaled} = \\frac{X-\\mu}{\\sigma}
\]

### Scaler 적용 시 주의사항

1. 시간 기준으로 Train/Validation/Test를 먼저 분리합니다.
2. Train 데이터로만 Scaler를 Fit합니다.
3. Validation과 Test에는 동일한 Scaler를 적용합니다.
4. Scaler를 모델과 함께 저장하고 버전 관리합니다.
5. NOx와 SO₂는 기본적으로 별도 Scaler를 관리하는 방안을 권장합니다.

또한 Scaler는 2차원 ML-ready 데이터에서 Fit한 후 Sequence를 생성하는 방식이 좋습니다.

중복된 Sliding Window 데이터를 펼쳐서 Fit하면 동일 시점의 데이터가 반복 집계될 수 있기 때문입니다.

# 10\. 데이터 설계에서 추가로 확인할 사항

이번 설계는 전체적인 구조가 잘 잡혀 있습니다. 다만 실제 학습을 시작하기 전에 다음 항목을 확인해야 합니다.

| 점검 항목 | 확인 내용 | 중요도 |
| --- | --- | --- |
| 데이터 중복 | 동일 굴뚝·물질·측정 시각의 중복 여부 | 높음 |
| 시간 간격 | 30분 슬롯의 누락 및 중복 여부 | 높음 |
| 단위 일관성 | 측정값과 기준값의 단위 일치 여부 | 높음 |
| 비율 계산 | Silver ratio와 ML-ready ratio\_pct 일치 여부 | 높음 |
| Lag 계산 | 정확한 과거 시점의 데이터 사용 여부 | 높음 |
| Rolling 계산 | 현재 포함 여부 및 6개 슬롯 기준 확인 | 높음 |
| Label 생성 | 미래 데이터의 유효성 및 판정 조건 | 높음 |
| 데이터 누수 | 미래 정보가 Feature에 포함되는지 확인 | 매우 높음 |
| 시간 분할 | Train/Validation/Test의 시간 순서 유지 | 매우 높음 |
| Sequence 생성 | 굴뚝·물질별 연속된 30분 간격 유지 | 매우 높음 |
| Scaler | Train 데이터만 Fit하는지 확인 | 높음 |
| 버전 관리 | Feature/Label/품질 정책 버전 추적 | 보통 |

## 10.1 추가로 권장하는 검증

**① SO₂와 SOx 명칭 통일**

설계서에는 `item_code = nox / sox`로 되어 있지만 데이터 규모는 SO₂로 표현되어 있습니다.

SOx는 황산화물의 일반적인 표현이고 SO₂는 이산화황을 의미합니다.

실제 원천 데이터가 SO₂라면 `item_code`도 `so2`로 통일하는 것이 좋습니다. 원천 데이터가 SOx 전체를 의미한다면 별도로 정의해야 합니다.

**② Feature와 Label의 시간 기준 통일**

`measured_at`은 슬롯 시작 시각으로 정의되어 있습니다.

따라서 T+30분, T+60분의 의미가 다음 중 무엇인지 명확하게 정의해야 합니다.

- 슬롯 시작 시각 기준
- 30분 측정 구간의 종료 시각 기준

예측 시점과 Label 연결 시점이 다르면 잘못된 정답이 만들어질 수 있습니다.

**③ LSTM 학습 가능 데이터 규모 별도 산출**

현재 집계된 분류 9,857,884행과 회귀 10,687,144행은 ML-ready 행 기준입니다.

LSTM은 여기에 추가로 6개 연속 시점 조건을 적용해야 합니다.

따라서 실제 LSTM 학습 가능 Sequence 수는 별도로 집계해야 합니다.

다음과 같은 통계가 필요합니다.

| 구분 | 집계 항목 |
| --- | --- |
| ML-ready | 전체 행 수 |
| Feature 적격 | `feature_valid = True` |
| 분류 적격 | `classification_eligible = True` |
| 회귀 적격 | `regression_eligible = True` |
| LSTM 분류 | 6개 연속 시점 + 분류 Label 유효 |
| LSTM 회귀 | 6개 연속 시점 + 회귀 Label 유효 |

**④ 데이터 적격 조건의 의미 구분**

현재 `feature_valid`는 최근 6개 슬롯이 모두 존재한다는 의미입니다.

하지만 실제로는 슬롯이 존재하는 것과 24개 Feature가 모두 유효한 것은 다를 수 있습니다.

예를 들어 측정값은 존재하지만 `standard_value`가 NULL이면 `ratio_pct`와 관련 Feature를 계산할 수 없습니다.

따라서 다음을 구분하는 것이 좋습니다.

- 슬롯 존재 여부
- Feature 계산 가능 여부
- 분류 Label 유효 여부
- 회귀 Label 유효 여부

`feature_valid`가 이 조건들을 어디까지 포함하는지 명확하게 정의해야 합니다.

# 13\. 최종 점검 의견

현재 교육생들이 설계한 ML-ready 데이터 구조는 머신러닝과 시계열 예측 모델을 함께 고려한 구조입니다.

다만 ML-ready 행 수가 많다는 사실만으로 학습 데이터가 충분하다고 판단해서는 안 됩니다.

다음 세 가지를 반드시 확인해야 합니다.

1. **데이터 품질:** 실제로 Feature와 Label을 신뢰할 수 있는가?
2. **학습 데이터 구성:** 분류와 회귀의 학습 조건이 정확하게 적용되었는가?
3. **시계열 데이터 구성:** LSTM이 동일한 굴뚝과 물질의 연속된 과거 데이터만 학습하는가?

특히 RF/XGBoost와 LSTM은 동일한 24개 Feature를 사용하더라도 데이터 구성 방식이 다릅니다.

- RF/XGBoost: 현재 시점의 Feature 24개를 하나의 행으로 학습
- LSTM: 과거 6개 시점의 Feature 24개를 하나의 Sequence로 학습

최종적으로는 전체 ML-ready 데이터 건수가 아니라 **각 모델에 실제로 입력되는 학습 데이터 건수와 품질을 별도로 관리하는 것**이 중요합니다.

데이터가 만들어지는 과정부터 모델 입력까지 연결해서 설명할 수 있어야 설계가 제대로 완료되었다고 볼 수 있습니다.
