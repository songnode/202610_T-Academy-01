# 11/2~11/6 주간 작업 계획
## AI-Ready Data 기반 TMS 데이터 파이프라인 구축 — Bronze·Silver

- **작업 기간:** 2026-11-02(월) ~ 2026-11-06(금)
- **이번 주 목표:** 환경공단·EPA·합성 데이터의 원본을 Bronze에 안전하게 모으고, 환경공단과 EPA를 각각 믿고 쓸 수 있는 Silver로 표준화한다.
- **기준 문서:** [프로젝트 정본](<(정본)굴뚝 TMS 데이터 파이프라인 및 Hybrid AI 사전 경고 시스템_20261101_01.md>)("정본 3.3"처럼 적은 곳은 프로젝트 정본의 절)
- **작업 방식:** 이 문서는 **무엇을, 어떤 순서와 방식으로** 할지 큰 흐름만 알려 준다. 도구 선택·코드 구조·분담·하루 일정은 팀이 정하고, 고른 방법과 이유를 멘토링 때 설명한다.

> ## 이번 주 핵심 목표
>
> 1. 세 원천의 원본을 손대지 않고 Bronze에 보관한다.
> 2. 원천마다 다른 필드·단위·시간을 하나의 공통 언어(필드 사전)로 정리한다.
> 3. 환경공단과 EPA를 **각각 별도의** Silver로 표준화한다.
> 4. 합성 데이터가 Kafka를 거쳐 Bronze까지 들어오는 길을 연다.
> 5. Silver가 AI 학습에 쓸 만한지 점검하고 **Silver를 완성**한다.


| 날짜 | 기준점 |
|---|---|
| 11/2(월) | 현황 조사, 활용 원칙, 필드 사전 초안 |

| 11/4(수) | 환경공단·EPA Silver 표준화 |

### 이번 주에 꼭 이해할 원칙

- **Bronze는 원본 그대로.** 수정·삭제하지 않는다. 문제가 생기면 Bronze에서 다시 만든다.
- **환경공단과 EPA는 Silver를 나눈다.** 측정 간격(30분/60분), 단위, 기준의 뜻이 다르다.
- **표준화는 이름 맞추기가 아니다.** 값의 뜻·단위·시간 기준까지 맞춰야 한다.
- **이상한 데이터는 지우지 않고 격리한다.** 왜 격리했는지 남긴다.

### Bronze는 두 가지 형태로 둔다

원본 파일만 있으면 조회·재고 조사·계보 추적 때마다 수천 개의 JSON을 열어야 한다. 표만 있으면 표로 바꾸는 과정에서 생긴 실수를 되돌릴 원래 모습이 없다. 그래서 Bronze를 둘로 나눈다.

| 구분 | 담는 것 | 하는 일 | 저장 위치(예) |
|---|---|---|---|
| **Bronze Raw** | 환경공단 API 응답, EPA 원본 CSV, Kafka 원본 메시지 | 받은 그대로 파일로 보존. **이것이 원본의 정본이다** | `tms-raw-local/bronze/source=…/` |
| **Bronze Table** | Raw를 행·열로 옮긴 표 | 저장 형식과 열 구조만 입힌다. 정제·판단은 하지 않는다 | Iceberg `tms_bronze.*` |

```text
tms-raw-local/bronze/                                    ← Bronze Raw (파일)
├── source=tms_api/collected_date=2026-11-02/collector=b/…json.gz   (collector = b·c·aws)
├── source=epa/…/원본.csv
└── source=synthetic_kafka/collected_date=2026-11-05/…json

tms-lake-local/warehouse/tms_bronze/                      ← Bronze Table (Iceberg)
├── tms_api_responses/
├── epa_emissions/
└── synthetic_events/
```

**Bronze Table에서 해도 되는 것과 Silver로 미루는 것**

| Bronze Table에서 해도 됨 (구조화) | Silver로 미룸 (정제·판단) |
|---|---|
| JSON·CSV → Parquet/Iceberg로 저장 형식 바꾸기 | 문자열 → 숫자, 시각 → KST 같은 **값의 타입 변환** |
| 열 이름 정하기. 값은 **원본 문자열 그대로** 둔다 | 결측·상태 문구 판정, 이상값 판정 |
| 수집 일자 기준 파티션 | 중복 제거, 값이 다른 충돌 격리 |
| 메타 열 추가: `ingested_at`, `data_origin`, `source`, `collector`, 원본 파일 경로, Kafka 파티션·오프셋 | 단위·코드 표준화, 배출구 × 항목 펼치기 |
| 원본 한 건 = 표 한 행 (세 수집자의 원본도 **합치지 않고** 모두 남김) | 업무 규칙에 따른 검증 |

- **Bronze Table은 언제든 Raw에서 다시 만들 수 있어야 한다.** 표가 잘못되면 표를 다시 만들고, Raw는 절대 고치거나 지우지 않는다.
- **확정 표지가 있는 Raw만** 표로 옮긴다. 올리다 끊긴 파일이 표에 들어가지 않게 한다.
- **깨진 원본도 버리지 않는다.** 열로 나누지 못하면 원문 그대로를 담는 열에 넣고 "읽기 실패" 표시를 남긴다. 걸러 내는 일은 Silver의 격리가 한다.
- 값을 숫자로 바꾸지 않는 이유는 Task 5의 고민할 점("값을 숫자로 바꾼 뒤에 비교하면 무엇이 문제인가?")과 이어진다.

# 3. Task별 큰 흐름

## Task 1. 데이터 활용 원칙·Bronze 재고 조사

- **왜:** 무엇이 있는지 모르면 무엇을 만들지도 정할 수 없다.
- **무엇을:** 원천별(환경공단·EPA·합성) 활용 범위와, 지금 쌓인 원본의 양·기간·누락 구간.
- **어떤 방식으로**
  1. 원천마다 "주 데이터 / 부 데이터 / 시험용"으로 역할을 정하고 팀 전원이 합의한다.
  2. 쌓인 원본을 원천·수집자·기간별로 세어 본다.
  3. 빠진 구간이 "원천에서 안 온 것"인지 "수집이 실패한 것"인지 나눠 본다.
- **결과물:** 데이터 활용 원칙, Bronze 재고표
- **고민할 점:** 누락을 어떻게 구분할 수 있는가? 구분할 근거는 어디에 남아 있는가?

## Task 2. 환경공단 수집·S3 적재

- **왜:** 수집 장비가 여러 곳에 있어도 원본은 한곳에서 믿고 꺼내 쓸 수 있어야 한다.
- **무엇을:** 로컬에 모인 원본의 S3 Bronze 이관, 수집 실패에 대비한 클라우드 안전망, "이 구간은 확정"이라는 표지.
- **어떤 방식으로**
  1. 원본을 바꾸지 않고 옮긴다. 옮긴 뒤 건수·내용이 같은지 확인한다.
  2. 로컬 수집이 멈춰도 원본이 끊기지 않도록 별도 경로를 하나 둔다.
  3. 구간이 다 모이면 확정 표지를 남겨 다음 단계가 그것을 보고 움직이게 한다.
  4. 확정된 Raw를 Bronze Table로 옮긴다. Raw 건수와 표의 행 수가 맞는지 확인한다.
- **결과물:** S3 Bronze Raw·Bronze Table, 안전망 동작 기록, 확정 표지 규칙
- **고민할 점:** 같은 구간을 두 경로가 모두 수집하면 어떻게 할 것인가?

## Task 3. EPA 수집·Bronze 적재

- **왜:** EPA는 사건이 많은 긴 기간의 데이터라 패턴을 배우는 데 쓴다.
- **무엇을:** EPA 분기·시설 파일의 수집과 원본 보관.
- **어떤 방식으로**
  1. 받을 범위(지역·기간·파일 종류)를 먼저 정한다.
  2. 받은 파일을 그대로 Bronze에 둔다. 다시 받아도 결과가 같게 한다.
  3. 받은 파일 목록과 건수를 기록한다.
  4. 원본 CSV를 Bronze Table로 옮긴다. 큰 파일이라 이 단계부터 Spark Batch를 쓰는 것을 고려한다.
- **결과물:** EPA Bronze Raw·Bronze Table, 수집 기록(최소 분기 1개 확정)
- **고민할 점:** 큰 파일을 받다 중간에 끊기면 어떻게 이어 갈 것인가?

## Task 4. 공통 필드·표준화 설계

- **왜:** 원천마다 같은 것을 다른 이름·단위·시간대로 부른다.
- **무엇을:** 필드 사전(뜻·단위·시간대), 원천별 매핑, 공통 상태 코드, 품질 검사 항목.
- **어떤 방식으로**
  1. 두 원천의 필드를 나란히 놓고 "같은 뜻인지"부터 확인한다.
  2. 공통 필드와 원천 고유 필드를 나눈다.
  3. 매핑은 코드가 아니라 설정으로 관리해 바꾸기 쉽게 한다.
- **결과물:** 필드 사전, 원천별 매핑 설정
- **고민할 점:** 이름이 같은 NOx라도 뜻이 다르면 어떻게 표시할 것인가?
- **이번 주에는 하지 않음:** 단위 변환, 두 원천을 합친 공통 View

## Task 5. 환경공단 Silver 표준화

- **왜:** 이후 모든 Feature·모델·판정이 이 Silver를 믿고 쓴다.
- **무엇을:** 국내 실측 Silver, 중복·충돌 데이터 격리.
- **어떤 방식으로**
  1. 필드 사전대로 표준화한다. 빈 값은 채우지 않고 빈 값으로 둔다.
  2. 같은 측정이 두 번 오면 하나만 남기고, 값이 서로 다르면 격리한다.
  3. 로컬에서 만든 결과와 AWS에서 만든 결과를 비교해 같은지 확인한다.
- **결과물:** 환경공단 Silver, 격리 기록, 로컬·AWS 비교 결과
- **고민할 점:** "같은 측정"을 무엇으로 판단할 것인가? 값을 숫자로 바꾼 뒤에 비교하면 무엇이 문제인가?

## Task 6. EPA Silver 표준화

- **왜:** EPA를 국내와 같은 틀로 분석하려면 따로 표준화된 Silver가 필요하다.
- **무엇을:** EPA Silver(분기 1개 이상), 법적 기준이 없는 EPA에 쓸 대리 기준.
- **어떤 방식으로**
  1. 분기 1개로 먼저 끝까지 해 보고, 확인되면 넓힌다.
  2. 원본 단위와 시간대를 그대로 보존한다.
  3. 대리 기준은 법적 허용기준이 아님을 분명히 표시한다.
- **결과물:** EPA Silver, 대리 기준 정의
- **고민할 점:** EPA 시각을 KST로 바꿀 때 무엇을 조심해야 하는가?

## Task 7. AI-Ready Data 점검

- **왜:** 데이터가 "있다"와 "AI 학습에 쓸 수 있다"는 다르다.
- **무엇을:** Bronze·Silver 점검표와 실제 점검 결과, 쓸 수 있음·조건부·쓸 수 없음 판정.
- **어떤 방식으로**
  1. 뜻·구조, 품질, 계보, 시간 정합성, 누수 가능성을 기준으로 점검표를 만든다.
  2. 실제 데이터로 점검하고 숫자로 남긴다.
  3. 판정과 그 근거를 함께 적는다.
- **결과물:** AI-Ready 점검표, 판정 결과
- **고민할 점:** "조건부"는 어떤 조건에서 쓸 수 있다는 뜻인가?

## Task 8. 합성 데이터 생성

- **왜:** 실측에서는 드문 상황(급등·결측·지연 등)을 일부러 만들어 시스템을 시험한다.
- **무엇을:** 시나리오 정의, 합성 생성기 1차, 생성 결과 검수.
- **어떤 방식으로**
  1. 어떤 상황을 만들지 시나리오와 기대 결과를 먼저 적는다.
  2. 생성하는 사람과 검수하는 사람을 나눈다.
  3. 합성 데이터는 실측과 섞이지 않게 출처를 표시한다.
  4. 합성 시계를 지킨다. `measured_at`은 실측처럼 30분 격자로 만들고, 이벤트는 20분마다 보낸다(1.5배속). 시나리오 첫 `measured_at`은 "발행 시작 시각 − 시나리오 길이 ÷ 3"으로 둬 미래 시각이 생기지 않게 한다(정본 3.3).
- **결과물:** 시나리오 목록, 기대 결과, 생성기 1차, 검수 기록
- **고민할 점:** 합성 데이터가 "그럴듯하다"는 것을 어떻게 확인할 것인가?
- **참고:** 어떤 시나리오부터 만들지 막막하면 [부록. 합성 데이터를 만드는 관점](#부록-합성-데이터를-만드는-관점)을 먼저 본다.

## Task 9. Kafka → Bronze

- **왜:** 실시간 유입 경로를 실제로 한 번 열어 봐야 다음 주 스트리밍을 이어 갈 수 있다.
- **이번 주 범위:** 합성 경로의 **앞부분**만 만든다. "받아서 원본 그대로 보관"까지이고, 값을 정제하거나 바꾸지 않는다. Silver·Feature로 처리하는 뒷부분은 11/9 주 Task 12에서 같은 작업에 덧붙인다.

  ```text
  이번 주(11/2):  생성기 → Kafka 토픽 → Spark Structured Streaming → Bronze(S3 source=synthetic_kafka/)
  다음 주(11/9):                        └ 같은 Spark 작업에 덧붙임 → Silver → Feature → Rule 판정 → Gold
  ```

- **무엇을:** 합성 이벤트 형식(이벤트 계약), Kafka 발행, Bronze 적재.
- **어떤 방식으로**
  1. 이벤트를 토픽 `tms.synthetic.v1`에 메시지 키 `stack_code|item_code`로 보낸다(같은 배출구 × 항목의 순서 유지). 이벤트에 꼭 들어갈 내용과 형식을 먼저 정한다. 실제 API 응답과 같은 항목(측정값·허용기준)과 `event_id`·`scenario_id`·`generator_version`·`data_origin`·`measured_at`·`ingested_at`을 넣는다(정본 3.3).
  2. **Bronze에 쓰는 주체는 처음부터 Spark Structured Streaming으로 한다.** 임시 Python Consumer로 만들면 다음 주에 Spark로 다시 만들어야 한다. 이번 주 Spark 작업은 "읽어서 원본 그대로 쓰기"만 한다. trigger는 1분, 체크포인트는 S3(또는 MinIO)의 정해진 경로에 둔다.
  3. 실측 원본과 같은 규칙으로 보관한다. MinIO 버퍼에 먼저 쓰고 S3에 올려 확정 표지를 남긴다. Bronze에서는 고치거나 지우지 않는다.
  4. 이벤트 1건이 Bronze까지 가는 것을 먼저 확인하고 넓힌다.
  5. Spark 작업은 메시지 원문을 Bronze Raw에, 같은 메시지를 열로 옮긴 행을 Bronze Table(`tms_bronze.synthetic_events`)에 쓴다. Kafka 파티션·오프셋을 함께 남겨 원문과 행을 이어 준다.
  6. 형식이 깨진 이벤트도 Bronze에는 원본 그대로 남긴다(Table에는 원문 열 + 읽기 실패 표시). 걸러 내는 일은 다음 주 Silver 단계가 격리로 한다.
- **결과물:** 이벤트 계약, Kafka → Spark → Bronze 적재 시연
- **고민할 점:** 같은 이벤트가 두 번 오면 어떻게 할 것인가?
- **이번 주에는 하지 않음:** 합성 데이터의 Silver 적재(11/9 주)

## Task 10. PostgreSQL 설계

- **왜:** 처리 이력·경고 이력·메타데이터는 자주 조회하고 갱신하므로 운영 DB에 둔다.
- **무엇을:** 운영 이력·메타데이터 테이블 설계(DDL 초안).
- **어떤 방식으로**
  1. PostgreSQL에 둘 것과 두지 않을 것(대용량 측정값)을 먼저 나눈다.
  2. 모든 테이블에 공통으로 들어갈 메타 필드를 정한다.
- **결과물:** DDL 초안, 저장 위치 구분표
- **고민할 점:** 측정값을 PostgreSQL에 두지 않는 이유는 무엇인가?

## Task 11. 실행 주체·처리 방식 정리

- **무엇을:** Airflow·EventBridge·Kafka·Spark의 역할 정의.
- **어떤 방식으로:** 각 처리 단계마다 "누가 시작시키고, 누가 처리하고, 실패하면 누가 다시 하는지"를 표로 정리한다.
- **결과물:** 실행 역할 문서
- **고민할 점:** 배치와 스트리밍에서 각 도구가 맡는 일은 어떻게 다른가?

## Task 12. 버전·데이터 계보 관리

- **왜:** 숫자가 이상할 때 어느 단계에서 바뀌었는지 찾을 수 있어야 한다.
- **무엇을:** 처리 이력과 버전 규칙.
- **어떤 방식으로**
  1. 각 단계에서 무엇을 남겨야 거슬러 갈 수 있는지 정한다(원본 위치, 처리 시각, 처리 버전).
  2. Silver 한 행 → Bronze Table 행 → Bronze Raw 파일까지 실제로 따라가 본다.
- **결과물:** 버전·계보 규칙, 추적 시연
- **고민할 점:** 변환 규칙을 바꾸면 이전 결과는 어떻게 구분할 것인가?

## Task 13. Silver 변환 점검 테스트

- **왜:** 코드를 고칠 때마다 표준화가 깨지지 않았는지 사람이 일일이 볼 수 없다.
- **무엇을:** 고정 사례(입력 → 기대 결과)와 CI 자동 실행.
- **어떤 방식으로**
  1. 정상, 중복, 충돌, 빈 값, 이상한 상태 문구 같은 대표 사례를 고른다.
  2. 사례마다 기대 결과를 정하고, 코드가 바뀔 때마다 자동으로 비교한다.
- **결과물:** 고정 사례 묶음, CI 실행 기록
- **고민할 점:** 어떤 사례가 빠지면 가장 위험한가?

# 부록. 합성 데이터를 만드는 관점

합성 데이터는 "값을 많이 만드는 것"이 아니라 **"시스템에 질문을 던지는 것"**이다. 시나리오 하나는 "이런 상황이 오면 우리 시스템이 이렇게 반응하는가?"라는 질문 하나다. 그래서 값을 만들기 전에 **무엇을 확인하고 싶은지**부터 정한다.

## A. 네 가지 관점

시나리오는 아래 네 관점 중 하나에서 출발한다. 관점마다 1~2개씩 고르면 이번 주 시나리오 목록이 된다.

| 관점 | 던지는 질문 | 시나리오 예시 |
|---|---|---|
| ① 판정 경계 | 기준대비율이 단계 경계(80·90·100%)를 넘을 때 제대로 반응하는가? | 70%에서 3시간 동안 천천히 올라 95%에 닿는다 / 88~92% 사이를 오락가락한다 / 한 번에 100%를 넘는다 |
| ② 시간 패턴 | 실제로 일어날 법한 변화 모양을 흉내 낼 수 있는가? | 평소 수준 유지(정상 기준선) / 갑자기 튀었다 돌아옴(급등) / 서서히 올라감(완만한 상승) / 가동 중지 후 재가동 |
| ③ 데이터 품질 | 지저분한 데이터가 와도 정상으로 착각하지 않는가? | 값이 빈 채로 옴 / "보수중" 같은 상태 문구 / 허용기준이 비어 있음 / 숫자가 아닌 값·형식이 깨진 이벤트 |
| ④ 전달·운영 | 이벤트가 이상하게 도착해도 원본이 안전하게 쌓이는가? | 같은 이벤트가 두 번 옴(중복) / 같은 측정인데 값이 다름(충돌) / 60분 넘게 늦게 옴 / 순서가 뒤바뀜 / 발행이 한동안 멈춤 |

- ①②는 **다음 주 판정·학습**을 위한 재료이고, ③④는 **이번 주 Bronze·Kafka 경로**를 바로 시험할 수 있다. 이번 주에는 ④를 최소 1개 포함한다.
- 처음에는 **정상 기준선 시나리오 하나**를 꼭 만든다. "아무 일도 없을 때 아무 일도 안 일어나는가"가 모든 비교의 출발점이다.

## B. "그럴듯함"은 실측에서 출발한다

- **참조 배출구(`ref_stack_code`)를 먼저 고른다.** 그 배출구의 실제 값에서 평소 수준, 흔들림 폭, 30분 사이 변화량, 높은 값(P99)을 본다. 다음 주 v1부터는 Train 구간 통계만 쓴다(정본 11/9 주 Task 11).
- **평소 모습을 먼저 흉내 내고, 한 가지만 바꾼다.** 기준선이 실측처럼 보여야 그 위에 얹은 급등·결측이 "시험하려는 그 한 가지"가 된다.
- **불가능한 값은 만들지 않는다.** 음수 농도, 평소의 100배, 30분 만에 0 → 최대처럼 실제로 안 나올 값은 시스템이 아니라 생성기를 시험하는 셈이다. 일부러 넣는 경우는 ③(형식·품질) 시나리오로 따로 분리한다.
- **무작위 잡음만으로는 시나리오가 아니다.** 잡음은 기준선에 얹는 양념이고, 시나리오의 뼈대는 "언제, 얼마나, 어떤 모양으로" 바뀌는지다.

## C. 시나리오 한 장 쓰는 틀

생성기 코드를 쓰기 전에 시나리오마다 아래 칸을 채운다. 다 채우지 못하면 아직 시나리오가 정해지지 않은 것이다.

| 칸 | 적을 것 | 작성 예 |
|---|---|---|
| `scenario_id` | 고유 번호 | S-02 |
| 관점·질문 | A의 어느 관점, 무엇을 확인하나 | ① 판정 경계 — 천천히 올라 90%를 넘을 때 미리 경고하는가 |
| 용도 | 학습용 / 평가·시연용 (겹치지 않게, 정본 12.3) | 평가·시연용 |
| 대상 | 합성 배출구(`SYN-`)·항목·참조 배출구 | SYN-ULS-001-03, NOX, 참조 실측 배출구 1곳 |
| 길이 | 측정 몇 개(30분 격자) | 3시간(측정 7개) |
| 값의 궤적 | 시점별 기준대비율 또는 값 | 70 → 74 → 78 → 83 → 87 → 91 → 95% |
| 섞는 문제 | 품질·전달 문제가 있으면 무엇을, 몇 번째 측정에 | 없음 |
| 기대 결과 | 이번 주 / 다음 주로 나눠 적기 | 이번 주: Bronze에 7건 원본 그대로 / 다음 주: 83%부터 CAUTION, 91%부터 WARNING |
| 확인 방법 | 무엇을 보고 맞다고 판단하나 | Bronze 건수·`scenario_id`별 조회, 다음 주 판정 결과와 대조 |

## D. 자주 하는 실수

- **한 시나리오에 문제를 여러 개 섞는다.** 결과가 어긋났을 때 무엇 때문인지 알 수 없다. 한 시나리오 = 한 질문.
- **기대 결과를 나중에 적는다.** 결과를 보고 기대를 맞추면 검수가 아니다. 생성 전에 적고, 생성한 사람이 아닌 사람이 대조한다.
- **기대 결과를 라벨이나 모델 입력으로 쓴다.** 기대 결과는 채점표일 뿐이다(정본 12.3).
- **학습용과 평가용 시나리오를 같이 쓴다.** 모델이 본 문제로 시험 보는 셈이다.
- **실제 배출구 코드를 쓴다.** 실제 사업장에 가짜 경고가 나갈 수 있다. 반드시 `SYN-` 접두어.
- **극적인 장면만 만든다.** 급등만 잔뜩이면 "평소에 조용한가"는 시험되지 않는다.

## E. 검수할 때 던질 질문
