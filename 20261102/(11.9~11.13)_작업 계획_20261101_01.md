### 이번 주에 꼭 이해할 원칙

- **라벨과 판정은 다르다.** 라벨은 과거로 만든 정답이고, Rule Engine은 지금 값으로 현재 단계를 정한다.
- **빈 값은 채우지 않는다.** 0이나 직전 값으로 메우면 모델이 거짓을 배운다.
- **배치와 스트리밍은 같은 함수를 쓴다.** 같은 데이터면 같은 결과가 나와야 한다.
- **EPA 기준은 법적 기준이 아니다.** 같은 NOx라도 국내는 농도, EPA는 배출률일 수 있다.

# 3. Task별 큰 흐름

## Task 1. 국내 EDA

- **왜:** 어떤 항목이 학습할 만큼 사건이 있는지 알아야 대상을 정할 수 있다.
- **어떤 방식으로**
  1. 항목·배출구별 분포, 결측, 상태 문구를 본다.
  2. 경고 수준에 가까워진 사건이 몇 번 있었는지 센다.
  3. 사건 수와 품질을 근거로 ML 대상 항목을 예비로 고른다.
- **결과물:** EDA 보고서, 항목별 사건 수, ML 대상 예비 목록
- **고민할 점:** 사건이 너무 적은 항목은 어떻게 다룰 것인가?

## Task 2. 데이터 구간 확정

- **왜:** 구간이 흔들리면 모든 평가가 의미를 잃는다.
- **어떤 방식으로**
  1. 네 구간을 날짜로 확정하고 문서로 남긴다.
  2. 구간 경계 근처에서 다음 구간 정보가 앞 구간으로 새지 않게 경계 처리 규칙을 정한다.
- **결과물:** 구간 확정 문서
- **고민할 점:** 60분 뒤를 맞히는 라벨이라면 경계에서 무엇이 새어 나갈 수 있는가?

## Task 3. 라벨 생성

- **왜:** 모델은 라벨을 정답으로 믿고 배운다. 라벨이 틀리면 모델도 틀린다.
- **무엇을:** 분류 라벨(60분 안에 기준 90%에 들어가는가), 회귀 라벨(60분 뒤 기준대비율).
- **어떤 방식으로**
  1. "다음 60분"은 t+30, t+60 두 행이다. 기준대비율은 반올림 없이 ≥ 0.90으로 비교하고, 측정 시각에 유효한 허용기준을 쓴다(정본 4.4·부록 B `label-v1`).
  2. 미래 값이 빠지면: 하나라도 확인된 진입이면 1로 둔다. 0은 두 값이 모두 유효할 때만 정한다. 나머지는 제외한다. 미래의 상태 문구는 음성이 아니라 "알 수 없음"이다.
  3. 제외한 행 수를 이유별(결측 / 상태 문구 / 허용기준 없음)·항목별로 기록한다.
  4. 행에 `is_reentry`를 표시하고, 사건을 셀 때는 끝난 뒤 60분 안에 다시 진입하면 같은 사건으로 묶는다.
  5. 회귀 라벨은 t+60 값이다. 모든 유효 행을 쓰고, t+60이 없으면 제외한다. 학습 라벨의 상한은 200%로 둔다(평가는 원래 값).
  6. 라벨은 구간이 닫힌 뒤 정한 시각의 Silver 스냅샷으로 만들고, `label_version`(`label-v1`)을 기록한다. 합성 행도 같은 규칙이다(Silver에 들어온 값, 합성 행 자신의 허용기준).
  7. 시점과 위 경우들이 맞는지 고정 사례로 확인한다(t+30만 ≥ 0.90, t+60만 ≥ 0.90, 한쪽 결측, 상태 문구, 재진입).
  8. **11/12까지 규칙을 고정**하고, Validation 결과를 본 뒤 바꾸지 않는다.
- **결과물:** 라벨 생성 코드, `label-v1` 규칙 문서, 제외 건수 기록, 시점 정합성·경우별 고정 사례 테스트
- **고민할 점:** 미래 정보가 특성에 섞이지 않았다는 것을 어떻게 증명할 것인가?

## Task 4. 공통 Feature Library

- **왜:** 학습할 때와 실시간 판정할 때 특성 계산이 다르면 모델이 엉뚱하게 동작한다.
- **무엇을:** 과거 값(Lag), 구간 통계(Rolling), 상태·시간 특성을 계산하는 공통 함수. 기존 국내 Feature 14개(정본 4.1)에 더해 **추가 후보 3개**(`ratio_diff_60m`, `ratio_diff_120m`, `ratio_slope_3h`)도 만든다. 넣을지는 11/18에 B의 Validation으로 정한다.
- **어떤 방식으로**
  1. 특성 목록과 계산 규칙을 설정으로 정한다.
  2. 30분·60분 간격 모두에서 맞게 동작하게 한다.
  3. 값이 모자란 구간은 계산하지 않고 비워 둔다. 기준은 정해져 있다: 3시간 창은 6개 중 4개 이상, 1시간 창은 2개 모두(정본 4.1).
- **결과물:** 공통 Feature Library, 간격별 고정 사례 테스트
- **고민할 점:** 창에 값이 모자라 빈 값이 된 행이 많은 배출구는 학습과 판정에서 어떻게 보이는가?

## Task 5. Feature 데이터셋·준비도 게이트

- **왜:** 학습 직전에 데이터가 정말 학습에 맞는지 한 번 더 걸러야 한다.
- **어떤 방식으로**
  1. Silver + 공통 Feature Library + 라벨로 Feature 데이터셋을 만든다.
  2. 구간 분리, 누수, 결측, 출처 구분을 점검하는 게이트를 만들고 통과 여부를 기록한다.
- **결과물:** Feature 데이터셋, 게이트 결과
- **고민할 점:** 게이트에서 "실패"하면 무엇을 멈출 것인가?

## Task 6. EPA Silver 확장

- **왜:** EPA 패턴을 배우려면 긴 기간의 데이터가 모두 필요하다.
- **어떤 방식으로:** 지난주 분기 1개로 검증한 방식을 전체 분기로 넓힌다. 늘린 뒤에도 건수와 품질을 확인한다.
- **결과물:** EPA Silver 전체 분기(못 끝내면 사유와 계획)

## Task 7. EPA 현상 분석

- **왜:** EPA에서 본 현상이 있어야 그것을 국내 특성으로 옮길 근거가 생긴다.
- **무엇을:** 가동 재개, 변동성 증가, 여러 항목 동시 상승 — 경고 직전에 이런 현상이 실제로 있는가.
- **어떤 방식으로:** 경고 진입 직전 구간과 평소 구간을 나눠 비교한다.
- **결과물:** 현상 분석 결과
- **고민할 점:** "있다"고 말하려면 어떤 비교가 필요한가?

## Task 8. 공통 특성 정의

- **왜:** 단위와 기준이 다른 두 원천을 함께 쓰려면 단위 없는 특성이 필요하다.
- **무엇을:** 두 원천에서 같은 식·같은 시간 창으로 계산하는 상대 특성 5개(`common-v1`: `rel_p99`, `rel_diff_60m`, `rel_roll_mean_3h`, `rel_roll_std_3h`, `hour`, 정본 부록 C), Task 7을 근거로 한 국내 특성 후보.
- **어떤 방식으로**
  1. 자기 P99 대비 비율로 단위를 없앤다. 국내 P99는 Train 구간 값으로만 낸다.
  2. 시차·창은 행 수가 아니라 시간(분)으로 정하고 `measured_at`으로 찾는다.
  3. 최소 유효 값 수(국내 3시간 창 6개 중 4개, EPA 3개 모두)를 지키고 빈 값은 채우지 않는다.
  4. 같은 흐름을 30분·60분 계열로 만든 고정 사례 테스트로 두 원천의 결과를 확인한다.
- **결과물:** 공통 특성 정의서(`config/features.yaml`의 `common-v1`), 고정 사례 테스트, 국내 특성 후보 목록
- **고민할 점:** 3시간 창에 국내는 값 6개, EPA는 3개가 들어간다. 표준편차가 같은 뜻이 되는가?

## Task 9. EPA 점수 모델

- **왜:** EPA의 많은 사건으로 "급등 패턴"을 배워, 그 점수를 국내 모델의 특성 하나로 쓴다.
- **어떤 방식으로**
  1. EPA 데이터만으로 학습한다(국내 데이터가 들어가지 않게).
  2. 버전을 고정하고 기록한다.
  3. 국내 NOx·SOx에 점수를 계산할 준비를 한다. 그 밖 항목은 빈 값으로 둔다(정본 부록 C.6).
- **결과물:** EPA 점수 모델(또는 학습 준비 코드)
- **고민할 점:** 이 점수를 국내 모든 항목에 써도 되는가?

## Task 10. 비교 실험 준비

- **왜:** 실험 조건이 다르면 비교가 의미 없다.
- **무엇을:** B(국내만, 기본·확장 Feature 세트) → B+E(EPA 점수 추가) → +S(합성 Train 추가)를 같은 조건으로 돌릴 준비. B+EP(EPA 행을 낮은 비중으로 합침)는 Could·참고 실험이다.
- **어떤 방식으로:** 같은 데이터 구간·같은 평가 방식으로 돌아가는 실험 틀을 만든다. B+EP를 할 경우에 대비한 합동 학습 데이터 구조는 선택이다.
- **결과물:** 실험 실행 코드, 실험 계획서

## Task 11. 합성 생성기 v1

- **왜:** 실측과 닮은 합성 데이터여야 시험과 증강에 쓸 수 있다.
- **어떤 방식으로:** Train 구간 통계만으로 생성 규칙을 정하고(다른 구간 정보를 쓰지 않음), 만든 데이터를 Kafka로 보낸다. 합성 배출구 × 항목마다 크기 통계를 가져온 참조 실측 배출구(`ref_stack_code`)를 하나 정해 기록한다. EPA 점수 계산에 그 배출구의 P99를 쓴다(정본 3.3, 부록 C.4). 합성 시계(30분 격자 `measured_at`, 20분마다 발행)는 1차와 같다.
- **결과물:** 합성 생성기 v1, 생성 결과

## Task 12. Kafka → Spark 스트리밍

- **왜:** 실시간으로 들어온 데이터도 배치와 같은 Silver·Feature를 거쳐야 한다.
- **11/2 주와의 차이:** 지난주에는 합성 이벤트를 **받아서 원본 그대로 보관**(Bronze)만 했다. 이번 주에는 같은 Spark 작업에 **처리 단계**를 덧붙여, 합성 행이 실측 행과 똑같이 Silver·Feature·현재 판정을 거치게 한다.

  | | 11/2 주 Task 9 | 이번 주 Task 12 |
  |---|---|---|
  | 범위 | 생성기 → Kafka → Spark → Bronze | 같은 Spark 작업 + Silver → Feature → Rule 판정 → Gold |
  | 값을 바꾸나 | 바꾸지 않음(원본 보존) | 정제·표준화·특성 계산 |
  | 핵심 | 이벤트 계약, 원본 보관 | 배치와 같은 공통 코드, 늦은·중복 이벤트 처리 |

- **어떤 방식으로**
  1. 지난주 Spark 작업을 새로 만들지 않고 이어 붙인다. Bronze 쓰기는 그대로 두고 그 뒤에 처리 단계를 더한다.
  2. 표준화와 특성 계산은 배치(표준화 Lambda·판정 Lambda)와 **같은 공통 코드**를 쓴다. 같은 입력이면 배치와 스트리밍이 같은 Silver 행·같은 Feature를 내야 한다.
  3. 중복 이벤트(같은 `event_id`)는 Silver에서 1행으로, 형식이 깨진 이벤트는 실측과 같은 격리 테이블로 보낸다.
  4. 정해진 운영 규칙(정본 3.3 "합성 스트리밍 운영 규칙")을 따른다.
     - 워터마크는 `measured_at` 기준 60분. 넘은 이벤트는 Silver에서 `late_beyond_watermark`로 격리한다.
     - `foreachBatch`로 Silver에 먼저 쓰고, 그 배치의 배출구 × 항목만 Silver에서 3시간 창을 읽어 Feature를 계산한다.
     - 메시지 키 `stack_code|item_code`, 토픽 `tms.synthetic.v1`.
     - trigger 1분, 체크포인트는 S3(또는 MinIO)에 둔다.
     - 합성 행의 신선도는 처리 시각 − `ingested_at`으로 본다(1.5배속이라 `measured_at`으로 보면 안 된다).
- **결과물:** 스트리밍 연결 시연, 처리 이력, 같은 입력을 배치·스트리밍에 넣어 결과가 같은지 확인하는 테스트
- **고민할 점:** 워터마크(60분)를 넘어 격리된 이벤트가 많아지면 무엇을 의심해야 하는가?
