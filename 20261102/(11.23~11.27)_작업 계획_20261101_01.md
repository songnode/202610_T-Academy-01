# 11/23~11/27 주간 작업 계획
## TMS 데이터 파이프라인 및 Hybrid AI 사전 경고 시스템 구축 — Test 운영과 중간 평가

- **작업 기간:** 2026-11-23(월) ~ 2026-11-27(금)
- **이번 주 목표:** 11/20에 고정한 모델과 판정 흐름 **그대로** Test 구간(11/23~12/4) 운영을 시작하고, 11/27에 **Test-1(11/23~11/26) 중간 평가**를 한다. 최종 성능 수치는 Test 전체로 12/7에 낸다.
- **기준 문서:** [프로젝트 정본](<(정본)굴뚝 TMS 데이터 파이프라인 및 Hybrid AI 사전 경고 시스템_20261101_01.md>)("정본 3.3"처럼 적은 곳은 프로젝트 정본의 절)
- **작업 방식:** 이 문서는 큰 흐름만 알려 준다. 방법·도구·분담은 팀이 정하고 이유를 멘토링 때 설명한다.

> **이번 주에는 모델을 새로 학습하거나 고치지 않는다.** 고정한 모델이 처음 보는 실측 데이터에서 얼마나 맞히는지 확인하는 주다. Test는 12/4까지 이어지므로 **Test-1 결과를 본 뒤에도 아무것도 바꾸지 않는다**(정본 4.5).

> ## 이번 주 핵심 목표
>
> 1. 고정한 상태 그대로 Test 구간을 운영하고, 운영 상태와 장애만 기록한다.
> 2. 장애에 대비한 절차서를 만든다.
> 3. 합성 시나리오로 시스템 반응을 평가한다.
> 4. 11/27에 승인 모델만 Test-1로 중간 평가하고, 왜 틀렸는지 1차로 분석한다.
> 5. 데이터 품질·모델 성능·시나리오 반응을 **섞지 않고** 중간 보고한다.

# 3. Task별 큰 흐름

## Task 1. Test 운영

- **왜:** 실제 운영처럼 돌려야 Test 결과가 운영 성능을 말해 준다.
- **어떤 방식으로**
  1. 고정한 상태 그대로 매일 데이터를 처리한다. 운영은 12/4까지 이어진다.
  2. 매일 수집·처리 건수, 장애, 조치만 기록한다(정답 라벨과 성능은 보지 않는다).
- **결과물:** 날짜별 운영 일지(12/4까지)
- **고민할 점:** 장애로 빠진 데이터는 평가에서 어떻게 다룰 것인가?

## Task 2. 운영 안정화·장애 대응 절차서

- **왜:** 장애가 났을 때 누구든 같은 순서로 확인하고 복구할 수 있어야 한다.
- **어떤 방식으로:** Bronze부터 Gold까지 단계마다 "무엇이 깨질 수 있나 → 어떻게 알아채나 → 어떻게 복구하나"를 정리한다. 이번 주 실제 장애 사례를 반영한다.
- **결과물:** 장애 대응 절차서(Runbook)

## Task 3. 합성 시나리오 반응 평가

- **왜:** 결측·급등·중복·지연처럼 드문 상황에서 시스템이 설계대로 반응하는지 확인한다.
- **어떤 방식으로:** 준비한 시나리오를 운영과 같은 경로로 흘리고, 시나리오마다 기대 결과와 실제 반응을 비교해 일치율을 낸다.
- **결과물:** 시나리오 반응 평가 결과

## Task 4. Test-1 중간 평가

- **왜:** 처음 보는 실측에서의 성능을 먼저 확인하고, 12/7 최종 평가 전에 오류 분석을 시작한다.
- **어떤 방식으로**
  1. 11/27 01:00 이후(Test-1 마지막 구간의 정답이 만들어진 뒤) 승인된 분류·회귀 모델만 Test-1로 평가한다.
  2. Validation 결과와 나란히 놓고 비교한다.
  3. 규칙만 쓸 때와 규칙 + ML을 쓸 때를 비교한다(사건을 더 먼저, 더 많이 잡는가).
  4. 사건 수와 신뢰 구간(배출구 단위)을 함께 적고, 결과표에 "중간 결과(Test-1)"라고 표시한다.
  5. 결과를 보고 모델·임계값·특성·규칙을 바꾸지 않는다.
- **결과물:** 분류·회귀 Test-1 결과표, 규칙만 vs 규칙 + ML 비교표(중간)
- **고민할 점:** Test-1은 주말이 없고 사건이 적다. 이 숫자를 어떻게 설명할 것인가?

## Task 5. 모델 오류 분석(1차)

- **왜:** 숫자만으로는 다음에 무엇을 고쳐야 할지 알 수 없다.
- **어떤 방식으로:** Test-1에서 놓친 사건, 오경보, 회귀 오차가 큰 사례를 골라 데이터·특성·모델 중 어디서 생긴 문제인지 나눠 본다. 12/7 주에 Test 전체로 보완한다.
- **결과물:** 오류 분석 기록(1차), 개선 방향(프로젝트 중에 적용하지 않음)

## Task 6. EPA·합성 효과 정리

- **왜:** EPA와 합성을 왜 썼는지, 실제로 도움이 됐는지를 정직하게 말해야 한다.
- **어떤 방식으로:** Validation 기준의 B·B+E·+S 비교, (실행했으면) B+EP 참고 결과, 시나리오 결과를 서로 섞지 않고 정리한다. 효과가 없었다면 그것도 결과다.
- **결과물:** 데이터 활용 효과와 한계 정리

## Task 7. 평가 세 축 보고서(중간판)

- **왜:** 서로 다른 질문의 답을 한 숫자로 섞으면 아무것도 말하지 못한다.
- **무엇을:** ① 데이터가 정확하게 변환됐는가 ② 모델이 맞혔는가 ③ 시스템이 설계대로 반응했는가.
- **어떤 방식으로:** 세 축을 각각 따로 정리하고, 마지막에 한눈에 보는 요약을 붙인다. ② 모델 성능은 Test-1 값으로 적고, 12/7 주에 Test 전체 값으로 바꾼다.
- **결과물:** 평가 세 축 보고서(중간판)

## Task 8. Gold·데이터 흐름 완료 점검

- **왜:** 다음 주부터는 Gold와 모델 위에 Agent를 올린다. 기반이 끝났는지 확인해야 한다.
- **어떤 방식으로:** 데이터 흐름, 모델 등록·고정, Test-1 평가 항목을 PASS·FAIL로 점검하고 FAIL은 이유와 처리 방향을 적는다. 모델 최종 점검은 12/7 주 Test 전체 평가 뒤에 한다.
- **결과물:** 완료 점검표(중간)

## Task 9. 외부 API 사전 확인

- **왜:** 다음 주 첫날 API 키나 조회 범위 문제로 막히지 않게 한다.
- **어떤 방식으로:** 주변 대기질·기상 API의 과거 자료 조회 가능 범위와, JEV 키 발급·호출(불일치 분류 요청 형식)을 미리 시험한다.
- **결과물:** API 확인 결과

# 8. 이번 주에 가장 중요한 것

1. **데이터:** Bronze부터 Gold까지 안정적으로 처리되는가?
2. **모델:** 고정한 모델이 처음 보는 실측에서도 쓸 만한가?(중간 답, 최종 답은 12/7)
3. **시스템:** 드문 상황에서도 설계대로 반응하는가?

세 질문에 근거를 붙여 답할 수 있으면, 다음 단계의 LLM·Agent가 믿고 쓸 기반이 생긴다.
