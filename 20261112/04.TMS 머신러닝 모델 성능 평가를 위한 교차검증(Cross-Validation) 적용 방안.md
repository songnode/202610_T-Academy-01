# TMS 머신러닝 모델 성능 평가를 위한 교차검증(Cross-Validation) 적용 방안

- 작성일: 2026.11.12
- 대상: TMS AI 이상 탐지 및 사전 경고 시스템
- 적용 모델: S1-C, N1-R, S1-R

---

## 1. 검토 배경

현재 TMS 프로젝트는 대만 CEMS 데이터를 활용하여 머신러닝 모델을 개발하고 있습니다.

모델의 성능을 평가할 때 Train, Validation, Test 데이터로 구분하는 일반적인 방법을 사용하고 있지만, 하나의 데이터 분할 결과만으로 모델의 성능을 판단하면 특정 기간의 데이터 특성에 따라 평가 결과가 달라질 수 있습니다.

예를 들어 특정 기간에는 오염물질 농도가 안정적으로 유지되다가 다른 기간에는 급격한 변동이나 고농도 발생이 많을 수 있습니다. 이때 한 번의 데이터 분할 결과만으로 모델의 성능을 판단하면 모델이 실제로 얼마나 안정적인지 충분히 확인하기 어렵습니다.

이러한 문제를 보완하기 위해 **교차검증(Cross-Validation)** 을 적용하고자 합니다.

이번 검토의 목적은 다음과 같습니다.

1. 서로 다른 기간의 데이터로 모델을 반복 평가하여 성능의 안정성을 확인합니다.
2. 특정 기간에만 성능이 좋은 모델인지 확인합니다.
3. 모델별 성능 편차와 일반화 가능성을 비교합니다.
4. 최종 Validation 및 Test 데이터의 역할을 유지하면서 평가 결과의 신뢰성을 높입니다.

단, TMS 데이터는 시간의 흐름에 따라 수집되는 시계열 데이터이므로 일반적인 무작위 K-Fold가 아닌 **시간 순서를 유지하는 시계열 교차검증(Time Series Cross-Validation)** 을 적용합니다.

## 2. 교차검증이란?

교차검증은 하나의 데이터셋을 여러 구간으로 나누고, 학습과 검증을 반복하여 모델의 성능을 평가하는 방법입니다.

일반적인 5-Fold 교차검증에서는 전체 데이터를 5개 구간으로 나눈 뒤, 각 구간을 한 번씩 검증 데이터로 사용합니다.

예를 들어 다음과 같습니다.

| 반복 | 학습 데이터 | 검증 데이터 |
|---|---|---|
| 1회차 | Fold 2~5 | Fold 1 |
| 2회차 | Fold 1, 3~5 | Fold 2 |
| 3회차 | Fold 1~2, 4~5 | Fold 3 |
| 4회차 | Fold 1~3, 5 | Fold 4 |
| 5회차 | Fold 1~4 | Fold 5 |

각 검증 구간에서 측정한 성능을 비교하면 특정 데이터 구간에 따라 모델의 성능이 얼마나 달라지는지 확인할 수 있습니다.

다만 위 방식은 데이터의 시간 순서를 고려하지 않는 일반적인 K-Fold 방식입니다.

### 2.1 TMS 데이터에 일반 K-Fold를 그대로 적용하면 안 되는 이유

TMS 데이터는 시간 순서가 중요합니다.

예를 들어 2025년 데이터를 학습하는데 2026년 데이터를 검증하는 것은 자연스럽지만, 2026년 데이터를 학습하면서 2025년 데이터를 검증하는 방식은 실제 운영 상황과 맞지 않습니다.

실제 운영에서는 과거 데이터를 이용해 미래의 값을 예측하기 때문입니다.

따라서 다음 원칙을 적용해야 합니다.

- 과거 데이터로 학습합니다.
- 학습에 사용하지 않은 이후 기간의 데이터로 검증합니다.
- 검증 구간은 시간 순서대로 이동합니다.
- 검증 구간이 바뀔 때마다 학습 데이터는 과거 방향으로 누적합니다.

이러한 방식을 **Expanding Window 방식의 시계열 교차검증**이라고 합니다.

## 3. 현재 TMS 데이터 구성 및 역할

현재 프로젝트에서 사용하는 대만 CEMS 데이터의 기간은 다음과 같습니다.

| 데이터 구분 | 데이터 기간 | 기간 | 주요 용도 |
|---|---|---:|---|
| Train | 2023.11 ~ 2025.10 | 24개월 | 교차검증 및 모델 학습 |
| Validation | 2025.11 ~ 2026.04 | 6개월 | 최종 모델 설정 및 운영 기준 결정 |
| Test | 2026.05 ~ 2026.10 | 6개월 | 최종 성능 평가 |
| 국내 TMS | 2026.10.31 ~ 2026.11.10 | 별도 기간 | 외부 데이터 일반화 평가 |

여기서 중요한 점은 **Train 데이터 안에서 교차검증을 수행하고, 기존 Validation과 Test 데이터는 별도로 유지한다는 것**입니다.

교차검증을 한다고 해서 기존 Validation이나 Test 데이터를 다시 Fold에 포함하는 것은 아닙니다.

### 3.1 각 데이터의 역할

| 데이터 | 역할 | 사용 가능 작업 | 주의사항 |
|---|---|---|---|
| Train | 모델 학습 및 교차검증 | 모델 학습, Feature 비교, 하이퍼파라미터 비교 | Fold별 학습 구간만 사용 |
| Validation | 최종 모델 설정 | 최종 모델 설정, 운영 임계값 결정 | Fold 검증에 중복 사용하지 않음 |
| Test | 최종 성능 평가 | 최종 성능 측정 및 보고 | 모델 선택이나 튜닝에 사용하지 않음 |
| 국내 TMS | 외부 데이터 평가 | 국내 데이터에 대한 일반화 성능 확인 | 학습 및 튜닝에 사용하지 않음 |

각 데이터의 역할을 쉽게 설명하면 다음과 같습니다.

- **Train:** 모델을 학습하고 여러 기간으로 나누어 성능을 확인하는 데이터
- **Validation:** 교차검증 결과를 바탕으로 최종 모델과 운영 기준을 결정하는 데이터
- **Test:** 최종적으로 선택한 모델이 새로운 기간에서도 어느 정도 성능을 보이는지 확인하는 데이터
- **국내 TMS:** 대만 데이터로 개발한 모델이 국내 데이터에서도 적용 가능한지 확인하는 외부 평가 데이터

## 4. TMS 교차검증 Fold 구성

이번 교차검증은 Train 데이터 24개월을 대상으로 4-Fold Expanding Window 방식으로 구성합니다.

각 Fold의 검증 기간은 3개월이며, 검증 기간이 뒤로 이동할수록 학습 데이터가 누적되는 구조입니다.

### 4.1 Fold별 데이터 구성

| 구분 | 학습 데이터 | 학습 기간 | 검증 데이터 | 검증 기간 |
|---|---|---:|---|---:|
| Fold 1 | 2023.11 ~ 2024.10 | 12개월 | 2024.11 ~ 2025.01 | 3개월 |
| Fold 2 | 2023.11 ~ 2025.01 | 15개월 | 2025.02 ~ 2025.04 | 3개월 |
| Fold 3 | 2023.11 ~ 2025.04 | 18개월 | 2025.05 ~ 2025.07 | 3개월 |
| Fold 4 | 2023.11 ~ 2025.07 | 21개월 | 2025.08 ~ 2025.10 | 3개월 |

각 Fold의 학습 기간은 이전 Fold의 학습 데이터와 검증 데이터를 누적하여 확장합니다.

### 4.2 Fold 구성 이해하기

```text
전체 Train 데이터 (2023.11 ~ 2025.10)
│
├─ Fold 1
│  ├─ 학습: 2023.11 ~ 2024.10
│  └─ 검증: 2024.11 ~ 2025.01
│
├─ Fold 2
│  ├─ 학습: 2023.11 ~ 2025.01
│  └─ 검증: 2025.02 ~ 2025.04
│
├─ Fold 3
│  ├─ 학습: 2023.11 ~ 2025.04
│  └─ 검증: 2025.05 ~ 2025.07
│
└─ Fold 4
   ├─ 학습: 2023.11 ~ 2025.07
   └─ 검증: 2025.08 ~ 2025.10
```

예를 들어 Fold 1에서는 2023년 11월부터 2024년 10월까지의 데이터로 학습하고, 그 이후인 2024년 11월부터 2025년 1월까지의 데이터로 검증합니다.

Fold 2에서는 기존 Fold 1의 학습 및 검증 기간을 포함하여 2025년 1월까지 학습하고, 2025년 2월부터 4월까지 검증합니다.

이 과정을 반복하면 과거 데이터만으로 미래 기간을 예측하는 상황을 여러 번 재현할 수 있습니다.

### 4.3 Fold 구성 시 확인할 사항

- 각 Fold의 학습 데이터와 검증 데이터가 시간상 겹치지 않아야 합니다.
- 검증 데이터는 학습 데이터보다 항상 이후 기간이어야 합니다.
- 동일한 기간의 데이터가 학습과 검증에 동시에 포함되지 않도록 해야 합니다.
- 모델별로 동일한 Fold 구성을 적용해야 공정한 비교가 가능합니다.
- 실제 데이터 건수와 라벨 생성 결과를 확인한 후 최종 Fold 구성을 확정해야 합니다.

## 5. 시계열 데이터의 데이터 누수 방지

교차검증에서 가장 중요한 부분 중 하나는 데이터 누수(Data Leakage)를 방지하는 것입니다.

데이터 누수란 모델 학습 과정에서 실제 예측 시점에는 알 수 없는 미래 정보가 사용되는 문제입니다.

TMS 프로젝트는 30분 단위로 데이터가 수집되고, 향후 60분의 값을 예측하거나 위험 진입 여부를 판단합니다.

따라서 학습 데이터와 검증 데이터의 경계에서 미래 정보가 섞이지 않도록 주의해야 합니다.

### 5.1 예측 시점과 라벨 생성 기준

현재 프로젝트의 모델은 다음과 같습니다.

| 모델 | 유형 | 예측 대상 |
|---|---|---|
| S1-C | Classification | 향후 60분 이내 SO₂ 위험 기준 진입 여부 |
| N1-R | Regression | 60분 후 NOx 실제 농도 |
| S1-R | Regression | 60분 후 SO₂ 실제 농도 |

30분 단위 데이터이므로 60분 후의 값은 일반적으로 두 행 이후의 값에 해당합니다.

예를 들어 다음과 같습니다.

| 현재 시점 | 예측 대상 시점 |
|---|---|
| 10:00 | 11:00 |
| 10:30 | 11:30 |
| 11:00 | 12:00 |

이때 학습 데이터의 마지막 시점에 해당하는 라벨을 만들기 위해 검증 기간의 실제 측정값을 가져오면 데이터 누수가 발생할 수 있습니다.

따라서 **학습 데이터의 라벨이 검증 기간의 미래 측정값에 의존하는 행은 학습에서 제외해야 합니다.**

실제 제외 건수는 라벨 생성 코드와 `excluded_rows` 처리 결과를 기준으로 확인합니다. 단순히 시간 기준으로 일괄 제외하기보다는 Stack, Item, timestamp 연속성 및 결측 구간을 함께 고려해야 합니다.

### 5.2 72시간 Rolling Feature 처리

현재 Feature Engineering에서는 과거 72시간의 데이터를 활용하는 Rolling Feature를 검토하고 있습니다.

이때 검증 시작 시점 이전의 과거 72시간 데이터를 활용하는 것은 허용할 수 있습니다.

실제 운영에서도 현재 시점의 예측을 위해 직전 72시간의 측정값을 활용하기 때문입니다.

예를 들어 검증 기간이 2025년 2월 1일부터 시작한다면, 1월 31일 이전의 과거 데이터는 검증 시점에 이미 확보된 정보이므로 사용할 수 있습니다.

다만 다음 사항을 확인해야 합니다.

- Rolling 계산은 과거 방향으로만 수행해야 합니다.
- 미래 데이터를 참조하는 `center=True` 등의 설정을 사용하지 않아야 합니다.
- 미래 값을 채우는 `bfill`이나 미래 정보가 섞이는 보간 처리를 주의해야 합니다.
- Stack 및 Item별로 Rolling 계산이 분리되어야 합니다.
- 평균, 표준편차, P99 등 전체 데이터에서 계산하는 통계값은 학습 구간만으로 산출해야 합니다.

따라서 과거 72시간의 데이터를 사용한다는 이유만으로 검증 시작 전 72시간을 무조건 제외할 필요는 없습니다.

단, Feature 생성 방식과 데이터 전처리 과정에서 미래 정보가 포함되지 않았는지는 별도로 검증해야 합니다.

## 6. 모델별 성능 평가 방법

교차검증을 수행할 때는 모델의 유형에 맞는 평가 지표를 사용해야 합니다.

현재 프로젝트는 Classification 모델 1개와 Regression 모델 2개로 구성되어 있습니다.

### 6.1 S1-C: SO₂ 위험 진입 여부 예측

S1-C는 향후 60분 이내에 SO₂ 농도가 위험 기준에 진입하는지를 예측하는 분류 모델입니다.

주요 평가 지표는 다음과 같습니다.

| 지표 | 의미 | 평가 목적 |
|---|---|---|
| AP | Average Precision | 위험 이벤트를 얼마나 잘 찾아내는지 평가 |
| Precision | 정밀도 | 위험하다고 판단한 결과 중 실제 위험 비율 |
| Recall | 재현율 | 실제 위험 이벤트 중 찾아낸 비율 |
| F2-score | F2 점수 | Precision보다 Recall을 상대적으로 중요하게 평가 |

TMS 사전 경고 시스템에서는 위험 이벤트를 놓치는 것이 중요하므로 Recall을 상대적으로 중요하게 평가하는 F2-score를 함께 확인합니다.

다만 F2-score는 분류 임계값에 따라 달라집니다.

예를 들어 모델의 위험 점수가 0.5 이상이면 위험으로 판단하도록 설정할 수 있지만, 임계값을 0.3으로 낮추면 일반적으로 더 많은 위험 이벤트를 찾아내는 대신 오탐이 늘어날 수 있습니다.

여기서 주의할 점이 있습니다.

**각 Fold의 검증 데이터에서 가장 좋은 F2-score가 나오는 임계값을 찾고, 같은 검증 데이터의 F2-score를 최종 성능으로 보고하면 안 됩니다.**

검증 데이터에 맞춰 임계값을 최적화한 결과이므로 성능이 실제보다 좋게 측정될 수 있기 때문입니다.

따라서 다음과 같이 구분합니다.

- AP: Fold별 검증 데이터에서 계산합니다.
- F2-score: 해당 Fold의 검증 데이터와 독립적으로 결정된 임계값을 사용해 계산합니다.
- Fold별 최적 임계값: 성능 지표가 아닌 임계값 안정성 분석 자료로 활용할 수 있습니다.
- 최종 운영 임계값: 별도 Validation 데이터를 활용해 결정합니다.

현재 사용 중인 S1-C의 점수 임계값 0.0424는 모델의 출력 점수에 적용하는 의사결정 기준으로 관리해야 합니다. 별도 보정 과정이 확인되지 않았다면 이를 보정된 확률이라고 표현하지 않는 것이 적절합니다.

### 6.2 N1-R / S1-R: 미래 농도 예측

N1-R과 S1-R은 향후 60분의 실제 농도를 예측하는 회귀 모델입니다.

| 모델 | 예측 대상 | 주요 평가 지표 |
|---|---|---|
| N1-R | 60분 후 NOx 농도 | MAE, RMSE |
| S1-R | 60분 후 SO₂ 농도 | MAE, RMSE |

- MAE: 예측값과 실제값의 평균적인 절대 오차
- RMSE: 큰 예측 오차에 더 큰 페널티를 주는 지표

회귀 모델은 XGBoost의 성능만 확인해서는 부족합니다.

현재 시점의 측정값을 그대로 미래 예측값으로 사용하는 Persistence Baseline과 비교해야 합니다.

Persistence 예측 방식은 다음과 같습니다.

```python
# Persistence Baseline
predicted_value_t_plus_60 = current_value_t
```

즉, 현재 농도가 60분 후에도 유지된다고 가정하는 단순한 예측 방식입니다.

비교 시에는 XGBoost와 Persistence가 반드시 동일한 Stack, Item, timestamp 및 유효한 정답 데이터 행을 사용해야 합니다.

추가로 다음 지표를 활용할 수 있습니다.

```text
Skill Score = 1 - (XGBoost MAE / Persistence MAE)
```

| 결과 | 의미 |
|---|---|
| Skill Score > 0 | XGBoost가 Persistence보다 우수 |
| Skill Score = 0 | 두 모델의 MAE가 동일 |
| Skill Score < 0 | Persistence가 XGBoost보다 우수 |

이렇게 비교하면 복잡한 머신러닝 모델을 사용하는 것이 단순한 현재값 유지 방식보다 실제로 얼마나 효과적인지 확인할 수 있습니다.

## 7. 교차검증 결과 정리 방법

교차검증은 단순히 Fold별 점수를 계산하는 것으로 끝나지 않습니다.

각 Fold의 성능을 비교하여 모델이 특정 기간에만 잘 동작하는지, 전체적으로 안정적인 성능을 보이는지 확인해야 합니다.

### 7.1 Fold별 평가 결과

예를 들어 다음과 같은 형태로 결과를 정리할 수 있습니다.

| 모델 | Fold | AP / MAE | Precision | Recall | F2 / RMSE |
|---|---:|---:|---:|---:|---:|
| S1-C | 1 | 측정값 | 측정값 | 측정값 | 측정값 |
| S1-C | 2 | 측정값 | 측정값 | 측정값 | 측정값 |
| S1-C | 3 | 측정값 | 측정값 | 측정값 | 측정값 |
| S1-C | 4 | 측정값 | 측정값 | 측정값 | 측정값 |
| N1-R | 1~4 | MAE / RMSE | - | - | - |
| S1-R | 1~4 | MAE / RMSE | - | - | - |

실제 결과 보고서에는 모델별로 Fold를 구분하여 작성하는 것이 좋습니다.

### 7.2 평균뿐 아니라 편차도 확인

Fold별 평가 결과는 평균만 보고 판단하면 안 됩니다.

예를 들어 다음 두 모델이 있다고 가정하겠습니다.

| 모델 | Fold 1 | Fold 2 | Fold 3 | Fold 4 | 평균 |
|---|---:|---:|---:|---:|---:|
| A 모델 | 0.85 | 0.84 | 0.83 | 0.84 | 0.84 |
| B 모델 | 0.95 | 0.80 | 0.70 | 0.91 | 0.84 |

두 모델의 평균 성능은 동일하지만, B 모델은 Fold별 성능 차이가 큽니다.

A 모델은 특정 기간에 치우치지 않고 비교적 안정적인 성능을 보이는 반면, B 모델은 기간에 따라 성능이 크게 달라집니다.

따라서 다음 항목을 함께 확인해야 합니다.

- 평균(Mean)
- 표준편차(Standard Deviation)
- 최솟값(Min)
- 최댓값(Max)
- Fold별 데이터 건수
- S1-C의 Fold별 양성 건수 및 양성 비율

특히 S1-C는 위험 이벤트의 발생 빈도가 Fold마다 다를 수 있으므로 양성 데이터 건수와 비율을 함께 확인해야 합니다.

또한 Fold별 AP의 평균과 모든 Fold의 예측 결과를 합쳐 계산한 전체 AP는 서로 다른 값이 될 수 있습니다. 보고서에는 어떤 방식으로 계산했는지 명시해야 합니다.

## 8. 추가 검토: Stack 단위 Group 교차검증

현재 대만 CEMS 데이터는 여러 Stack에서 측정된 데이터를 포함하고 있습니다.

일반적인 시간 기준 교차검증은 기존에 관측된 Stack의 과거 데이터를 학습하고, 같은 Stack의 미래 데이터를 예측하는 성능을 평가합니다.

하지만 실제 운영에서는 학습에 사용하지 않은 새로운 Stack에 모델을 적용해야 하는 상황도 발생할 수 있습니다.

이러한 상황을 확인하기 위해 Stack 단위 Group 교차검증을 추가로 검토할 수 있습니다.

### 8.1 시간 기준 교차검증과 Group 교차검증 비교

| 구분 | 시간 기준 교차검증 | Stack Group 교차검증 |
|---|---|---|
| 분리 기준 | 시간 | Stack 또는 사업장 |
| 학습 데이터 | 과거 기간 | 일부 Stack |
| 검증 데이터 | 이후 기간 | 학습에 포함되지 않은 Stack |
| 확인 목적 | 미래 기간 예측 성능 | 새로운 Stack에 대한 일반화 성능 |

Group 교차검증은 기존에 학습하지 않은 Stack에 대한 성능을 확인하는 보완 평가입니다.

다만 시간 기준 교차검증과 Group 교차검증의 성능 차이를 단순히 모델의 Stack 암기 정도로 해석해서는 안 됩니다.

Stack별 데이터 분포, 측정 기간, 양성 비율 및 운전 조건 차이도 성능에 영향을 줄 수 있기 때문입니다.

또한 여러 Stack이 동일한 사업장에 속한다면 Stack 단위가 아닌 사업장 단위로 그룹을 구성하는 것이 더 적절할 수 있습니다.

Group 교차검증은 시간 기준 교차검증을 대체하는 것이 아니라 별도의 일반화 평가로 활용하는 것을 권장합니다.

## 9. 교차검증과 Bootstrap의 차이

교차검증과 Bootstrap은 모두 평가 결과의 신뢰성을 확인하는 데 사용할 수 있지만 목적이 다릅니다.

| 구분 | 교차검증(Cross-Validation) | Bootstrap |
|---|---|---|
| 주요 목적 | 여러 데이터 구간에서 모델 성능 확인 | 평가 결과의 불확실성 추정 |
| 데이터 처리 | 학습 및 검증 구간을 나누어 반복 | 복원 추출로 표본을 반복 구성 |
| 확인 사항 | 기간별 성능 안정성 | 성능 추정치의 신뢰구간 |
| TMS 활용 | 시계열 구간별 모델 성능 비교 | MAE, AP 등의 신뢰구간 추정 |

TMS 데이터는 시간적으로 인접한 데이터끼리 상관관계가 있을 수 있으므로 행 단위로 무작위 Bootstrap을 수행하면 실제 불확실성이 제대로 반영되지 않을 수 있습니다.

Bootstrap을 추가 적용한다면 시간 블록을 고려한 Block Bootstrap 등을 검토하는 것이 적절합니다.

또한 Stack 단위 Bootstrap만으로는 동일 Stack 내부의 시간적 상관관계까지 자동으로 해결되지 않으므로 표본 추출 단위를 신중하게 설계해야 합니다.

현재 단계에서는 교차검증을 우선 적용하고, Bootstrap은 필요할 때 추가 평가 방법으로 검토하는 것을 권장합니다.

## 10. 최종 적용 절차

이번 교차검증 적용은 다음 순서로 진행합니다.

| 순서 | 수행 내용 | 주요 확인 사항 |
|---:|---|---|
| 1 | 기존 데이터 분할 확인 | Train, Validation, Test 기간 확인 |
| 2 | Train 데이터 기반 Fold 구성 | 4-Fold Expanding Window |
| 3 | 데이터 전처리 및 Feature 생성 | 미래 정보 누수 여부 확인 |
| 4 | Fold별 모델 학습 | S1-C, N1-R, S1-R 동일 기준 적용 |
| 5 | Fold별 성능 평가 | AP, Precision, Recall, F2, MAE, RMSE |
| 6 | Fold별 성능 비교 | 평균, 표준편차, 최솟값, 최댓값 |
| 7 | 최종 모델 설정 | 기존 Validation 활용 |
| 8 | 최종 성능 평가 | 기존 Test 데이터 활용 |
| 9 | 국내 데이터 외부 평가 | 국내 TMS 데이터 활용 |

### 10.1 데이터 사용 시 반드시 지켜야 할 원칙

1. 교차검증은 기존 Train 데이터 24개월 안에서 수행합니다.
2. 기존 Validation은 Fold 검증에 포함하지 않습니다.
3. Test 데이터는 최종 모델의 성능을 평가할 때만 사용합니다.
4. 국내 TMS 데이터는 외부 일반화 성능 평가에만 사용합니다.
5. 각 Fold의 학습 및 검증 과정에서 미래 데이터가 포함되지 않도록 합니다.
6. 최종 운영 임계값은 별도 Validation 데이터를 활용해 결정합니다.
7. 최종 Test 결과를 확인한 후 해당 결과에 맞춰 모델을 다시 튜닝하지 않습니다.

## 11. 최종 정리

이번 교차검증의 핵심은 모델의 성능을 한 번 측정하는 것이 아니라, **서로 다른 과거·미래 기간을 기준으로 반복 평가하여 모델의 성능이 얼마나 안정적인지 확인하는 것**입니다.

현재 TMS 프로젝트에서는 다음과 같이 진행하는 것을 권장합니다.

| 구분 | 적용 방안 |
|---|---|
| 교차검증 방식 | Expanding Window Time Series Cross-Validation |
| Fold 수 | 4-Fold |
| Fold 검증 기간 | 각 3개월 |
| Fold 학습 데이터 | 12개월 → 15개월 → 18개월 → 21개월 |
| 최종 모델 설정 | 기존 Validation 6개월 |
| 최종 성능 평가 | 기존 Test 6개월 |
| 외부 평가 | 국내 TMS 데이터 |
| 추가 평가 | Stack 단위 Group 교차검증 검토 |

**멘티들이 반드시 이해해야 할 핵심은 다음 세 가지입니다.**

- 첫째, TMS는 시계열 데이터이므로 무작위로 데이터를 나누지 않고 과거 데이터로 미래 데이터를 검증해야 합니다.
- 둘째, 교차검증은 모델의 기간별 성능 안정성을 확인하기 위한 것이며, 기존 Validation과 Test의 역할을 대신하지 않습니다.
- 셋째, 평균 성능이 높더라도 Fold별 편차가 크다면 특정 기간에만 잘 동작하는 모델일 수 있으므로 성능의 일관성까지 확인해야 합니다.

결국 모델의 성능을 판단할 때는 단순히 하나의 평가 점수가 높은지를 보는 것이 아니라, **서로 다른 기간에서도 일관된 성능을 유지하는지, 실제 운영 환경에서도 활용할 수 있는 수준인지를 함께 확인해야 합니다.**

위 Fold 구성은 현재 공유된 데이터 기간을 기준으로 한 권장안입니다. 실제 적용 전 다음 사항을 확인해야 합니다.

- S1-C의 양성 데이터 건수와 양성 비율

- S1-C 임계값 결정 과정과 Fold별 F2-score 계산 방식
- N1-R 및 S1-R과 Persistence Baseline의 평가 대상 행 일치 여부

이 항목들을 확인한 후 Fold별 데이터 건수와 평가 지표를 확정하는 것이 좋습니다.
