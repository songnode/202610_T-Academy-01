# TMS 프로젝트: AWS MLflow 활용 및 MLOps 이해

## 1. MLOps란 무엇인가?

MLOps는 Machine Learning Operations의 약자로, 머신러닝 모델을 개발하고 운영하는 전체 과정을 체계적으로 관리하는 방법론이다.

일반적인 소프트웨어 개발에서는 코드를 개발하고 테스트한 후 서버에 배포한다.

머신러닝 시스템에서는 코드뿐 아니라 학습 데이터, Feature, 모델 파일, 모델 성능까지 관리해야 한다.

예를 들어 TMS 프로젝트에서 NOx 예측 모델을 개발했다고 가정해 보자.

처음에는 XGBoost 모델의 성능이 좋았지만, 시간이 지나면서 측정 데이터의 분포가 바뀌어 예측 성능이 떨어질 수 있다.

이때 단순히 새로운 모델을 학습하는 것만으로는 충분하지 않다.

- 어떤 데이터로 학습했는가?
- 어떤 파라미터를 사용했는가?
- 기존 모델보다 성능이 좋아졌는가?
- 새로운 모델을 운영에 적용해도 되는가?
- 문제가 발생하면 이전 모델로 복구할 수 있는가?
- 운영 중 모델의 성능이 떨어지고 있지는 않은가?

이러한 과정을 지속적으로 관리하는 것이 MLOps다.

### MLOps를 쉽게 이해하기

| 구분 | 설명 |
|---|---|
| DevOps | 소프트웨어 개발과 운영을 자동화하고 관리 |
| MLOps | 머신러닝 모델의 개발, 학습, 배포, 운영을 자동화하고 관리 |

**핵심:** MLOps는 모델을 한 번 학습시키는 것이 아니라, 모델이 실제 운영 환경에서도 안정적으로 동작하도록 지속적으로 관리하는 체계다.

## 2. MLOps 전체 생명주기(Model Lifecycle)

MLOps는 일반적으로 다음과 같은 흐름으로 구성된다.

```text
[Data Collection]
       |
       v
[Data Processing]
       |
       v
[Feature Engineering]
       |
       v
[Model Training]
       |
       v
[Model Evaluation]
       |
       v
[Model Registry]
       |
       v
[Model Deployment]
       |
       v
[Model Serving]
       |
       v
[Model Monitoring]
       |
       v
[Retraining]
       |
       +--------> 다시 Model Training
```

각 단계의 역할은 다음과 같다.

| 단계 | 역할 | TMS 적용 예시 |
|---|---|---|
| Data Collection | 데이터 수집 | NOx, SO2 측정 데이터 |
| Data Processing | 데이터 정제 | 결측치 및 이상값 처리 |
| Feature Engineering | 모델 입력 데이터 생성 | 과거 측정값, 이동평균, Lag Feature |
| Model Training | 모델 학습 | XGBoost, Random Forest, LSTM |
| Model Evaluation | 모델 성능 평가 | Recall, F1-score, MAE, RMSE |
| Model Registry | 모델 버전 관리 | NOx XGBoost v1.0 |
| Model Deployment | 운영 환경에 모델 배포 | ECS 또는 SageMaker |
| Model Serving | 실제 데이터 추론 | 다음 30분 NOx 예측 |
| Model Monitoring | 모델 운영 상태 확인 | 예측 오차 및 Data Drift |
| Retraining | 모델 재학습 | 새로운 데이터로 모델 개선 |

여기서 Model Deployment와 Model Serving은 구분해서 이해해야 한다.

- Model Deployment: 모델을 운영 환경에 설치하고 사용할 수 있도록 배포하는 과정
- Model Serving: 배포된 모델에 데이터를 전달하고 실제 예측 결과를 반환하는 과정

## 3. MLflow란 무엇인가?

MLflow는 머신러닝 실험과 모델의 생명주기를 관리하기 위한 오픈소스 플랫폼이다.

MLOps를 구현할 때 활용할 수 있는 대표적인 도구 중 하나다.

TMS 프로젝트에서는 여러 모델을 학습하고 성능을 비교한 다음, 운영에 사용할 모델을 버전별로 관리하는 데 사용할 수 있다.

### 3.1 MLflow의 주요 기능

| 기능 | 설명 | TMS 적용 예시 |
|---|---|---|
| Tracking | 학습 실험 기록 | XGBoost와 LSTM 비교 |
| Parameters | 학습 파라미터 기록 | learning_rate, max_depth |
| Metrics | 모델 평가 지표 기록 | Recall, F1-score, MAE |
| Artifacts | 학습 결과물 저장 | 모델 파일, 평가 그래프 |
| Model Registry | 모델 버전 및 상태 관리 | xgboost_v1.0, xgboost_v1.1 |
| Model Packaging | 모델과 실행 환경 정보 관리 | 모델 로딩 및 추론 환경 |

### 3.2 MLflow를 사용하는 이유

다음과 같은 상황을 생각해 보자.

TMS NOx 예측 모델을 세 가지 방식으로 학습했다.

| 모델 | Recall | F1-score |
|---|---:|---:|
| Random Forest | 0.78 | 0.80 |
| XGBoost | 0.86 | 0.85 |
| LSTM | 0.89 | 0.87 |

이때 단순히 LSTM의 성능이 가장 높다고 해서 바로 운영에 적용하는 것은 바람직하지 않다.

실제 운영에서는 다음 사항도 확인해야 한다.

- 학습 데이터와 평가 데이터가 적절하게 분리되었는가?
- 데이터 누수(Data Leakage)는 없는가?
- 모델 추론 속도는 적절한가?
- 특정 굴뚝이나 측정 항목에서 성능이 떨어지지는 않는가?
- 운영 환경에서 동일한 전처리를 수행할 수 있는가?

MLflow는 모델별 실험 설정과 평가 결과를 기록하여 이러한 비교와 추적을 쉽게 해준다.

## 4. MLflow의 핵심 기능 이해하기

### 4.1 Experiment Tracking

Experiment Tracking은 모델 학습 실험의 기록을 관리하는 기능이다.

예를 들어 XGBoost의 학습 파라미터를 변경하면서 여러 번 실험할 수 있다.

```text
Experiment: TMS_NOX_PREDICTION

  Run 1
    Model: XGBoost
    max_depth: 5
    learning_rate: 0.05
    Recall: 0.82

  Run 2
    Model: XGBoost
    max_depth: 7
    learning_rate: 0.03
    Recall: 0.86

  Run 3
    Model: XGBoost
    max_depth: 9
    learning_rate: 0.01
    Recall: 0.84
```

이렇게 실험 결과를 기록하면 어떤 설정이 좋은 성능을 냈는지 비교할 수 있다.

### 4.2 Parameters와 Metrics

두 개념은 반드시 구분해야 한다.

**Parameters**

모델을 학습할 때 설정하는 값이다.

예시:

```python
params = {
    "max_depth": 7,
    "learning_rate": 0.03,
    "n_estimators": 300
}
```

**Metrics**

학습이 완료된 모델의 성능을 평가한 결과다.

예시:

```python
metrics = {
    "recall": 0.86,
    "f1_score": 0.85,
    "precision": 0.84
}
```

정리하면 다음과 같다.

- Parameters: 모델을 어떤 설정으로 학습했는가?
- Metrics: 학습한 모델이 얼마나 잘 예측하는가?

### 4.3 Artifacts

Artifacts는 학습 과정에서 생성된 파일을 저장하는 기능이다.

TMS 프로젝트에서는 다음과 같은 파일을 관리할 수 있다.

```text
artifacts/
  |
  +-- model.pkl
  |
  +-- scaler.pkl
  |
  +-- feature_config.json
  |
  +-- confusion_matrix.png
  |
  +-- feature_importance.png
  |
  +-- evaluation_report.json
```

단, Scaler는 모든 모델에 필요한 것은 아니다. 모델 학습에 사용한 전처리 과정에 따라 저장해야 한다.

### 4.4 Model Registry

Model Registry는 학습된 모델을 버전별로 등록하고 관리하는 기능이다.

예를 들어 다음과 같이 관리할 수 있다.

```text
TMS_NOX_MODEL
  |
  +-- Version 1
  |     XGBoost
  |     Recall: 0.82
  |
  +-- Version 2
  |     XGBoost
  |     Recall: 0.86
  |
  +-- Version 3
        LSTM
        Recall: 0.89
```

Model Registry를 사용하면 어떤 모델이 운영에 사용되고 있는지 추적할 수 있다.

중요한 점은 모델 버전이 높다고 무조건 좋은 모델은 아니라는 것이다.

운영 모델은 성능, 안정성, 추론 속도, 데이터 적합성 등을 검토하여 선정해야 한다.

## 5. AWS에서 MLflow를 활용하는 방법

MLflow는 오픈소스이므로 AWS 환경에서도 사용할 수 있다.

AWS에서 MLflow를 활용하는 방법은 크게 두 가지로 이해하면 쉽다.

1. AWS의 관리형 ML 서비스인 SageMaker와 연동
2. EC2 또는 ECS 등의 AWS 인프라에 MLflow를 직접 구축

### 5.1 Amazon SageMaker + MLflow

Amazon SageMaker는 AWS에서 제공하는 머신러닝 관리형 서비스다.

MLflow와 연동하면 실험 추적과 모델 관리를 MLflow로 수행하고, 실제 모델 배포와 추론은 SageMaker를 활용할 수 있다.

```text
[Model Training]
       |
       v
     [MLflow]
       |
       +-------------------+
       |                   |
       v                   v
[Experiment Tracking] [Model Registry]
                           |
                           v
                    [SageMaker]
                           |
                           v
                  [SageMaker Endpoint]
                           |
                           v
                      [Prediction]
```

각 기술의 역할은 다음과 같다.

| 기술 | 역할 |
|---|---|
| MLflow Tracking | 모델 학습 실험 기록 |
| MLflow Model Registry | 모델 버전 관리 |
| Amazon S3 | 모델 파일 및 아티팩트 저장 |
| SageMaker | 모델 배포 및 추론 인프라 |
| SageMaker Endpoint | API 기반 실시간 추론 |

예를 들어 MLflow에 등록된 XGBoost 모델을 SageMaker에 배포하면, 외부 시스템이 SageMaker Endpoint를 호출하여 예측 결과를 받을 수 있다.

**장점**

- AWS 관리형 ML 인프라를 활용할 수 있다.
- 모델 배포와 추론을 관리하기 편리하다.
- 모델 확장과 운영 자동화에 유리하다.
- MLflow와 연동하여 실험 및 모델 버전을 관리할 수 있다.

**단점**

- AWS 서비스 구조를 이해해야 한다.
- 사용한 인프라와 추론 방식에 따라 비용이 발생한다.
- 초기 PoC에는 다소 복잡할 수 있다.

### 5.2 EC2 또는 ECS에 MLflow 직접 구축

SageMaker를 사용하지 않고 AWS 인프라에 MLflow를 직접 구축하는 방법도 있다.

예를 들어 EC2에 MLflow Tracking Server를 설치하고, Amazon S3를 Artifact 저장소로 사용할 수 있다.

```text
             [ML Training]
                   |
                   v
          [MLflow Tracking]
                   |
          +--------+--------+
          |                 |
          v                 v
   [Experiment DB]     [Amazon S3]
   PostgreSQL/RDS      Model Artifacts
          |
          v
    [Model Registry]
```

여기서 주의할 점이 있다.

MLflow Tracking Server는 실험 기록과 모델 관리 기능을 제공하는 서버이지, 그 자체가 AWS의 완전한 모델 운영 인프라는 아니다.

실제 모델 추론을 위해서는 별도의 서빙 환경이 필요하다.

예를 들어 다음과 같이 구성할 수 있다.

```text
[MLflow Tracking Server]
          |
          v
    [Model Registry]
          |
          v
      [Amazon S3]
          |
          v
   [ECS + FastAPI]
          |
          v
    [Prediction API]
```

**장점**

- AWS 인프라를 자유롭게 구성할 수 있다.
- 기존 Python 코드를 활용하기 쉽다.
- SageMaker를 사용하지 않고도 모델 관리와 서빙을 구성할 수 있다.

**단점**

- MLflow 서버 운영과 장애 대응을 직접 해야 한다.
- 인증, 권한, 백업, 데이터베이스 관리가 필요하다.
- 모델 배포 및 확장 기능을 별도로 설계해야 한다.

## 6. MLflow와 SageMaker, ECS의 역할 차이

멘티들이 가장 혼동하기 쉬운 부분이다.

MLflow와 SageMaker, ECS는 같은 역할을 하는 기술이 아니다.

| 기술 | 주요 역할 | 비유 |
|---|---|---|
| MLflow | 실험 및 모델 관리 | 모델 관리 담당자 |
| Amazon S3 | 모델 파일 저장 | 파일 보관소 |
| SageMaker | 관리형 ML 배포 및 추론 | ML 전용 운영 환경 |
| ECS | 컨테이너 실행 및 관리 | 애플리케이션 실행 환경 |
| FastAPI | 추론 API 개발 | 외부 요청을 받는 창구 |
| Airflow | 작업 스케줄링 및 흐름 관리 | 작업 관리자 |

예를 들어 MLflow에 등록된 모델을 ECS에서 실행할 수 있다.

또는 SageMaker에 배포할 수도 있다.

즉, MLflow가 모델을 관리하고 SageMaker나 ECS가 모델을 실행하는 구조다.

### MLflow를 사용하면 바로 서빙이 가능한가?

MLflow는 모델을 불러오고 실행할 수 있는 기능을 제공한다.

예를 들어 MLflow Models의 `mlflow models serve` 명령을 이용하면 모델을 REST API 형태로 실행할 수 있다.

하지만 실제 운영 환경에서는 다음 항목도 고려해야 한다.

- 서버 실행 환경
- 네트워크 및 인증
- 요청량과 동시성
- 서버 확장
- 장애 복구
- 모델 버전 교체
- 모니터링

따라서 실제 AWS 운영에서는 MLflow의 모델 서빙 기능을 단독으로 사용하는 것보다 ECS, SageMaker 등의 인프라와 조합하는 것이 일반적인 설계 선택지다.

## 7. AWS 기반 MLOps 아키텍처

이제 MLflow와 AWS 서비스를 연결하여 전체 구조를 살펴보자.

### 7.1 전체 아키텍처

```text
                  [TMS Data]
                      |
                      v
                 [Amazon S3]
                      |
                      v
               [Data Processing]
                Airflow / Spark
                      |
                      v
                [Feature Data]
                      |
                      v
                [Model Training]
                 Python / ML
                      |
                      v
                [Model Evaluation]
                      |
                      v
                    [MLflow]
                      |
             +--------+--------+
             |                 |
             v                 v
       [Tracking]       [Model Registry]
                               |
                               v
                         [Amazon S3]
                         Model Artifacts
                               |
                               v
                       [Model Deployment]
                               |
                 +-------------+-------------+
                 |                           |
                 v                           v
           [SageMaker]                 [ECS + FastAPI]
                 |                           |
                 +-------------+-------------+
                               |
                               v
                         [Model Serving]
                               |
                               v
                         [Prediction]
                               |
                               v
                        [Rule Engine]
                               |
                               v
                         [Final Decision]
                               |
                               v
                       [Monitoring]
                       Grafana / Logs
                               |
                               v
                         [Retraining]
```

이 구조에서는 MLflow가 모델의 학습 실험과 버전을 관리하고, AWS가 데이터 저장과 모델 실행 환경을 제공한다.

### 7.2 AWS 서비스별 역할

| AWS 서비스 | MLOps에서의 역할 |
|---|---|
| Amazon S3 | 원본 데이터, Feature, 모델 아티팩트 저장 |
| AWS Glue Data Catalog | 데이터 테이블 및 스키마 메타데이터 관리 |
| Amazon Athena | S3 데이터 조회 및 분석 |
| AWS Glue | 데이터 카탈로그 및 ETL 기능 |
| Amazon RDS | MLflow Tracking Backend 저장소로 활용 가능 |
| Amazon ECS | Docker 기반 모델 서빙 |
| Amazon EKS | Kubernetes 기반 모델 운영 |
| Amazon SageMaker | 관리형 모델 학습, 배포 및 추론 |
| Amazon CloudWatch | 로그 및 인프라 모니터링 |
| Amazon EventBridge | 이벤트 기반 작업 실행 및 스케줄링 |

모든 서비스를 한꺼번에 도입할 필요는 없다. 프로젝트의 요구사항에 맞는 서비스부터 선택해야 한다.

## 8. MLflow와 AWS를 이용한 TMS 모델 서빙 예시

TMS 프로젝트에서 XGBoost NOx 예측 모델을 운영한다고 가정해 보자.

### 8.1 모델 학습 및 MLflow 기록

```python
import mlflow
import mlflow.xgboost

from xgboost import XGBClassifier
from sklearn.metrics import recall_score, f1_score

mlflow.set_experiment("TMS_NOX_PREDICTION")

with mlflow.start_run():

    params = {
        "max_depth": 7,
        "learning_rate": 0.03,
        "n_estimators": 300
    }

    model = XGBClassifier(**params)

    model.fit(X_train, y_train)

    predictions = model.predict(X_test)

    recall = recall_score(y_test, predictions)
    f1 = f1_score(y_test, predictions)

    mlflow.log_params(params)
    mlflow.log_metric("recall", recall)
    mlflow.log_metric("f1_score", f1)

    mlflow.xgboost.log_model(
        model,
        name="model"
    )
```

위 코드는 학습 실험과 평가 결과를 MLflow에 기록하는 기본적인 예시다.

실제 프로젝트에서는 학습 데이터 버전, Feature 명세, 전처리 설정, 평가 기준도 함께 기록하는 것이 좋다.

### 8.2 모델 Registry 등록

학습 결과를 확인한 후 운영 후보 모델을 Registry에 등록한다.

MLflow 버전에 따라 등록 방식과 API가 다를 수 있으므로, 프로젝트에서 사용하는 MLflow 버전을 기준으로 구현해야 한다.

일반적인 등록 흐름은 다음과 같다.

```text
[MLflow Training Run]
          |
          v
[Model Evaluation]
          |
          v
[Register Model]
          |
          v
[Model Registry]
          |
          v
[Approved Model]
```

### 8.3 등록된 모델 불러오기

모델이 등록되면 추론 프로그램에서 해당 모델을 불러올 수 있다.

```python
import mlflow.pyfunc

model_uri = "models:/TMS_NOX_MODEL/3"

model = mlflow.pyfunc.load_model(model_uri)

predictions = model.predict(X_inference)
```

위 예시의 `3`은 Model Registry에 등록된 모델 버전이다.

실제 운영에서는 임의의 버전을 사용하지 않고, 승인된 모델 버전을 명시적으로 지정하거나 배포 설정에 따라 관리해야 한다.

### 8.4 추론 결과 저장

```python
result = {
    "stack_code": "STACK_001",
    "item_code": "nox",
    "predicted_value_30m": 92.5,
    "model_version": "3"
}
```

이후 Python Rule Engine이 예측 결과를 받아 최종 경고를 판정한다.

## 9. MLOps 자동화와 CI/CD

MLOps에서는 모델 학습과 배포 과정을 자동화하는 것도 중요하다.

여기서 CI/CD 개념을 이해해야 한다.

- CI(Continuous Integration): 코드 변경 사항을 지속적으로 통합하고 테스트하는 과정
- CD(Continuous Delivery/Deployment): 검증된 변경 사항을 배포하는 과정

MLOps에서는 일반적인 코드뿐 아니라 모델과 데이터의 검증도 고려한다.

### 9.1 일반적인 CI/CD

```text
[Developer]
     |
     v
[Git Push]
     |
     v
[Build]
     |
     v
[Test]
     |
     v
[Deploy]
```

### 9.2 MLOps 파이프라인

```text
[New Data]
    |
    v
[Data Validation]
    |
    v
[Model Training]
    |
    v
[Model Evaluation]
    |
    v
[MLflow Registry]
    |
    v
[Approval]
    |
    v
[Model Deployment]
    |
    v
[Model Monitoring]
```

코드 변경과 모델 변경은 서로 다른 검증이 필요하다.

예를 들어 Python 코드의 단위 테스트가 통과했다고 해서 모델의 Recall까지 개선되었다고 볼 수는 없다.

따라서 MLOps에서는 다음을 별도로 검증하는 것이 좋다.

- 코드 테스트
- 데이터 품질 검사
- Feature 검증
- 모델 성능 평가
- 추론 테스트
- 배포 후 운영 상태 확인

## 10. MLOps에서 자동 재학습은 어떻게 동작할까?

운영 중 모델의 성능이 떨어지면 새로운 데이터를 이용해 모델을 다시 학습할 수 있다.

이를 Model Retraining이라고 한다.

예를 들어 TMS에서 다음과 같은 상황이 발생했다고 가정하자.

- 기존 NOx 모델의 Recall이 감소했다.
- 최근 측정 데이터의 분포가 바뀌었다.
- 실제 측정값과 예측값 사이의 오차가 커졌다.

이때 재학습 파이프라인을 실행할 수 있다.

```text
[Production Monitoring]
          |
          v
[Performance Degradation]
          |
          v
[Retraining Trigger]
          |
          v
[New Data Collection]
          |
          v
[Model Training]
          |
          v
[Model Evaluation]
          |
          v
[MLflow Registry]
          |
          v
[Human Approval]
          |
          v
[New Model Deployment]
```

중요한 것은 성능 저하가 감지되었다고 무조건 자동으로 운영 모델을 교체하는 것은 아니라는 점이다.

새로운 모델의 성능과 안정성을 검증한 뒤 승인 절차를 거쳐 배포하는 것이 안전하다.

### 자동 재학습과 자동 배포의 차이

| 구분 | 설명 |
|---|---|
| 자동 재학습 | 새로운 데이터로 모델을 다시 학습 |
| 자동 평가 | 신규 모델의 성능을 검증 |
| 자동 등록 | 평가 조건을 통과한 모델을 Registry에 등록 |
| 자동 배포 | 승인 정책에 따라 운영 환경에 배포 |
| Rollback | 문제가 생기면 이전 모델로 복구 |

재학습, 모델 등록, 운영 배포는 서로 분리해서 설계해야 한다.

## 11. TMS 프로젝트에서 추천하는 MLOps 구축 단계

처음부터 완전한 MLOps 플랫폼을 구축할 필요는 없다.

교육 프로젝트에서는 다음과 같이 단계적으로 진행하는 것이 좋다.

### 1단계: MLflow 실험 관리

목표: 여러 모델의 성능을 비교하고 기록한다.

구현 항목:

- MLflow Tracking Server 구성
- Experiment 생성
- 학습 파라미터 기록
- Recall, F1-score, MAE, RMSE 기록
- 모델 파일 및 평가 결과 저장

### 2단계: Model Registry

목표: 운영 후보 모델을 버전별로 관리한다.

구현 항목:

- 모델 등록
- 모델 버전 관리
- 평가 결과 연결
- 운영 승인 모델 지정
- 이전 버전 확인

### 3단계: AWS 기반 모델 서빙

목표: 등록된 모델을 AWS에서 실행한다.

초기 추천 구조:

```text
[MLflow]
    |
    v
[Amazon S3]
    |
    v
[Airflow]
    |
    v
[Python Batch Inference]
    |
    v
[Rule Engine]
    |
    v
[Prediction Storage]
```

이후 필요하면 다음 방식으로 확장한다.

```text
[MLflow Model Registry]
          |
          v
     [Amazon S3]
          |
          v
   [Docker Container]
          |
          v
     [Amazon ECS]
          |
          v
       [FastAPI]
          |
          v
    [Prediction API]
```

또는 SageMaker를 활용한 관리형 서빙으로 확장할 수 있다.

### 4단계: Model Monitoring

목표: 운영 중 모델의 성능과 데이터 상태를 확인한다.

구현 항목:

- 추론 시간
- 예측 오류율
- Data Drift
- Model Drift
- 실제값 대비 예측 오차
- 모델 버전별 성능 비교

### 5단계: 재학습 및 배포 자동화

목표: 모델 성능이 저하되면 재학습부터 검증까지 자동화한다.

구현 항목:

- Airflow 기반 재학습 파이프라인
- MLflow 실험 기록
- 신규 모델 평가
- 승인 및 배포
- 이전 모델 Rollback

## 14. 최종 정리

MLOps는 단순히 모델을 학습시키고 서버에 올리는 기술이 아니다.

데이터 수집부터 모델 학습, 성능 검증, 버전 관리, 배포, 모니터링, 재학습까지 전체 과정을 지속적으로 관리하는 체계다.

TMS 프로젝트에서는 다음 역할을 구분해서 이해하면 된다.

- **MLflow:** 어떤 모델을 학습했고, 성능이 어떠하며, 어떤 버전을 운영할지 관리한다.
- **Amazon S3:** 학습 데이터와 모델 파일을 저장한다.
- **Airflow:** 데이터 처리, 추론, 재학습 작업의 실행 순서를 관리한다.
- **SageMaker 또는 ECS:** 모델을 실제 AWS 환경에서 실행한다.
- **FastAPI:** 외부 시스템에서 모델을 호출할 수 있도록 API를 제공한다.
- **Python Rule Engine:** 모델의 예측 결과를 운영 규칙과 결합하여 최종 판정한다.
- **Grafana 및 CloudWatch:** 모델과 인프라의 운영 상태를 모니터링한다.

**가장 중요한 것은 모델 학습, 모델 관리, 모델 서빙, 최종 운영 판정을 분리해서 설계하는 것이다.**

모델을 한 번 학습하는 것으로 프로젝트가 끝나는 것이 아니라, 실제 운영 데이터에서 성능을 확인하고 필요한 경우 재학습과 검증을 거쳐 더 나은 모델로 개선하는 것이 MLOps의 핵심이다.
