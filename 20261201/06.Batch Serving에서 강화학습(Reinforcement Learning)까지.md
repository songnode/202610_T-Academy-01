# TMS 프로젝트: Batch Serving에서 강화학습(Reinforcement Learning)까지

## 1. 전체 학습 목표

TMS 프로젝트에서는 NOx(질소산화물), SO2(황산화물) 측정 데이터를 이용하여 미래의 농도와 기준 초과 가능성을 예측하는 AI 모델을 개발한다.

초기에는 머신러닝과 딥러닝 모델을 학습하고, 실제 운영 데이터에 적용하는 Batch Serving을 구현한다.

이후 Batch Serving으로 축적한 예측 결과와 실제 측정 결과, 설비 운영 이력 등을 활용하여 강화학습(Reinforcement Learning)으로 확장할 수 있다.

최종적으로는 단순히 미래의 상태를 예측하는 시스템을 넘어, 운영 상황에 적합한 대응 정책을 평가하고 추천하는 시스템으로 발전시키는 것이 목표다.

### 전체 발전 방향

```text
1단계: 예측 모델 개발
        |
        v
2단계: Batch Serving
        |
        v
3단계: 운영 데이터 축적
        |
        v
4단계: 강화학습 데이터 구성
        |
        v
5단계: Offline Reinforcement Learning
        |
        v
6단계: 정책 평가 및 시뮬레이션
        |
        v
7단계: 운영자 승인 기반 정책 적용
```

**핵심 개념**

- 머신러닝: 데이터를 학습하여 미래 값을 예측한다.
- Batch Serving: 학습된 모델로 일정 주기마다 예측을 수행한다.
- 강화학습: 상태와 행동, 보상을 바탕으로 더 나은 행동 정책을 학습한다.

---

## 2. 1단계: TMS 예측 모델 개발

먼저 TMS 측정 데이터를 이용하여 예측 모델을 학습한다.

### 2.1 학습 데이터

TMS 프로젝트에서는 다음과 같은 데이터를 활용할 수 있다.

| 데이터 | 설명 |
|---|---|
| NOx | 질소산화물 측정값 |
| SO2 | 황산화물 측정값 |
| Temperature | 온도 |
| Flow Rate | 배출가스 유량 |
| Pressure | 압력 |
| Historical Values | 과거 측정값 |
| Lag Features | 이전 시점의 측정값 |
| Rolling Statistics | 이동평균, 이동표준편차 등 |

실제 데이터셋에서 제공되는 항목과 프로젝트에서 생성하는 Feature를 구분하여 관리해야 한다.

### 2.2 모델 학습

다음과 같은 모델을 비교할 수 있다.

| 모델 | 특징 |
|---|---|
| Persistence | 직전 측정값을 미래값으로 예측하는 기준 모델 |
| Random Forest | 여러 결정 트리를 결합한 머신러닝 모델 |
| XGBoost | 부스팅 기반 머신러닝 모델 |
| LSTM | 시계열의 순차적인 패턴을 학습하는 딥러닝 모델 |

예를 들어 다음과 같은 예측을 수행한다.

```text
입력 데이터
  |
  +-- 현재 NOx: 85.2
  +-- 과거 NOx 측정값
  +-- 온도
  +-- 유량
  |
  v
[XGBoost Model]
  |
  v
30분 후 NOx 예측
  |
  v
92.5
```

여기서 모델은 미래의 NOx 농도를 예측할 뿐, 설비를 어떻게 조작해야 하는지는 결정하지 않는다.

### 2.3 모델 평가

학습한 모델은 적절한 평가 지표로 비교한다.

| 평가 지표 | 의미 |
|---|---|
| MAE | 실제값과 예측값의 평균 절대 오차 |
| RMSE | 오차를 제곱하여 계산한 평균 제곱근 오차 |
| Precision | 경고 예측 중 실제로 기준 초과에 해당하는 비율 |
| Recall | 실제 기준 초과 사례 중 모델이 찾아낸 비율 |
| F1-score | Precision과 Recall의 조화평균 |

회귀 모델과 분류 모델은 평가 목적이 다르므로 적절한 지표를 구분해서 사용해야 한다.

## 3. 2단계: Batch Serving 구현

Batch Serving은 일정한 시간 간격으로 데이터를 모아서 학습된 모델에 입력하고 예측 결과를 생성하는 방식이다.

현재 TMS 프로젝트에서는 30분 단위 데이터 처리를 기준으로 Batch Serving을 먼저 구현하는 것이 적합하다.

### 3.1 Batch Serving 구조

```text
[TMS 측정 데이터 수집]
          |
          v
      [Amazon S3]
          |
          v
    [Bronze / Silver]
          |
          v
       [Gold Layer]
          |
          v
       [Airflow]
      30분 주기 실행
          |
          v
   [Python Inference]
          |
          v
      [MLflow Model]
          |
          v
      [Prediction]
          |
          v
   [Python Rule Engine]
          |
          v
      [Final Decision]
          |
          v
  [Gold / PostgreSQL]
```

### 3.2 Batch Serving 처리 과정

1. TMS 측정 데이터를 수집한다.
2. Amazon S3에 원본 데이터를 저장한다.
3. Silver Layer에서 데이터 정제 및 표준화를 수행한다.
4. Gold Layer에서 모델 입력 Feature를 생성한다.
5. Airflow가 정해진 시간에 추론 작업을 실행한다.
6. MLflow에서 승인된 모델 버전을 확인한다.
7. Python Inference가 모델을 실행한다.
8. 모델이 미래 NOx 또는 SO2 농도를 예측한다.
9. Python Rule Engine이 최종 경고 여부를 판단한다.
10. 예측 결과와 판정 이력을 저장한다.

### 3.3 예측 결과 예시

```json
{
  "prediction_id": "PRED_20261128_001",
  "stack_code": "STACK_001",
  "item_code": "nox",
  "prediction_time": "2026-11-28T10:00:00",
  "predicted_value_30m": 92.5,
  "exceedance_probability": 0.87,
  "model_name": "TMS_NOX_MODEL",
  "model_version": "3"
}
```

이 결과는 모델이 예측한 정보다.

최종 경고 여부는 Python Rule Engine이 운영 기준과 데이터 품질 등을 검토한 후 결정한다.

### 3.4 Batch Serving에서 중요한 점

Batch Serving은 단순히 예측값을 만드는 작업으로 끝나면 안 된다.

강화학습까지 고려한다면 다음 데이터를 함께 저장하는 것이 중요하다.

- 예측 시점의 입력 데이터
- 모델 예측값
- 모델 버전
- 최종 판정 결과
- 실제 측정값
- 실제 측정값이 확정된 시점
- 설비 운영 이력(확보 가능한 경우)

이 데이터가 이후 강화학습을 위한 기초 자료가 된다.

## 4. 3단계: Batch Serving 결과를 축적한다

강화학습으로 연결하기 위해서는 Batch Serving 결과를 지속적으로 저장해야 한다.

특히 예측값과 실제 측정값을 연결하는 작업이 중요하다.

### 4.1 예측값과 실제값 비교

예를 들어 10:00 시점에 모델이 30분 후 NOx 농도를 예측했다고 가정하자.

| 시간 | 데이터 | 값 |
|---|---|---:|
| 10:00 | 현재 NOx | 85.2 |
| 10:00 | 30분 후 예측 NOx | 92.5 |
| 10:30 | 실제 NOx | 94.1 |

이 경우 예측 오차는 다음과 같다.

\[
Prediction\ Error = 94.1 - 92.5 = 1.6
\]

예측값과 실제값을 비교하면 모델의 예측 성능을 확인할 수 있다.

30분 후뿐 아니라 60분 후 예측도 동일한 방식으로 검증할 수 있다.

### 4.2 운영 이력도 함께 저장해야 한다

강화학습을 위해서는 측정 데이터만으로 충분하지 않을 수 있다.

실제 운영자가 어떤 조치를 취했는지에 대한 이력이 중요하다.

예를 들어 다음과 같은 데이터다.

| 시간 | NOx | 운영 조치 | 조치 결과 |
|---|---:|---|---|
| 10:00 | 85.2 | 조치 없음 | - |
| 10:30 | 94.1 | 연소 조건 조정 | 농도 변화 |
| 11:00 | 88.3 | 조치 유지 | 농도 감소 |
| 11:30 | 79.5 | 조치 완료 | 안정화 |

위 표는 이해를 위한 가상 사례다.

실제 설비 운영 이력이 없다면 행동(Action)을 임의로 만들어 실제 운영에서 수행된 것처럼 학습해서는 안 된다.

**중요:** 강화학습은 측정값만으로 학습하는 것이 아니라, 어떤 상태에서 어떤 행동을 했고 그 결과가 어떻게 바뀌었는지에 대한 정보가 필요하다.

## 5. 4단계: 강화학습(Reinforcement Learning)이란?

강화학습은 에이전트(Agent)가 환경(Environment)과 상호작용하면서 보상(Reward)을 최대화하는 행동 정책(Policy)을 학습하는 방법이다.

쉽게 설명하면 다음과 같다.

> 현재 상황을 파악하고, 어떤 행동을 했을 때 더 좋은 결과가 나오는지 학습하는 방법이다.

일반적인 머신러닝은 미래의 값을 예측하는 데 초점을 둔다.

반면 강화학습은 현재 상태에서 어떤 행동을 선택해야 장기적으로 더 좋은 결과를 얻을 수 있는지 학습한다.

### 5.1 머신러닝과 강화학습의 차이

| 구분 | 일반적인 머신러닝 | 강화학습 |
|---|---|---|
| 목적 | 미래 값 또는 클래스를 예측 | 좋은 행동 정책 학습 |
| 입력 | Feature | State |
| 출력 | 예측값 또는 확률 | Action |
| 학습 기준 | 정답과 예측 오차 | Reward |
| 학습 방식 | 정답 데이터 기반 학습 등 | 환경과의 상호작용 또는 과거 경험 |
| TMS 예시 | 30분 후 NOx 농도 예측 | 운영 상황에 따른 조치 정책 추천 |

예를 들어 다음과 같이 생각할 수 있다.

**일반 머신러닝**

```text
현재 NOx = 85.2
       |
       v
[예측 모델]
       |
       v
30분 후 NOx = 92.5
```

**강화학습**

```text
현재 NOx = 85.2
       |
       v
[강화학습 Agent]
       |
       v
추천 행동 = 운영 조건 조정
       |
       v
[환경 또는 시뮬레이터]
       |
       v
다음 상태 확인
       |
       v
[Reward 계산]
       |
       v
정책 개선
```

여기서 추천 행동은 개념적인 예시이며, 실제 TMS에서 가능한 조작 항목과 허용 범위는 설비 운영 기준에 따라 정의해야 한다.

## 6. 강화학습의 핵심 구성 요소

강화학습을 이해하려면 다섯 가지 개념을 알아야 한다.

### 6.1 Agent

Agent는 행동을 선택하는 주체다.

TMS에서는 강화학습 알고리즘으로 학습된 정책이 Agent의 행동을 결정하는 역할을 할 수 있다.

### 6.2 Environment

Environment는 Agent가 행동을 수행했을 때 상태가 변화하는 환경이다.

TMS에서는 실제 설비 또는 설비 동작을 모사한 시뮬레이터가 Environment가 될 수 있다.

### 6.3 State

State는 현재 환경의 상태를 나타내는 정보다.

TMS 예시:

```json
{
  "nox": 85.2,
  "so2": 30.4,
  "temperature": 120.5,
  "flow_rate": 35.4,
  "recent_nox_average": 82.1
}
```

실제 State에는 설비 운영 상태, 제어 변수, 제한 조건 등도 포함할 수 있다.

### 6.4 Action

Action은 Agent가 선택하는 행동이다.

TMS에서 가능한 행동은 실제 설비의 제어 가능 범위와 운영 절차를 확인한 후 정의해야 한다.

개념적인 예시는 다음과 같다.

```text
Action 1: 현재 운전 조건 유지
Action 2: 운영 조건 조정 요청
Action 3: 추가 점검 요청
Action 4: 운영자 확인 요청
```

실제 설비의 연료 공급량, 공기 공급량 등의 조작 변수를 사용할 수도 있지만, 해당 조작이 가능한 설비인지와 안전 범위를 먼저 확인해야 한다.

### 6.5 Reward

Reward는 행동의 결과가 얼마나 좋았는지를 수치로 표현한 것이다.

TMS에서는 다음과 같은 요소를 고려할 수 있다.

| 평가 요소 | 보상 설계 방향 |
|---|---|
| NOx 감소 | 긍정적인 보상 |
| SO2 감소 | 긍정적인 보상 |
| 기준 초과 | 큰 패널티 |
| 설비 안정성 | 긍정적인 보상 |
| 에너지 사용량 | 효율성에 따른 보상 |
| 불필요한 조작 | 패널티 |
| 안전 제한 위반 | 매우 큰 패널티 또는 행동 불허 |

단, 단순히 배출 농도를 낮추는 것만 보상하면 안 된다.

설비 안정성, 안전 제한, 에너지 효율 등도 함께 고려해야 한다.

### 강화학습의 기본 구조

```text
           [Agent]
              |
              | Action
              v
        [Environment]
              |
              | New State
              | Reward
              v
           [Agent]
              |
              v
        [Policy Update]
              |
              v
          반복 학습
```

## 7. 5단계: Batch Serving과 강화학습은 어떻게 연결되는가?

여기가 이번 강의에서 가장 중요한 부분이다.

Batch Serving이 강화학습을 직접 수행하는 것은 아니다.

Batch Serving은 정해진 시간마다 예측을 수행하고 결과를 축적한다.

이렇게 축적된 데이터는 강화학습을 위한 과거 경험 데이터로 활용할 수 있다.

### 7.1 연결 구조

```text
[실제 TMS 데이터]
        |
        v
   [Batch Serving]
        |
        v
 [모델 예측 결과]
        |
        v
 [실제 측정값과 비교]
        |
        v
 [운영 이력 축적]
        |
        v
[State / Action / Reward 구성]
        |
        v
[Offline Reinforcement Learning]
        |
        v
   [Policy Evaluation]
        |
        v
    [Simulation]
        |
        v
  [운영자 승인]
        |
        v
  [정책 적용 또는 추천]
```

### 7.2 각 단계의 역할

| 단계 | 설명 |
|---|---|
| Batch Serving | 일정 주기로 모델 예측 |
| Prediction Storage | 예측 결과 저장 |
| Actual Data Matching | 예측 시점과 실제 측정값 연결 |
| Operation History | 실제 운영 조치 이력 저장 |
| RL Dataset | State, Action, Reward 데이터 구성 |
| Offline RL | 과거 경험 데이터로 정책 학습 |
| Policy Evaluation | 정책의 예상 성능 평가 |
| Simulation | 가상 환경에서 정책 검증 |
| Approval | 운영자 검토 및 승인 |

### 7.3 중요한 데이터 구분

강화학습을 위해서는 다음 세 가지를 구분해야 한다.

**① State**

행동을 선택하기 직전의 환경 상태다.

예를 들어 10:00 시점의 NOx, SO2, 온도, 유량 등이 해당한다.

**② Action**

그 상태에서 실제로 수행된 행동이다.

예를 들어 운영자가 설비 운전 조건을 조정했다면 그 조치 내용이 Action이다.

**③ Reward**

행동 이후 환경이 어떻게 변했는지를 기준으로 계산한 보상이다.

예를 들어 조치 이후 NOx가 감소하고 설비 안정성이 유지되었다면 긍정적인 보상을 줄 수 있다.

이 세 가지가 연결되어야 강화학습에 활용할 수 있는 데이터가 된다.

---

## 8. 6단계: Offline Reinforcement Learning

TMS 프로젝트에서는 처음부터 실제 설비를 대상으로 강화학습을 수행하는 것은 위험할 수 있다.

따라서 먼저 Offline Reinforcement Learning을 검토하는 것이 좋다.

Offline RL은 과거에 수집한 데이터를 이용해 정책을 학습하는 방식이다.

실제 환경에서 Agent가 직접 행동을 수행하면서 시행착오를 겪는 대신, 기존에 축적된 경험 데이터를 활용한다.

### 8.1 Offline RL의 기본 구조

```text
[Historical Data]
       |
       v
[State / Action / Reward]
       |
       v
[Offline RL Algorithm]
       |
       v
[Policy Model]
       |
       v
[Policy Evaluation]
       |
       v
[Simulation]
```

### 8.2 Offline RL에 필요한 데이터

일반적으로 다음과 같은 구조의 데이터를 준비한다.

| 필드 | 의미 | TMS 예시 |
|---|---|---|
| state | 행동 전 상태 | NOx 85.2, SO2 30.4 |
| action | 실제 수행한 행동 | 운전 조건 조정 |
| reward | 행동 결과의 보상 | 배출 농도 감소 및 안정성 유지 |
| next_state | 행동 후 상태 | NOx 78.5, SO2 29.8 |
| done | 에피소드 종료 여부 | 운영 시나리오 종료 |

예시:

```json
{
  "timestamp": "2026-11-28T10:00:00",
  "state": {
    "nox": 85.2,
    "so2": 30.4,
    "temperature": 120.5
  },
  "action": "adjust_operation",
  "reward": 0.8,
  "next_state": {
    "nox": 78.5,
    "so2": 29.8,
    "temperature": 121.2
  },
  "done": false
}
```

위 데이터는 이해를 위한 예시다. 실제 Action과 Reward는 설비 운영 이력과 검증된 평가 기준을 기반으로 구성해야 한다.

### 8.3 Offline RL 알고리즘

Offline RL을 구현할 때 검토할 수 있는 알고리즘은 다음과 같다.

| 알고리즘 | 특징 |
|---|---|
| CQL (Conservative Q-Learning) | 과거 데이터에 없는 행동의 가치를 과도하게 높게 평가하지 않도록 보수적으로 학습 |
| IQL (Implicit Q-Learning) | 과거 데이터 분포를 활용하여 오프라인 정책 학습 |
| BC (Behavioral Cloning) | 과거 운영자의 행동을 모방하는 학습 방식 |
| TD3+BC | TD3와 행동 모방을 결합한 Offline RL 접근법 |

처음부터 복잡한 알고리즘을 적용하기보다는 Behavioral Cloning으로 기존 운영 패턴을 학습해 보고, 이후 CQL이나 IQL을 비교하는 접근을 고려할 수 있다.

단, Behavioral Cloning은 엄밀히 말해 강화학습 알고리즘 자체라기보다는 과거 행동을 모방하는 지도학습 기반 접근법이다. Offline RL과 비교하기 위한 기준선으로 활용할 수 있다.

---

## 9. 7단계: Reward 설계

강화학습에서 가장 중요한 부분 중 하나는 Reward 설계다.

모델의 성능은 알고리즘만으로 결정되지 않는다.

어떤 행동을 좋은 행동이라고 평가할 것인지 명확하게 정의해야 한다.

### 9.1 TMS Reward 설계 예시

TMS에서는 다음 요소를 고려할 수 있다.

```text
Total Reward
    |
    +-- NOx 개선 정도
    |
    +-- SO2 개선 정도
    |
    +-- 기준 초과 여부
    |
    +-- 설비 안정성
    |
    +-- 에너지 효율
    |
    +-- 불필요한 조작 여부
```

개념적인 수식은 다음과 같이 표현할 수 있다.

\[
R_t =
w_1 R_{NOx}
+ w_2 R_{SO2}
+ w_3 R_{Stability}
+ w_4 R_{Energy}
- w_5 P_{Violation}
\]

여기서 각 항목은 보상 또는 패널티를 의미하며, \(w\)는 각 항목의 중요도를 조절하는 가중치다.

실제 구현에서는 항목별 단위와 범위가 다르므로 정규화가 필요하다.

### 9.2 Reward 설계 시 주의사항

- NOx만 낮추고 SO2가 증가하는 행동을 좋은 행동으로 평가하면 안 된다.
- 에너지 효율만 높이고 설비 안전성이 떨어지는 행동을 허용하면 안 된다.
- 단기적인 배출 농도 감소뿐 아니라 장기적인 설비 안정성을 고려해야 한다.
- 안전 제한 위반은 단순한 작은 패널티로 처리하지 않고 행동 자체를 제한하는 방법도 고려해야 한다.

Reward 설계는 실제 설비 운영 전문가와 협의하여 정의해야 한다.

## 10. 8단계: 시뮬레이션 환경 구성

Offline RL로 정책을 학습했다고 해서 바로 실제 설비에 적용해서는 안 된다.

학습된 정책이 실제 운영 환경에서도 적절하게 동작하는지 검증해야 한다.

이를 위해 시뮬레이션 환경을 구성할 수 있다.

### 10.1 시뮬레이션이 필요한 이유

실제 설비에서 강화학습 Agent가 다양한 행동을 시도하도록 하면 안전성과 운영 안정성에 문제가 발생할 수 있다.

시뮬레이션 환경에서는 실제 설비에 영향을 주지 않고 여러 정책을 시험할 수 있다.

```text
[현재 상태]
     |
     v
[RL Agent]
     |
     v
[행동 선택]
     |
     v
[시뮬레이션 환경]
     |
     v
[다음 상태 예측]
     |
     v
[Reward 계산]
     |
     v
[정책 성능 평가]
```

### 10.2 시뮬레이션 환경 구성 방법

| 방법 | 설명 |
|---|---|
| Historical Replay | 과거 데이터를 시간 순서대로 재생 |
| Rule-based Simulation | 정의된 규칙에 따라 상태 변화 계산 |
| Predictive Model | ML 모델을 활용해 행동 이후 상태 변화를 추정 |
| Digital Twin | 실제 설비의 동작을 가상 환경으로 모델링 |

초기에는 Historical Replay와 간단한 Rule-based Simulation부터 검토하는 것이 현실적이다.

단, Historical Replay는 과거에 실제로 발생한 상황을 재생하는 것이므로, 과거에 수행하지 않았던 새로운 행동의 결과를 알려주지는 못한다.

Predictive Model을 이용한 시뮬레이션도 모델의 예측 오차와 불확실성을 함께 고려해야 한다.

### 10.3 TMS에서의 시뮬레이션 흐름

```text
[Historical TMS Data]
         |
         v
 [Predictive Model]
         |
         v
 [RL Agent Action]
         |
         v
 [Simulation Environment]
         |
         v
 [Next State Prediction]
         |
         v
 [Reward Calculation]
         |
         v
 [Policy Evaluation]
```

여기서 예측 모델은 강화학습 Agent가 선택한 행동에 따라 다음 상태가 어떻게 바뀔지를 추정하는 데 활용할 수 있다.

하지만 단순한 상관관계 기반 예측 모델이 행동의 인과적인 효과까지 정확하게 예측한다고 볼 수는 없다.

따라서 시뮬레이션 결과는 실제 운영에 적용하기 전에 별도의 검증이 필요하다.

## 11. 9단계: 강화학습 정책을 실제 운영에 적용하는 방법

최종적으로 강화학습을 이용해 학습한 정책을 운영에 적용하는 방법은 여러 가지가 있다.

초기에는 실제 설비를 직접 제어하기보다는 운영자에게 행동을 추천하는 방식이 적합하다.

### 11.1 단계별 적용

```text
[Offline RL Training]
          |
          v
   [Policy Evaluation]
          |
          v
      [Simulation]
          |
          v
     [Policy Approval]
          |
          v
    [Recommendation]
          |
          v
     [Human Review]
          |
          v
    [Operator Decision]
```

### 11.2 운영 적용 수준

| 단계 | 적용 방식 | 설명 |
|---|---|---|
| Level 1 | 분석 | 과거 데이터로 정책 분석 |
| Level 2 | 시뮬레이션 | 가상 환경에서 정책 평가 |
| Level 3 | 추천 | 운영자에게 적절한 행동 추천 |
| Level 4 | 승인 기반 실행 | 운영자가 승인한 행동만 실행 |
| Level 5 | 자동 제어 | 안전성이 충분히 검증된 범위에서 자동 실행 |

TMS 프로젝트에서는 Level 2~3까지를 우선적인 목표로 삼는 것을 추천한다.

실제 설비 자동 제어는 별도의 안전성 검증, 제어 시스템 연계, 권한 관리, 운영자 승인 체계가 갖춰져야 한다.

## 12. MLOps와 강화학습은 어떻게 연결되는가?

MLOps는 강화학습 모델에도 적용할 수 있다.

일반적인 머신러닝 모델과 마찬가지로 강화학습 모델도 학습, 평가, 등록, 배포, 모니터링 과정이 필요하다.

다만 강화학습에서는 일반적인 예측 모델의 평가 지표 외에도 정책의 보상, 안전성, 행동 분포 등을 함께 평가해야 한다.

### 12.1 전체 구조

```text
              [TMS Data]
                  |
                  v
            [Batch Serving]
                  |
                  v
           [Operational Data]
                  |
                  v
        [State / Action / Reward]
                  |
                  v
          [Offline RL Training]
                  |
                  v
             [Policy Model]
                  |
                  v
           [Policy Evaluation]
                  |
                  v
             [Simulation]
                  |
                  v
            [MLflow Registry]
                  |
                  v
           [Policy Deployment]
                  |
                  v
           [Recommendation]
                  |
                  v
            [Human Approval]
                  |
                  v
             [Monitoring]
```

### 12.2 MLflow로 강화학습도 관리할 수 있을까?

가능하다.

MLflow는 강화학습 전용 플랫폼은 아니지만, 강화학습 실험 결과와 모델 아티팩트를 기록하는 데 활용할 수 있다.

예를 들어 다음과 같은 항목을 기록할 수 있다.

| 관리 항목 | 예시 |
|---|---|
| Algorithm | CQL, IQL |
| Parameters | learning_rate, batch_size |
| Reward | 평균 보상 |
| Episode Return | 에피소드별 누적 보상 |
| Constraint Violation | 제약 조건 위반 횟수 |
| Policy Artifact | 학습된 정책 파일 |
| Evaluation Result | 정책 평가 결과 |
| Dataset Version | 학습에 사용한 데이터 버전 |

강화학습에서는 모델 파일뿐 아니라 학습에 사용한 데이터셋, 환경 설정, Reward 정의, Action 공간도 함께 관리해야 한다.

## 14. 프로젝트 구현 권장 순서

강화학습을 처음부터 구현하기보다는 다음 순서로 진행하는 것이 좋다.

| 단계 | 구현 내용 | 목표 |
|---|---|---|
| 1단계 | XGBoost / LSTM 학습 | 미래 NOx, SO2 예측 |
| 2단계 | MLflow 도입 | 모델 실험 및 버전 관리 |
| 3단계 | Batch Serving | 30분 주기 추론 |
| 4단계 | 예측값과 실제값 연결 | 예측 성능 검증 |
| 5단계 | 운영 이력 확보 | State / Action / Reward 데이터 준비 |
| 6단계 | Behavioral Cloning | 기존 운영 행동 모방 기준선 |
| 7단계 | Offline RL | 과거 데이터 기반 정책 학습 |
| 8단계 | Simulation | 신규 정책 검증 |
| 9단계 | 운영자 추천 | 안전한 정책 추천 서비스 |

여기서 가장 중요한 선행 조건은 실제 설비의 운영 행동 이력을 확보하는 것이다.

운영 행동 이력이 없다면 State와 측정값을 이용한 예측 모델은 만들 수 있지만, 실제 행동에 따른 결과를 학습하는 강화학습 데이터는 충분히 만들기 어렵다.

## 15. 멘티 강의 시 강조할 핵심 질문

### Q1. Batch Serving을 구현하면 강화학습을 바로 할 수 있는가?

아니다.

Batch Serving은 예측 결과를 주기적으로 생성하는 방식이다.

강화학습을 하려면 여기에 실제 운영 행동 이력과 행동 이후의 결과가 추가로 필요하다.

### Q2. Batch Serving 결과가 강화학습에 왜 필요한가?

예측 결과와 실제 측정값을 연결하면 현재 상태와 미래 상태의 관계를 분석할 수 있다.

여기에 실제 운영 조치 이력을 추가하면 State, Action, Reward를 구성할 수 있는 기반이 된다.

### Q3. 강화학습은 모델이 스스로 발전한다는 의미인가?

일부는 맞지만 정확히는 보상에 따라 더 나은 행동 정책을 학습하는 것이다.

운영 중인 모델이 자동으로 계속 바뀌는 것은 아니다.

학습된 정책을 평가하고 승인한 후 운영 환경에 배포하는 과정이 필요하다.

### Q4. 강화학습을 위해 반드시 실제 설비를 제어해야 하는가?

아니다.

과거 운영 데이터를 활용한 Offline RL과 시뮬레이션을 통해 정책을 먼저 학습하고 검증할 수 있다.

### Q5. 예측 모델과 강화학습 모델은 같은 모델인가?

아니다.

예측 모델은 미래 상태를 예측하고, 강화학습 정책은 현재 상태에서 어떤 행동을 선택할지 결정한다.

두 모델을 함께 활용할 수 있지만 역할은 다르다.

---

## 16. 최종 정리

TMS 프로젝트는 처음부터 강화학습을 구현하는 것보다 예측 모델과 Batch Serving을 먼저 완성하는 것이 좋다.

그 이유는 강화학습을 수행하기 위한 데이터와 환경을 먼저 준비해야 하기 때문이다.

전체 발전 방향은 다음과 같다.

**1. 예측 단계**

- NOx, SO2 미래 농도 예측
- XGBoost, LSTM 모델 비교
- MLflow로 모델 관리

**2. 운영 단계**

- Airflow 기반 Batch Serving
- 30분 단위 추론
- 예측값과 실제 측정값 비교
- 운영 이력 축적

**3. 강화학습 준비 단계**

- State 정의
- Action 정의
- Reward 설계
- 실제 운영 행동 이력 확보

**4. 강화학습 단계**

- Offline RL 학습
- 정책 평가
- 시뮬레이션 검증
- MLflow로 정책 버전 관리

**5. 운영 확장 단계**

- 운영자에게 최적 행동 추천
- 승인 기반 정책 적용
- 성능 및 안전성 모니터링

### 가장 중요한 핵심 메시지

> Batch Serving은 강화학습의 시작점이 아니라, 강화학습에 필요한 운영 데이터를 축적하는 기반이다.

> 머신러닝은 미래를 예측하고, 강화학습은 더 나은 행동을 학습한다.

> TMS의 최종 목표는 단순한 배출 농도 예측을 넘어, 운영 상황을 분석하고 안전한 대응 방안을 추천할 수 있는 AI 시스템으로 발전시키는 것이다.
