# 3. Task별 큰 흐름

## Task 1. 버그 수정

- **왜:** 발표 시연이 끊기지 않게 하는 것이 이번 주 최우선이다.
- **어떤 방식으로**
  1. 통합 시연에서 끊긴 곳과 점검표 오류를 목록으로 만들고 우선순위를 정한다.
  2. 고칠 때는 판정 흐름을 건드리지 않는다.
  3. 고친 내용은 PR과 리뷰로 남긴다.
- **결과물:** 수정 목록, PR 기록
- **고민할 점:** 이 수정이 "버그 수정"인가, "새 기능"인가?

## Task 2. 미완료 항목 마무리

- **왜:** 못 한 것을 숨기는 것보다 이유와 함께 밝히는 것이 신뢰를 준다.
- **어떤 방식으로:** 최종 점검표의 모든 항목을 "완료" 또는 "미완료 + 이유"로 정리한다.
- **결과물:** 정리된 최종 점검표

## Task 3. 결과 문서 정리

- **왜:** 발표를 듣지 못한 사람도 문서만으로 결과를 확인할 수 있어야 한다.
- **어떤 방식으로:** 그동안 만든 평가 세 축 보고서, Test 결과, 오류 분석, 장애 대응 절차서, Agent 평가를 하나의 검증 문서 묶음으로 정리한다. 숫자는 원래 결과를 그대로 쓴다.
- **결과물:** 검증 문서 묶음

## Task 4. 발표 자료

- **왜:** 7주 동안 한 일을 청중이 따라올 수 있는 이야기로 바꿔야 한다.
- **어떤 방식으로**
  1. 문제 → 구조 → 데이터 → 모델 → 판정·Agent → 평가 → 한계 순서로 뼈대를 만든다.
  2. 장마다 "왜 이렇게 했는가"를 한 줄로 넣는다.
  3. 한계와 다음에 할 일을 숨기지 않는다.
- **결과물:** 발표 자료 최종본
- **고민할 점:** 청중이 발표 후 기억해야 할 한 문장은 무엇인가?

## Task 5. 시연 준비

- **왜:** 시연은 실패할 수 있다. 실패해도 발표는 이어져야 한다.
- **어떤 방식으로:** 시연 시나리오와 데이터를 고정하고, 키·계정·서비스가 살아 있는지 확인하는 점검표를 만들고, 예비 시연 영상을 녹화한다.
- **결과물:** 시연 시나리오, 시연 전 점검표, 예비 영상

## Task 6. 리허설 2회

- **왜:** 실제 시간으로 해 봐야 어디서 길어지고 어디서 막히는지 안다.
- **어떤 방식으로:** 실제 발표 시간으로 두 번 하고, 지적 사항을 기록해 다음 리허설 전에 고친다. 예상 질문과 답도 준비한다.
- **결과물:** 리허설 기록, 예상 질문·답

## Task 7. 저장소 정리

- **왜:** 다른 사람이 받아서 실행할 수 있어야 결과가 재현 가능하다.
- **어떤 방식으로:** README와 실행 방법·설정 예시를 정리하고, 코드·문서·화면 캡처에 비밀값이 없는지 점검한 뒤 최종 태그를 붙인다.
- **결과물:** 정리된 저장소, 비밀값 점검 기록, 최종 태그

## Task 8. 최종 발표

- **어떤 방식으로:** 발표 1시간 전에 시연 점검표로 확인하고, 발표와 질의응답을 한다. 시연이 실패하면 예비 영상으로 넘어간다.
- **결과물:** **최종 발표(12/17)**
