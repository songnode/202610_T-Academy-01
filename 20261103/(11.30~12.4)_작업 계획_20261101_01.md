# 11/30~12/4 주간 작업 계획
## TMS 데이터 파이프라인 및 Hybrid AI 사전 경고 시스템 구축 — Agent 부품과 설계

- **작업 기간:** 2026-11-30(월) ~ 2026-12-04(금)
- **이번 주 목표:** 완성된 Gold와 모델 위에 **Agent 부품**(규칙 계층, 질문 유형 결정, 조회 함수, LLM 경고 설명, RAG 벡터 DB)과 **JEV 불일치 분류**를 만들고, 다음 주에 구현할 **Agent·대시보드·n8n을 설계**한다.
- **기준 문서:** [프로젝트 정본](<(정본)굴뚝 TMS 데이터 파이프라인 및 Hybrid AI 사전 경고 시스템_20261101_01.md>)("정본 3.3"처럼 적은 곳은 프로젝트 정본의 절)
- **작업 방식:** 이 문서는 큰 흐름만 알려 준다. 방법·도구·분담은 팀이 정하고 이유를 멘토링 때 설명한다.

> **이번 주 기능은 Gold와 경고 이력을 읽기만 한다.** 판정·모델·평가 지표를 바꾸지 않는다.
>
> **Test 운영은 12/4까지 이어진다(정본 4.5).** 승인 모델·운영 임계값·특성 정의·Rule Engine·판정 Lambda·Spark 판정 코드를 건드리지 않는다. Agent·RAG·LLM 설명은 판정 흐름 밖에서 만든다. 성능을 문서나 설명에 적을 때는 Validation 결과 또는 Test-1 중간 결과임을 밝힌다.

> ## 이번 주 핵심 목표
>
> 1. 확실한 질문은 규칙으로 먼저 처리하고, 질문 유형은 키워드 규칙으로 고른다.
> 2. RF·XGBoost 예측 차이가 기준값 이상인 행만 JEV로 불일치 유형을 분류한다(정본 7~8장).
> 3. 질문 유형마다 쓸 조회 함수를 만든다.
> 4. LLM 경고 설명은 Gold의 검증된 숫자로만 쓰게 한다.
> 5. 법령·판정 규칙 문서로 벡터 DB를 만든다.
> 6. Agent·대시보드·n8n을 설계하고 멘토와 검토한다.
> 7. (Should) 경고 대응·법령 절차 근거 문서를 모으고, 즉석 추론·What-if 경로를 설계한다.

# 3. Task별 큰 흐름

## Task 1. 규칙 계층·키워드 분류기

- **왜:** 답이 분명한 질문까지 AI에 맡기면 느리고 틀릴 수 있다.
- **어떤 방식으로**
  1. 범위 밖 질문을 막는 규칙과, 사업장·배출구·항목·기간을 알아보는 사전을 만든다.
  2. 키워드로 질문 유형을 고르는 분류기를 만든다. 질문 유형을 고르는 유일한 경로다.
- **결과물:** 규칙 계층, 키워드 분류기, 고정 사례 테스트
- **고민할 점:** 규칙에서 끝낼 질문과 다음 단계로 넘길 질문의 경계는 어디인가?

## Task 2. LLM 경고 설명

- **왜:** 경고를 받은 사람은 "왜"를 알고 싶다. 하지만 LLM이 숫자를 지어내면 안 된다.
- **어떤 방식으로**
  1. Gold에 있는 검증된 값만 LLM에 넘긴다.
  2. 설명 속 숫자를 원래 값과 자동으로 대조한다.
  3. 대조에 실패하면 정해진 템플릿 문장으로 바꾼다.
- **결과물:** 경고 설명 기능, 숫자 대조 모듈
- **고민할 점:** 숫자가 아닌 표현(예: "급격히")은 어떻게 검증할 것인가?

## Task 3. 질문 유형 결정·조회 함수

- **왜:** 질문 유형이 정해지면 미리 만든 조회 함수만 실행하게 해서 엉뚱한 조회를 막는다.
- **어떤 방식으로**
  1. 키워드 분류기가 정해진 질문 유형 중 하나를 고른다. 맞는 유형이 없거나 둘 이상이면 되묻는다.
  2. 질문 유형마다 하나씩 조회 함수를 만들고 입출력을 명세한다.
- **결과물:** 질문 유형 결정 연결, 조회 함수와 명세

## Task 4. 새 상태 문구 PR 절차

- **왜:** 처음 보는 상태 문구를 잘못 분류하면 판정이 틀어진다. 사람이 검토해야 한다.
- **어떤 방식으로:** 담당자가 설정 변경을 PR로 올리고 서로 다른 두 명이 검토한 뒤에만 반영하는 절차를 정하고, 시험 PR을 한 번 낸다. 자동 반영은 하지 않는다.
- **결과물:** 절차 문서, 시험 PR 1건

## Task 5. 평가 질문 세트

- **왜:** 다음 주에 키워드 분류기와 Agent를 평가하려면 정답이 있는 질문 세트가 필요하다.
- **어떤 방식으로:** 유형마다 같은 수의 질문을 만들고 정답 유형을 붙인다. 만든 사람과 검토하는 사람을 나눈다.
- **결과물:** 평가 질문 세트

## Task 6. RAG 문서 수집·정제

- **왜:** 법령·규칙 질문에는 근거 문서를 인용해 답해야 한다.
- **어떤 방식으로**
  1. 판정 규칙 문서 → 안내 문서 → 법령 핵심 조문 순으로 좁게 모은다.
  2. 원문은 Bronze에 보관한다.
  3. 검색 단위로 조각을 나누고, 출처(문서명·조문·시행일)를 붙인다.
- **결과물:** 문서 원본, 조각과 메타데이터

## Task 7. 벡터 DB 구축

- **왜:** 질문과 비슷한 조각을 빠르고 정확하게 찾아야 한다.
- **어떤 방식으로:** 임베딩 모델을 하나 정해 고정하고 색인한 뒤, 정답 조각이 있는 질문으로 검색 품질을 잰다. 점수가 낮으면 "찾지 못함"으로 답할 기준도 정한다.
- **결과물:** 벡터 DB, 검색 평가 결과

## Task 8. AI Agent 설계

- **왜:** 다음 주에 조립하려면 질문이 어떤 단계를 거치는지 먼저 정해야 한다.
- **무엇을:** ① 규칙 → ② 질문 유형(키워드) → ③ Gold의 ML 예측 결과 조회 → 도구(조회 함수·RAG 검색) → LLM 답변, 그리고 브리핑과 평가 방법.
- **어떤 방식으로:** 단계마다 입력·출력·실패 시 처리를 정하고, 도구는 조회 함수와 RAG 검색만 쓰게 한다(SQL을 만들어 실행하지 않음).
- **LLM+RAG 활용 사례도 경로를 정한다(정본 12/7 주 "LLM+RAG 활용 사례"):**
  - (Should) 경고 대응 안내: `response_guide` 유형 → Gold 행 조회 → `response_guide_v1` 검색 → LLM이 확인 항목 정리
  - (Should) 법령 절차 설명: `regulation_qa` 유형에서 조문이 여러 개 검색될 때 → LLM이 절차 순서로 엮음
  - (Could) 혼합 질문: 허용하는 유형 조합(예: `current_status` + `regulation_qa`)을 정하고, 그 밖의 다중 유형은 되묻기 유지
  - (Could) EPA 지식 카드 연결: `alert_reason`·`epa_knowledge` 답변에 `epa_cards_v1` 검색 결과를 `[EPA · 참고]`로 따로 붙임
- **즉석 추론·What-if 경로도 정한다(Task 16):** `model_infer` 유형 → 승인 모델 즉석 추론 → 예측 비교 페이지. 다른 경로와 달리 ③ Gold 조회 대신 모델을 부른다.
- **결과물:** Agent 설계서

## Task 9. 대시보드 설계

- **왜:** 화면을 보는 사람이 첫 화면에서 무엇을 알아야 하는지 먼저 정해야 한다.
- **어떤 방식으로:** 화면마다 목적·보는 사람·데이터·필터·표시 문구를 정하고 배치도를 그린다. 기본 화면은 실측만 보이게 한다.
- **결과물:** 대시보드 설계서, 배치도

## Task 10. n8n 설계

- **왜:** Slack 알림은 최소한으로, 두 가지만 보낸다.
- **무엇을:** ① 기준치 초과 알림 ② 수집·처리 현황 알림(정기 요약 + 장애 즉시).
- **어떤 방식으로:** 각 흐름의 입력(무엇을 읽나), 출력(어느 채널로 무엇을), 중복·실패 처리를 정한다. n8n은 읽고 보내기만 한다.
- **결과물:** n8n 설계서
- **이번에도 하지 않음:** 사전 경고·주의 Slack 송신, 피드백 버튼

## Task 11. (Should) 주변 대기질·기상 적재

- **왜:** 사업장 값과 주변 환경을 함께 보면 이해가 깊어진다(참고용).

## Task 13. JEV 불일치 분류

- **왜:** 두 모델의 예측이 크게 다를 때 운영자가 확인할지 정해 주면, 놓치기 쉬운 위험을 대시보드에서 따로 볼 수 있다(정본 7~8장).
- **어떤 방식으로**
  1. 판정 흐름 밖의 별도 작업으로 만든다. Gold에서 불일치 표시(차이 ≥ 기준값)가 붙은 행을 읽기만 한다.
  2. A안 Python 규칙으로 유형(RISK_LIKELY / MODEL_ERROR_LIKELY / UNDETERMINED)을 먼저 정한다.
  3. JEV 키가 있으면 같은 행을 JEV로도 분류하고(B안), 응답 형식과 허용된 분류값을 검증한다.
  4. 두 결과와 응답 시간·성공 여부를 JEV 이력에 남기고, 운영자 확인 표시를 기록한다.
  5. JEV가 실패하거나 늦으면 A안 결과를 쓴다.
- **결과물:** A안 규칙, JEV Client, JEV 이력 테이블, 고정 사례 테스트
- **지키는 것:** 현재 단계·사전 경고·승인 모델·운영 임계값·불일치 기준값을 바꾸지 않는다. 입력의 최근 오차는 정답이 확정된 예측으로만 계산한다.
- **고민할 점:** JEV와 A안이 다르게 판단한 행을 어떻게 모아 두면 다음 주 평가에 쓰기 쉬운가?

## Task 16. (Should) 즉석 추론·What-if 설계

- **왜:** "측정값이 지금보다 20% 오르면 경고에 들어가나?"는 Gold에 답이 없다. 승인 모델을 직접 불러야 답할 수 있고, 같은 경로로 변화 없이 부르면 판정 흐름과 같은 값이 나오는지 확인할 수 있다(정본 12/7 주 "모델 즉석 추론·What-if").
- **무엇을:** 세 단계를 하나의 기능으로 설계한다.

  | 단계 | 우선순위 | 입력 | 출력 |
  |---|---|---|---|
  | ① 모델 즉석 추론 | Should | 질문(배출구·항목) | 즉석 추론 결과와 같은 기준시각 Gold 값 |
  | ② 입력값 변화 예측 비교 | Could | ① + 슬라이더(측정값 변화율) | 변화 전후 진입 확률·예측 대비율 |
  | ③ 자연어 What-if | Could | "20% 오르면"처럼 변화율이 든 질문 | ②와 같음 |

- **어떤 방식으로**
  1. 질문 유형 `model_infer`와 키워드(예측해, 돌려 봐, 오르면, 내려가면, 몇 % 등)를 정한다. 배출구·항목은 Task 1의 사전을 그대로 쓰고, 배출구가 없으면 되묻는다.
  2. 입력을 만드는 순서를 정한다: Silver에서 해당 배출구 × 항목의 기준시각까지 3시간 창을 판정 흐름과 같은 `ingested_at` 조건으로 읽는다 → 복사본에서 **기준시각 행의 `measure_value`만** 변화율만큼 바꾼다 → 공통 Feature Library로 Feature를 다시 계산한다(판정 흐름과 같은 Feature 정의·버전) → 기준시각 행의 Feature를 승인 모델 3개(분류 모델 `clf-v1`, XGBoost 회귀 모델 `reg-v1`, RF 회귀 모델 `rf-reg-v1`)에 넣는다. B+E가 채택됐다면 `epa_surge_score`도 EPA 점수 모델로 다시 계산한다.
  3. Feature 값을 직접 고치지 않는다. `ratio_pct`만 바꾸면 `ratio_diff_30m`·Rolling 평균이 옛 값으로 남아 있을 수 없는 입력이 된다. 판정 뒤에 늦게 들어온 값도 창에 넣지 않는다. 넣으면 같은 기준시각이라도 Feature가 달라진다.
  4. 해석 규칙을 정한다: "20% 오르면"은 상대 증가(측정값 ×1.2)이고, 기준시각 값 하나만 바꾼다. 허용 범위(예: −30%~+50%) 밖이면 "모델이 학습하지 않은 범위"로 안내하고 추론하지 않는다.
  5. 결과 카드 문구를 정한다: `[가정 시뮬레이션 · 판정 아님]`, 기준시각, 변화율, 변화 전후 값, 모델 버전, "실제 판정은 Gold 값을 따릅니다". 가정값 기준 현재 단계를 보여 줄지도 정한다.
  6. 평가 질의를 10건 이상 만든다. 정상 질의, 되묻기(배출구 없음), 범위 밖, 거절(판정 저장·Slack 송신 요청), 다른 유형으로 보내기(예: "어제 왜 경고 떴어?" → `alert_reason`)를 섞는다.
  7. **0% 검증 사례**를 정한다: 변화율 0%로 다시 계산한 Feature가 `online_features`의 같은 키 행과 같고, 예측이 Gold의 `entry_probability`·`predicted_ratio_pct`·`rf_predicted_ratio_pct`와 같아야 한다.
- **결과물:** 즉석 추론·What-if 설계(입력 순서, 해석 규칙, 허용 범위, 화면 문구), `model_infer` 키워드, 평가 질의, 0% 검증 사례
- **지키는 것:** 결과를 Gold·`ops.warning_history`·Slack에 쓰지 않고 `ops.nl_query_log`에만 남긴다. 승인 모델은 읽기 전용으로 불러오고 판정 흐름의 모델·임계값·Feature 정의를 바꾸지 않는다. 화면은 Streamlit 예측 비교 페이지에만 두고 Kibana에는 넣지 않는다.
- **고민할 점:** 화면에 "가정값 기준 현재 단계"를 보여 주면 운영자가 실제 판정으로 오해하지 않을까?
