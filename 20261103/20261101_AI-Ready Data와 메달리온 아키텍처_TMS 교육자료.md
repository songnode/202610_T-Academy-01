# 1. AI-Ready Data란 무엇인가

## 1.1 "잘 관리된 데이터"와 "AI에 맞는 데이터"는 다르다

굴뚝 TMS에서 어떤 배출구의 기준대비율이 평소 60%대인데 갑자기 95%가 찍혔다고 해 봅시다.

- 일반적인 품질 관리에서는 **이상치**로 보고 지우거나 따로 표시할 수 있습니다.
- 우리 AI는 **"60분 안에 경고 단계(90%)에 들어갈지"** 를 미리 알아내는 것이 목적입니다. 이 값은 지워야 할 값이 아니라 **가장 중요한 학습 재료**일 수 있습니다.

물론 측정기 오류로 생긴 값과 실제 급등은 구분해야 합니다. 핵심은 이것입니다.

> **데이터가 좋은지 나쁜지는 쓰는 목적에 따라 달라집니다.**
> AI-Ready Data는 AI가 하려는 일에 맞게 데이터의 의미·품질·대표성·출처를 확인하고, 그 상태를 계속 지켜 가는 것입니다.

AI-Ready Data는 특정 제품이나 데이터베이스 이름이 아닙니다. Bronze·Silver·Gold 같은 처리 구조 위에 **"AI가 이 데이터를 믿고 써도 되는가"를 확인하는 기준과 습관**을 얹는 것입니다.

## 1.2 기존 데이터 관리에 무엇을 더 보나

| 기존 데이터 관리에서 보는 것 | AI 관점에서 더 보는 것 | 우리 프로젝트의 예 |
|---|---|---|
| 컬럼·타입이 표준에 맞는가 | 모델 입력으로 쓸 수 있는가 | 측정값이 숫자인지, 상태 문구(가동중지·보수중)인지 구분 |
| 필수값이 빠지지 않았는가 | 예측에 필요한 기간·사건 수가 충분한가 | Train 2주에 90% 진입 사건이 몇 건인가 |
| 중복이 없는가 | 데이터 한 건의 단위(Grain)가 목적에 맞는가 | 배출구 × 항목 × 30분 한 행 |
| 잘못된 값이 있는가 | 이상값이 실제 위험 신호인지 측정 오류인지 | 급등과 측정기 오류 구분 |
| 테이블 관계가 맞는가 | 업무 의미와 정답(라벨) 기준이 분명한가 | "60분 안 90% 진입"의 정확한 정의(`label-v1`) |
| 접근 권한이 있는가 | AI의 결과까지 통제하는가 | 모델 예측이 현재 판정을 낮추지 못하게 함 |

## 1.3 예시: 환경공단 응답 그대로는 왜 바로 못 쓰나

환경공단 API는 30분마다 배출구 하나당 한 행을 주고, 그 안에 항목별 측정값과 허용기준이 함께 들어 있습니다(정본 3.1). 응답을 단순하게 펼치면 다음과 같습니다.

| 측정 시각 | 사업장 | 배출구 | 항목 | 측정값 | 허용기준 |
|---|---|---|---|---:|---:|
| 2026-11-10 09:00 | ○○사업장 | 3 | NOx | 42.5 | 100 |
| 2026-11-10 09:00 | ○○사업장 | 3 | SOx | 18.2 | 80 |
| 2026-11-10 09:30 | ○○사업장 | 3 | NOx | 보수중 | 100 |
| 2026-11-10 09:30 | ○○사업장 | 3 | NOx | 45.1 | 100 |

저장만 하면 "수집"입니다. AI가 쓰려면 다음을 확인해야 합니다.

- 09:30 NOx에 "보수중"과 45.1이 **둘 다** 있습니다. 같은 측정이 두 번 온 것인가, 값이 다른 충돌인가?
- "보수중"은 0이 아닙니다. 정상도 아닙니다. **상태 문구**로 따로 표시해야 합니다.
- 측정 시각은 KST인가? 수집 시각(`ingested_at`)과 구분했는가?
- 기준대비율(측정값 ÷ 허용기준 × 100)은 그 시각에 유효한 허용기준으로 계산했는가?
- "60분 뒤"를 맞히려면 10:00·10:30 값을 **시간으로** 찾아 정답과 연결해야 합니다.

이런 확인을 거친 뒤에야 AI가 쓸 수 있는 데이터가 됩니다.

# 2. 세 가지 관점: Align · Qualify · Govern

Gartner는 AI-Ready Data를 세 관점으로 나눕니다.

| 관점 | 핵심 질문 | 한 줄 뜻 |
|---|---|---|
| **Align** | 데이터가 AI가 풀려는 문제에 맞는가? | 목적을 먼저 정하고, 그에 맞는 데이터를 준비한다 |
| **Qualify** | 데이터가 필요한 조건을 **계속** 충족하는가? | 한 번 확인하고 끝내지 않고 계속 검증한다 |
| **Govern** | 데이터와 AI 결과를 안전하고 책임 있게 쓰는가? | 출처·책임·권한·결과 사용을 통제한다 |

> **주의:** "Align = 컬럼 이름과 단위 맞추기"로만 이해하면 좁습니다. 표준화는 Align의 일부(의미 맞추기)이자 Qualify의 대상(검증)입니다. Align의 출발점은 **"무엇을 예측하려는가"** 입니다.

## 2.1 Align — 목적에 맞는 데이터 준비

| 검토 요소 | 질문 | 우리 프로젝트 |
|---|---|---|
| AI 기법 | 어떤 AI를 쓰나 | **분류 모델**(주, 60분 안 90% 진입 확률) + **회귀 모델 2개**(60분 후 기준대비율, XGBoost 주·RF 비교)(정본 5.1) |
| 양(Quantification) | 기간·건수·사건 수가 충분한가 | Train 10/30~11/12, 전국 약 3,340개 배출구, 항목별 진입 사건 수(11/9 주 EDA) |
| 의미와 라벨 | 값의 뜻과 정답 기준이 분명한가 | 기준대비율의 계산식, `label-v1`(t+30 또는 t+60 중 하나라도 ≥ 90%)(정본 4.4) |
| 품질 | 목적에 맞는 품질인가 | 결측·중복·충돌·상태 문구·시간 간격 검증 |
| 신뢰(Trust) | 원천과 처리 과정을 믿을 수 있나 | 수집자 3중화(`b`·`c`·`aws`), 확정 표지, 처리 버전 기록(정본 부록 A) |
| 다양성 | 다양한 상황이 들어 있나 | 실측 + 합성 시나리오(급등·지속 상승·결측·지연 등) + EPA 급등 패턴 |
| 계보(Lineage) | 어디서 와서 어떤 과정을 거쳤나 | Bronze 원본 → Silver → Feature → Gold 판정까지 추적 |

### 데이터 모델링의 기본도 여전히 중요하다

| 요소 | 왜 중요한가 | 우리 프로젝트 |
|---|---|---|
| Entity | 무엇을 표현하나 | 사업장, 배출구, 측정 |
| Attribute | 컬럼의 뜻 | `measured_at`, `measure_value`, `standard_value`, `ratio_pct` |
| Identifier | 정확히 구분하는 값 | 사업장 + `stack_code` + `item_code` + `measured_at` (+ `data_origin`) |
| Relationship | 대상 간 관계 | 사업장 1 : 배출구 N, 배출구 1 : 항목 N |
| **Grain** | 한 행이 무엇인가 | **`data_origin` × 배출구 × 항목 × 30분 측정 시각** |
| Metadata | 코드·단위·규칙 설명 | 필드 사전, 상태 문구 매핑, 항목별 단위(11/2 주 Task 4) |

Grain을 잘못 잡으면 뒤가 모두 틀어집니다. 예를 들어 사업장 단위 1시간 평균으로 묶으면 배출구·항목이 섞이고 30분 정보가 사라집니다. 그래서 우리 Feature는 **Silver의 배출구 × 항목 × 30분 행에서 바로** 만듭니다(정본 3.7).

## 2.2 Qualify — 한 번 준비하고 끝나지 않는다

새 배출구가 생기거나, 상태 문구가 바뀌거나, 수집이 지연되거나, 배출 패턴이 달라질 수 있습니다. 그래서 계속 검증합니다.

| 검토 요소 | 뜻 | 우리 프로젝트 |
|---|---|---|
| 검증(Validation) | 요구 조건을 만족하나 | 스키마·단위·결측·시간 간격·중복·충돌 검사, Silver 변환 점검 테스트(11/2 주 Task 13) |
| 성능·비용 | 제때, 감당할 비용으로 처리되나 | 05·35분 수집 → 15·45분 표준화, Spark trigger 1분, 저장 용량 |
| 버전 관리 | 데이터·규칙의 변경 이력 | `label-v1`, `common-v1`, `epa-surge-v1`, `proxy-v0`, `clf-v1 / reg-v1 / rf-reg-v1`, 규칙 버전, 생성기 버전(`gen-v1`) |
| 회귀 테스트 | 바꾼 뒤에도 기존 기능이 맞나 | Silver·Feature·Label·Rule 고정 사례 테스트를 CI에(11/9 주 Task 15) |
| 관찰(Observability) | 상태를 계속 보나 | 수집 누락률, 격리 건수, 변환 실패, 지연 → n8n 수집·처리 현황 알림(12/7 주) |

## 2.3 Govern — 안전하고 책임 있게

**데이터에 접근할 수 있다는 것과, 그 데이터를 그렇게 써도 된다는 것은 다릅니다.** AI가 만든 결과(예측·설명)도 관리 대상입니다.

| 검토 요소 | 뜻 | 우리 프로젝트 |
|---|---|---|
| 책임(Stewardship) | 누가 관리하나 | 수집·표준화·품질 담당 구분. 새 상태 문구는 PR로 올리고 **두 명이 검토**(11/30 주 Task 4) |
| 기준·규정 | 법과 이용 조건을 지키나 | 90%는 **프로젝트 내부 기준**이며 법적 위반 판단이 아님. 법령 답변은 위반 여부를 판단하지 않음 |
| AI 윤리 | 결과를 사실처럼 말하지 않나 | 예측은 "가능성"으로, 즉석 추론은 "판정 아님"으로 표시 |
| 추론 통제 | 허용된 입력·출력만 쓰나 | 현재 단계는 Rule Engine이 정하고 ML이 낮추지 못함. LLM은 Gold 숫자만 쓰고 자동 대조. Agent는 SQL을 만들지 않음 |
| 편향·공정성 | 특정 배출구·기간에 치우치지 않았나 | 배출구 단위 신뢰 구간, 항목별 사건 수 보고. 합성 행은 Train의 30% 이내 |
| 공유 | 적절한 범위로 공유하나 | 합성 배출구는 `SYN-` 접두어(실제 사업장에 가짜 경고가 나가지 않게), 비밀값은 환경변수만 |

# 3. 메달리온 아키텍처 — 일반적인 설명과 우리 프로젝트의 차이

## 3.1 일반적인 메달리온 아키텍처

데이터를 가공 수준에 따라 세 층으로 나누는 구조입니다.

- **Bronze:** 원천 데이터를 그대로 보존
- **Silver:** 정제·표준화·품질 검증
- **Gold:** 분석·업무에 바로 쓰는 데이터

교과서나 다른 자료에서는 흔히 "Gold = 집계표", "Feature는 Gold 다음에 만든다"고 설명합니다. **우리 프로젝트는 여기서 두 가지가 다릅니다.**

## 3.2 우리 프로젝트에서 달라지는 두 가지

| 일반적인 설명 | 우리 프로젝트 | 이유 |
|---|---|---|
| Gold = 사업장·시간별 **집계표** | Gold = **판정 결과표** `tms_gold.judgement` 하나. 배출구 × 항목 × 기준 시각마다 한 행(정상 행 포함) | 화면·알림·Agent 답변의 숫자를 한 곳에서 가져와야 서로 어긋나지 않습니다. 집계는 **뷰**(`gold.v_daily_summary`)로 만듭니다 |
| Gold → Feature 순서 | Silver → **Feature**(따로 된 층 `tms_feature.*`) → 모델 → **Gold** | Gold 집계로 Feature를 만들면 30분 정보와 배출구·항목 구분이 사라집니다. Feature는 모델의 **입력**, Gold는 모델과 규칙의 **결과**입니다 |

## 3.3 우리 프로젝트의 층 구조

```text
 [원천]  환경공단 API(30분, 주)      합성 이벤트(Kafka)        EPA CAMPD 분기 파일(부)
            │                           │                          │
            ▼                           ▼                          ▼
 Bronze   S3 원본 그대로 보존(수집자·수집 시각·확정 표지)  ── 고치지 않는다
            │
            ▼
 Silver   tms_silver.measurements (국내 실측·합성, data_origin으로 구분)
          epa_silver.*            (EPA는 따로)             ── 표준화·격리·상태 문구 표시
            │
            ├──────────────▶ Label(label-v1 스냅샷) ── 학습·평가 때만, Gold에 넣지 않음
            ▼
 Feature  tms_feature.keco_features(학습) / tms_feature.online_features(운영)
            │
            ▼
 모델     분류 clf-v1 · XGBoost 회귀 reg-v1 · RF 회귀 rf-reg-v1   +   Rule Engine(현재 단계)
            │
            ▼
 Gold     tms_gold.judgement (판정 결과 원본, 한 행에 현재·예측·최종)
          gold.v_judgement_observed(실측 전용 뷰) · gold.v_daily_summary(일간 집계 뷰)
            │
            ├──▶ ops.warning_history (PostgreSQL, 경고 행만 복사한 운영 테이블)
            ├──▶ Elasticsearch → Kibana / Streamlit
            └──▶ (판정 흐름 밖) JEV 불일치 분류 → ops.jev_history
```

| 층 | 무엇이 있나 | AI-Ready와의 연결 |
|---|---|---|
| Bronze | 원본 그대로 | Trust·Lineage: 문제가 생기면 언제든 여기서 다시 만든다 |
| Silver | 표준화·정제된 측정 | Align(의미)·Qualify(품질)의 중심 |
| Feature | 모델 입력값 | Align: 목적(60분 예측)에 맞는 입력 |
| Label | 학습 정답 | Align: 예측 대상과 정답 기준의 명확화 |
| Gold | 판정·예측 결과 | Govern·Qualify: 결과 추적, 평가의 기준점 |

> Silver를 만들었다고 AI-Ready가 끝나지 않습니다. Feature·Label의 정의, 대표성, 계보, 계속되는 검증까지 갖춰야 합니다.

# 4. 층별로 무엇을 만드나

## 4.1 Bronze — 원본과 출처 보존 (11/2 주)

놓친 30분은 다시 받을 수 없습니다. 환경공단 API는 **과거 조회가 안 되기** 때문입니다. 그래서 세 수집자가 같은 시각(매시 05·35분)에 따로 받습니다(정본 부록 A).

| 수집자 | 경로 | 역할 |
|---|---|---|
| `b` | 장비 B Airflow → MinIO → S3 | 주 수집 |
| `c` | 장비 C Airflow → MinIO → S3 | 보조(다른 장비·네트워크) |
| `aws` | EventBridge → 수집 Lambda → S3 | 안전망. 항상 수집 |

Bronze에 남기는 것:

| 항목 | 뜻 |
|---|---|
| 원본 파일·응답 | 받은 그대로(수정·삭제 금지) |
| 수집자(`collector=b·c·aws`) | 누가 받았나. 세 원본이 서로 덮어쓰지 않게 경로에 넣음 |
| 수집 시각 | 언제 받았나 |
| 매니페스트·확정 표지 | 건수·크기·해시와 "온전히 올라갔다"는 표시. Silver는 확정 표지가 있는 원본만 읽음 |
| (합성) `event_id`·`scenario_id`·`generator_version`·`data_origin` | 어떤 시나리오로, 어느 생성기 버전이 만든 이벤트인가 |

형식이 깨진 이벤트도 Bronze에는 그대로 남깁니다. 걸러 내는 일은 Silver가 **격리**로 합니다.

## 4.2 Silver — 표준화와 품질 확보 (11/2 주)

세 수집자의 원본을 **업무 키**로 합쳐 한 번만 셉니다.

> 업무 키 = (`data_origin`, `source`, 지역, 사업장, 배출구, 항목, `measured_at`)

| 경우 | 처리 |
|---|---|
| 세 수집자의 값이 같음 | 1행, `dup_count = 3`, `seen_collectors = [b, c, aws]` |
| 같은 키인데 값이 다름 | **어느 쪽도 고르지 않고 격리**, 사유 기록 |
| 상태 문구(보수중 등) | 측정값 대신 `record_state`로 표시. 0으로 바꾸지 않음 |
| 빈 값 | 채우지 않고 빈 값으로 둠 |

주요 열(예시 — 정확한 이름은 11/2 주 Task 4 필드 사전에서 확정):

| 열 | 뜻 |
|---|---|
| `data_origin` | 실측(`keco_observed`) / 합성(`synthetic`) 구분 |
| `region_std`, `fact_manage_nm`, `stack_code`, `item_code` | 지역·사업장·배출구·항목 |
| `measured_at`, `ingested_at` | 측정 시각(KST), 들어온 시각 — **둘을 구분**한다 |
| `measure_value`, `standard_value` | 측정값, 그 시각에 유효한 허용기준 |
| `ratio_pct` | 기준대비율 = 측정값 ÷ 허용기준 × 100 (반올림하지 않음) |
| `record_state`, `is_valid` | 상태 문구, 유효한 측정인지 |
| `dup_count`, `seen_collectors` | 몇 수집자가 같은 값을 받았나 |

> **이름만 맞춘다고 의미가 같아지지 않습니다.** EPA의 NOx는 배출률(lbs/mmBtu), 국내는 농도(ppm)입니다. 그래서 EPA는 `epa_silver.*`로 **따로** 둡니다. EPA에는 법적 기준이 없어 대리 기준(`proxy-v0`)을 쓰고, 법적 기준이 아님을 표시합니다.

## 4.3 Feature — 모델이 쓸 입력 (11/9 주)

국내 Feature 14개 중 일부입니다(정본 4.1).

| Feature | 뜻 |
|---|---|
| `ratio_pct` | 현재 기준대비율 |
| `ratio_lag_30m` · `ratio_lag_60m` | 30분 전 · 60분 전 기준대비율 |
| `ratio_rolling_mean_1h` · `ratio_rolling_mean_3h` | 최근 1시간 · 3시간 평균 |
| `ratio_diff_30m` | 직전 구간 대비 변화량 |
| `ratio_pct_change_30m` | 직전 구간 대비 변화율(직전 값이 0이면 빈 값) |
| `hour` · `dayofweek` | 시간대 · 요일 |

예시(배출구 A NOx):

| 기준 시각 | `ratio_pct` | `ratio_lag_30m` | `ratio_lag_60m` | `ratio_diff_30m` |
|---|---:|---:|---:|---:|
| 13:00 | 66.0 | 60.0 | 58.0 | 6.0 |
| 13:30 | 72.0 | 66.0 | 60.0 | 6.0 |
| 14:00 | 78.0 | 72.0 | 66.0 | 6.0 |

만들 때 지킬 것:

1. **시간으로 찾습니다.** "30분 전 값"은 행 순서가 아니라 `measured_at − 30분`으로 찾습니다. 중간이 빠지면 "한 행 전"이 60분 전일 수 있습니다.
2. **창에 값이 충분할 때만 계산합니다.** 3시간 창은 6개 중 4개 이상, 1시간 창은 2개 모두. 모자라면 빈 값입니다.
3. **예측 시점에 알 수 있던 값만 씁니다.** 늦게 들어온 값은 그 시각의 Feature에 넣지 않습니다.
4. **학습과 운영이 같은 함수를 씁니다.** 공통 Feature Library 하나로 국내 배치·합성 스트리밍·EPA를 모두 계산합니다.
5. **`data_origin` × 배출구 × 항목별로 따로** 계산합니다. 합성 값이 실측 배출구의 Lag에 섞이면 안 됩니다.

> 별도의 Feature Store 제품이 꼭 필요하지는 않습니다. 우리는 Silver 창을 읽어 공통 Feature Library로 계산하고, 추론에 쓴 값을 `tms_feature.online_features`에 남깁니다.

## 4.4 Label — 모델이 배울 정답 (11/9 주)

| 라벨 | 모델 | 정답 |
|---|---|---|
| `label_entry_60m` **(주)** | 분류 | 지금 90% 미만일 때, **t+30 또는 t+60 중 하나라도 ≥ 90%** 이면 1 |
| `label_ratio_60m` (보조) | 회귀 | t+60의 기준대비율(학습용 상한 200%) |

왜 두 시점을 보나요?

| 시각 | 기준대비율 | |
|---|---:|---|
| 09:00 | 78% | 기준 시각 |
| 09:30 | **93%** | 진입 |
| 10:00 | 88% | 다시 내려옴 |

t+60(10:00, 88%)만 보면 라벨이 0이 되어 **실제 진입을 놓칩니다.** 그래서 분류 라벨은 1입니다.

미래 값이 빠졌을 때가 가장 중요합니다.

| t+30 | t+60 | 라벨 | 이유 |
|---|---|---|---|
| 88% | 85% | 0 | 둘 다 확인됐고 진입 없음 |
| 93% | 결측 | 1 | 진입이 확인됨 |
| 88% | 결측 | **제외** | t+60에 진입했을 수도 있음 |
| 보수중 | 85% | **제외** | 점검 중에 올랐을 수도 있음 |

> **확인된 진입은 남기고, 0(음성)은 두 값이 모두 유효할 때만.** 미래의 상태 문구는 "정상"이 아니라 "알 수 없음"입니다. 빈 정답을 0으로 채우지 않습니다.

라벨 규칙은 `label-v1`이라는 이름으로 **11/12까지 고정**하고, 결과를 본 뒤 바꾸지 않습니다(정본 부록 B).

## 4.5 Gold — 판정 결과의 원본 (11/16 주)

`tms_gold.judgement` 한 행에 다음이 함께 들어갑니다(정본 3.6).

| 묶음 | 예 |
|---|---|
| 키 | `data_origin`, `stack_code`, `item_code`, `measured_at`, `rules_version`, `model_version` |
| 현재 | `current_ratio_pct`, `current_level`(Rule Engine) |
| 예측 | `entry_probability`(분류), `predicted_ratio_pct`(XGBoost), `rf_predicted_ratio_pct`(RF) |
| 판정 | `final_level`, `early_warning`, `early_warning_reason`, `model_disagreement` |
| 보류·추적 | `hold_reason`, 사용한 Feature·특성·점수 버전, `processed_at` |

Gold의 네 가지 규칙:

1. **같은 키는 한 번만 씁니다.** 재시도해도 행이 두 번 생기지 않습니다.
2. **고쳐 쓰지 않습니다.** 모델이나 규칙이 바뀌면 키가 달라져 새 행이 생깁니다.
3. **늦게 온 값으로 다시 판정하지 않습니다.** Gold는 "그 시각에 알 수 있던 값으로 내린 판정"입니다.
4. **라벨은 Gold에 넣지 않습니다.** 평가할 때 Gold 예측과 라벨 스냅샷을 키로 조인합니다.

> **숫자의 원본은 언제나 Gold입니다.** 경고 이력(PostgreSQL), Elasticsearch, Agent 답변은 모두 Gold 값을 복사해 씁니다. 화면이 따로 계산하지 않습니다.

# 5. 세 데이터 원천의 역할

| 원천 | 역할 | 처리 경로 | 어디에 쓰나 |
|---|---|---|---|
| **환경공단 TMS API**(주) | 실제 배출 | Airflow·EventBridge → Lambda → Silver | 모델 학습·**검증·평가(Validation·Test는 실측만)** |
| **합성 데이터** | 드문 상황 시험, 학습 보강 | Python 생성기 → Kafka → Spark Structured Streaming | ① 시나리오 반응 평가 ② +S 실험의 Train 보강 |
| **EPA CAMPD**(부) | 급등 패턴 학습 | 분기 파일 → Glue·Spark Batch | EPA 점수 모델(`epa-surge-v1`) → 국내 NOx·SOx의 `epa_surge_score` |

## 5.1 합성 데이터는 "장난감"이 아니다 — 하지만 섞는 규칙이 있다

합성 데이터도 실측과 **같은 Silver 구조, 같은 Feature 코드, 같은 모델, 같은 판정 규칙**을 통과합니다(정본 3.1). 다만:

- 출처(`data_origin`)와 시나리오(`scenario_id`)를 반드시 구분합니다.
- **성능 평가(Validation·Test)에는 실측만** 씁니다.
- 학습에 더할 때(+S)는 Train 행의 30% 이내, 가중치 0.5로 고정합니다.
- 학습용 시나리오와 평가·시연용 시나리오가 겹치지 않게 `scenario_id`로 나눕니다.
- 합성 배출구는 `SYN-` 접두어를 씁니다. 크기 통계를 가져온 실측 배출구는 `ref_stack_code`로 기록합니다.

| 시나리오 예 | 확인하는 것 |
|---|---|
| 정상 변동 | 실측 정상 패턴과 비슷한가 |
| 급등 | 사전 경고가 제때 나는가 |
| 지속 상승 | 추세를 잡는가 |
| 결측 | 빈 값·보류가 제대로 남는가 |
| 지연 | 워터마크(60분)를 넘으면 격리되는가 |
| 중복 | 같은 `event_id`가 1행이 되는가 |
| 측정기 이상 | 실제 위험 신호와 구분되는가 |

> 합성 데이터가 많다고 모델이 좋아지지 않습니다. 실측 분포와 너무 다르면 오히려 나빠집니다. 그래서 +S는 **Validation에서 나아질 때만** 채택합니다.

## 5.2 EPA는 "가중치"가 아니라 "지식"을 옮긴다

EPA와 국내는 단위(배출률 vs 농도), 간격(60분 vs 30분), 기준의 뜻(법적 기준 없음 vs 허용기준)이 모두 다릅니다. 그래서 EPA 행을 국내 학습에 그대로 섞지 않고:

1. 두 원천에서 **같은 식**으로 계산되는 단위 없는 특성 5개(`common-v1`, 자기 P99 대비 %)를 만들고
2. EPA만으로 급등 점수 모델(`epa-surge-v1`)을 학습한 뒤
3. 국내 NOx·SOx 행에 그 점수를 **Feature 하나**로 붙입니다(B+E 실험, 정본 부록 C).

# 6. 기술별 역할

**누가 시작시키고, 누가 전달하고, 누가 처리하는지**를 구분하면 헷갈리지 않습니다.

| 기술 | 역할 | 우리 프로젝트 |
|---|---|---|
| Airflow · EventBridge | 작업의 **시각과 순서** 관리 | 05·35분 수집, 15·45분 표준화 Lambda 깨우기, 재시도 |
| Lambda · PyIceberg | 실측 **처리** | 수집 안전망, Silver 표준화, 판정 |
| Kafka | 이벤트 **전달** | 합성 이벤트, 토픽 `tms.synthetic.v1`, 키 `stack_code|item_code` |
| Spark Structured Streaming | 합성 **처리** | Bronze → Silver → Feature → 판정, trigger 1분, 워터마크 60분 |
| Glue · Spark Batch | EPA 대량 **처리** | EPA 분기 파일 표준화 |
| S3 · MinIO | **저장소** | MinIO는 로컬 버퍼, S3가 원본 저장소 |
| Parquet | **파일 형식** | 컬럼 단위 저장, 압축·조회에 유리 |
| Apache Iceberg | **테이블 형식** | 여러 파일을 하나의 테이블로. 스키마·스냅샷·MERGE |
| Glue Data Catalog | 테이블 **메타데이터** | Iceberg 테이블 목록·스키마 |
| PostgreSQL | **운영 이력** | 경고 이력, JEV 이력, 질의 기록처럼 자주 읽고 갱신하는 것 |

> Airflow는 데이터를 분석하지 않습니다. Kafka는 데이터를 정제하지 않습니다. **Airflow는 관리하고, Kafka는 전달하고, Lambda·Spark는 처리합니다.**

### Parquet와 Iceberg의 차이

- **Parquet:** 데이터를 담는 **파일** 하나의 형식
- **Iceberg:** 그 파일들을 **테이블**처럼 관리하는 규칙. 스냅샷이 있어서 "그때의 데이터"로 돌아가 볼 수 있습니다. 라벨 스냅샷, Feature 스냅샷 고정에 이 성질을 씁니다.

### 저장 구조 예시

```text
S3
├── bronze/
│   ├── keco/collector=b|c|aws/…        환경공단 원본(수집자별)
│   ├── synthetic_kafka/…               합성 이벤트 원본
│   └── epa/…                           EPA 분기 파일
└── warehouse/ (Iceberg)
    ├── tms_silver.measurements
    ├── epa_silver.*
    ├── tms_feature.keco_features · online_features
    └── tms_gold.judgement  (+ 뷰 gold.v_judgement_observed · v_daily_summary)
```

경로 이름은 예시입니다. 실제 경로는 11/2 주에 팀이 정하고 계보 규칙(Task 12)에 적습니다.

# 7. 데이터가 모델과 판정으로 이어지는 방식

## 7.1 세 모델, 세 질문

같은 Feature 한 행을 세 모델에 넣고, 서로 다른 질문의 답을 받습니다(정본 5.1).

| 모델 | 질문 | 답(Gold 열) | 역할 |
|---|---|---|---|
| 분류 `clf-v1` (XGBoost 또는 RF) | 60분 안에 90%를 넘을까? | `entry_probability` 0.52 | **주 모델** |
| XGBoost 회귀 `reg-v1` | 60분 뒤 몇 %일까? | `predicted_ratio_pct` 98% | 보조 |
| RF 회귀 `rf-reg-v1` | 같은 질문, 다른 방식 | `rf_predicted_ratio_pct` 82% | 비교(검산) |

**분류 모델인데 왜 0/1이 아니라 0.52인가요?** 분류 모델은 클래스(0/1)도, 클래스별 확률도 낼 수 있습니다. 0/1은 확률을 기준값으로 자른 결과일 뿐입니다(기본값 0.5). 90% 진입은 드문 사건이라 0.5로 자르면 많이 놓치므로, 우리는 **확률을 받아 두고** Validation에서 정한 운영 임계값으로 Python Final Decision이 자릅니다. 그 결과가 Gold의 `early_warning`(true/false)입니다. 확률이 있어야 임계값 조정과 PR-AUC 계산도 할 수 있습니다.

두 회귀의 차이(|98 − 82| = 16%p)가 기준값(10%p에서 출발) 이상이면 "모델 불일치"로 표시합니다.

## 7.2 AI는 돕고, 판정은 Python 규칙이 한다

```text
 Rule Engine(현재 값 → 현재 단계)  ─┐
 분류 확률 · XGBoost 회귀           ─┼─▶ Python Final Decision ─▶ Gold
 두 회귀의 차이(불일치)              ─┘      · 현재 단계는 ML이 낮추지 못함
                                            · 확률 ≥ 임계값 또는 XGBoost ≥ 90%면 사전 경고
                                            · JEV는 기다리지 않음(판정 흐름 밖에서 불일치 행만 분류)
```

| 기준대비율 | 현재 단계 |
|---|---|
| 80% 미만 | NORMAL |
| 80~90% | CAUTION |
| 90~100% | WARNING |
| 100% 이상 | EXCEEDANCE |

이 경계는 **프로젝트 내부 기준**이며 법적 위반 여부를 판단하지 않습니다.

## 7.3 평가는 무엇으로 하나

- **분류(주):** PR-AUC, 사건 단위 Recall·Precision·F1, 오경보 건수, Lead Time(60분 전 / 30분 전 / 놓침)
- **회귀(보조):** MAE, RMSE, **Persistence**(60분 뒤에도 지금과 같다고 보는 예측) 대비 개선율
- R²는 배출구마다 수준 차이가 커서 높게 나와도 좋은 예측이라는 뜻이 아닐 수 있으므로 참고로만 씁니다.
- **시간 순서로 나눕니다.** Train 10/30~11/12 → Validation 11/13~11/17 → 연결·고정 11/18~11/22 → Test 11/23~12/4. 무작위 분할을 쓰지 않습니다.
- **Validation으로 고르고 Test로 한 번 보고합니다.** Test를 보고 바꾸지 않습니다.

# 8. 꼭 지켜야 할 다섯 가지

## 8.1 미래 정보를 쓰지 않는다 (데이터 누수)

09:00에 10:00을 예측하는데 10:00 값이 Feature에 들어가면, 평가에서는 성능이 좋아 보이지만 실제 운영에서는 맞히지 못합니다.

- Feature는 `ingested_at`이 예측 시점 이전인 값만
- 구간 경계 60분은 빼서 라벨이 다음 구간을 보지 않게
- P99 같은 통계는 **Train 구간만**으로 계산

## 8.2 시간으로 찾는다

"두 행 뒤"는 60분 뒤가 아닐 수 있습니다. Feature와 라벨 모두 `measured_at` 기준 시간 창으로 찾습니다.

## 8.3 빈 값을 채우지 않는다

0이나 직전 값으로 메우면 모델이 거짓을 배웁니다. 빈 값은 빈 값으로, 이유(결측·상태 문구·허용기준 없음)는 따로 셉니다.

## 8.4 거슬러 갈 수 있어야 한다 (데이터 계보)

모델이 틀렸을 때 다음에 답할 수 있어야 합니다.

| 질문 | 어디서 확인하나 |
|---|---|
| 어떤 원본이었나 | Bronze 경로, `seen_collectors`, 확정 표지 |
| 어떻게 바뀌었나 | Silver 처리 버전, 격리 기록 |
| 어떤 입력이 들어갔나 | `tms_feature.online_features`(Gold와 같은 키) |
| 어떤 모델·규칙이었나 | Gold의 `model_version`, `rules_version` |
| 그 시각에 무엇을 알았나 | Gold는 그 시각의 판정이고 고쳐 쓰지 않음 |

## 8.5 출처를 섞지 않는다

실측·합성·EPA는 `data_origin`과 테이블로 구분합니다. 성능 수치와 실측 경고 건수는 **실측만으로** 말합니다(`gold.v_judgement_observed`).

# 9. 품질을 숫자로 보여 주는 지표

"잘 됐다"를 말하려면 숫자가 필요합니다. 아래 목표는 **출발점 예시**이고, 실제 기준은 팀이 정해 결정 기록에 남깁니다.

| 영역 | 지표 | 목표 예시 |
|---|---|---|
| 완전성 | 필수 열 결측률(상태 문구 제외) | 1% 이하 |
| 유일성 | 같은 업무 키 중복 | 0건 |
| 적시성 | 30분 구간 수집 성공률(원천 미수신과 수집 실패를 나눠서) | 99% 이상 |
| 표준화 | Silver 변환 점검 테스트 | 100% 일치 |
| 충돌 | 같은 키·다른 값 격리 건수 | 0건을 목표로 하되 숨기지 않고 보고 |
| Feature | Feature 생성 성공률(창 부족 빈 값 비율도 함께) | 99% 이상 |
| 라벨 | 이유별·항목별 제외 행 수 | 구간 닫힌 뒤 산출 |
| 계보 | Silver 한 행 → Bronze 원본 추적 | 100% |
| 대표성 | 실측·합성 분포 비교, 항목별 사건 수 | 시나리오별 확인 |

> 숫자가 나쁘면 숨기지 말고 **원인과 조치**를 함께 적습니다. "충돌 12건, 원인: 수집자 c의 시각 표기 오류, 조치: 매핑 수정 PR"처럼요.

# 10. 프로젝트 안에서 AI-Ready를 확인하는 관문

AI-Ready는 마지막에 한 번 확인하는 것이 아닙니다. 우리 일정에는 **네 번의 관문**이 있습니다.

| 언제 | 관문 | 무엇을 보나 | 통과하지 못하면 |
|---|---|---|---|
| 11/6 (11/2 주 Task 7) | **AI-Ready Data 점검** | Bronze·Silver의 뜻·구조, 품질, 계보, 시간 정합성, 누수 가능성 → `usable` / `conditional` / `unusable` 판정 | Feature·라벨 작업을 시작하지 않음 |
| 11/13 (11/9 주 Task 5) | **AI 준비도 게이트** | Feature 데이터셋의 구간 분리·누수·결측·출처 구분 | 학습 리허설을 멈추고 원인부터 |
| 11/18 오전 (11/16 주 Task 4) | **본 실험 전 게이트** | 구간 분리·미래 정보 누수·출처 분리를 다시 확인 | 본 실험을 시작하지 않음 |
| 11/27·12/7 (평가 세 축 ①) | **Silver 변환 점검** | 원본이 규칙대로 Silver로 바뀌는가(고정 사례 100% 일치) | 모델 성능과 섞지 않고 따로 보고 |

`conditional`(조건부)은 "어떤 조건에서는 써도 된다"는 뜻입니다. 예: "HCl은 0이 많아 변화율 Feature를 쓸 수 없음 → 변화량만 사용". 조건을 반드시 함께 적습니다.

# 11. 체크리스트

## Align

- [ ] 무엇을 예측하는지 한 문장으로 말할 수 있다("60분 안에 기준대비율 90% 진입")
- [ ] 한 행(Grain)이 무엇인지 안다: `data_origin` × 배출구 × 항목 × 30분
- [ ] 필드 사전에 항목별 뜻·단위·시간대가 있다
- [ ] 분류·회귀 라벨의 정의(`label-v1`)를 설명할 수 있다
- [ ] 항목별 사건 수를 알고, ML 대상 항목을 근거와 함께 골랐다
- [ ] 세 원천의 역할(국내 주, EPA 부, 합성 시험·보강)을 구분한다

## Qualify

- [ ] 중복·충돌·빈 값·상태 문구를 각각 다르게 처리한다
- [ ] 측정 시각과 수집 시각을 구분한다
- [ ] Feature와 라벨을 시간으로 찾고, 고정 사례 테스트가 있다
- [ ] 배치와 스트리밍이 같은 입력에 같은 결과를 낸다
- [ ] 라벨·특성·모델·규칙에 버전이 붙어 있다
- [ ] 바꾼 뒤 CI의 고정 사례 테스트가 통과한다
- [ ] 수집 누락률·격리 건수·지연을 매일 볼 수 있다

## Govern

- [ ] 실측·합성·EPA가 출처로 구분되고, 성능은 실측만으로 말한다
- [ ] 새 상태 문구는 PR과 두 명 검토로만 반영한다
- [ ] 모델 예측·Rule Engine 판정·최종 판정이 화면에서 구분된다
- [ ] 예측과 즉석 추론을 사실처럼 표현하지 않는다
- [ ] 합성 배출구는 `SYN-`이고 실제 사업장에 알림이 가지 않는다
- [ ] 비밀값이 코드·문서·화면 캡처에 없다

# 12. 핵심 용어 한눈에

| 용어 | 한 줄 뜻 |
|---|---|
| AI-Ready Data | AI가 목적에 맞게 믿고 쓸 수 있도록 준비하고 계속 관리하는 데이터 |
| Align | 목적에 맞는 데이터를 준비하는 관점 |
| Qualify | 데이터가 조건을 계속 충족하는지 검증하는 관점 |
| Govern | 출처·책임·권한·AI 결과를 통제하는 관점 |
| Grain | 한 행이 무엇을 뜻하는가(우리: 배출구 × 항목 × 30분) |
| Bronze | 원본 그대로 보존 |
| Silver | 표준화·정제·격리 |
| Feature | 모델 입력값. Silver에서 바로 만든다 |
| Label | 모델이 배울 정답. Gold에 넣지 않는다 |
| Gold | 판정 결과의 원본(`tms_gold.judgement`). 집계는 뷰 |
| 격리 | 지우지 않고 따로 두고 사유를 남기는 것 |
| 상태 문구 | 측정값 대신 오는 "가동중지·보수중" 등. 0도 정상도 아니다 |
| 데이터 누수 | 예측 시점에 알 수 없는 미래 정보가 입력에 섞이는 문제 |
| 데이터 계보 | 원본부터 판정까지 거슬러 갈 수 있는 기록 |
| 스냅샷 | 특정 시점의 데이터를 고정한 판본(라벨·Feature 고정에 사용) |
| Persistence | "60분 뒤에도 지금과 같다"고 보는 가장 단순한 예측. 모델이 이것보다 나아야 의미가 있다 |
| Airflow · EventBridge | 작업의 시각과 순서 관리 |
| Kafka | 이벤트 전달 |
| Spark Structured Streaming | 합성 이벤트를 연속 처리 |
| Parquet · Iceberg | 파일 형식 · 그 파일들을 테이블로 관리하는 형식 |

# 13. 마무리 — 스스로 답해 볼 질문

AI 프로젝트에서 많은 사람이 "어떤 모델을 쓸까"부터 고민합니다. 하지만 다음 중 하나만 있어도 XGBoost든 RF든 결과를 믿을 수 없습니다.

- 측정 시각이 어긋난 데이터
- "보수중"이 0으로 바뀐 데이터
- 배출구·항목이 섞인 데이터
- 학습 때와 운영 때 Feature 계산이 다른 경우
- 미래 값이 입력에 섞인 경우

> **이번 프로젝트의 목표는 모델 하나를 만드는 것이 아니라, 모델이 계속 믿고 쓸 수 있는 데이터를 공급받는 구조를 만드는 것입니다.**

각자의 Task가 이 구조의 어느 부분인지 생각하면서 진행하면 좋겠습니다. 다음 질문에 답할 수 있으면 이 자료를 이해한 것입니다.

1. 95%로 튄 값을 지우면 안 되는 이유와, 그래도 확인해야 하는 것은 무엇인가?
2. 우리 Gold가 집계표가 아니라 판정 결과표인 이유는 무엇인가?
3. Feature를 Gold가 아니라 Silver에서 만드는 이유는 무엇인가?
4. t+60 하나만 보는 라벨은 무엇을 놓치는가?
5. 합성 데이터를 학습에 더할 수는 있지만 평가에 쓰지 않는 이유는 무엇인가?
6. EPA 행을 국내 학습에 그대로 섞지 않고 점수 하나로만 옮기는 이유는 무엇인가?
7. 모델이 틀린 예측을 했을 때, 어떤 테이블을 어떤 순서로 보면 원인을 찾을 수 있는가?
