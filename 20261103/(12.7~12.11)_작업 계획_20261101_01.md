# 3. Task별 큰 흐름

## Task 1. Agent 하이브리드 질의 조립

- **왜:** 규칙·ML·LLM이 각자 잘하는 일만 맡게 해야 답이 정확하고 설명 가능하다.
- **어떤 방식으로**
  1. 설계서의 단계를 순서대로 잇는다. 앞 단계에서 확정되면 뒤 단계를 건너뛴다.
  2. 미래 위험 질문에는 Gold에 있는 승인 모델의 예측값을 근거로 붙인다(새로 돌리지 않는다). 예외는 `model_infer` 유형뿐이고 Task 20~22가 맡는다.
  3. LLM 답변은 도구 결과의 숫자만 쓰게 하고, 대조에 실패하면 템플릿 답변으로 바꾼다.
  4. 질문마다 거친 단계와 근거를 기록한다.
- **결과물:** Agent 실행 진입점, 질의 기록
- **고민할 점:** 화면에 보이는 숫자와 Agent 답의 숫자가 항상 같다는 것을 어떻게 보장할 것인가?

## Task 2. RAG 답변 연결

- **왜:** 법령·규칙 질문은 근거 조문을 보여 줘야 믿을 수 있다.
- **어떤 방식으로:** 검색된 조각만 근거로 답하고 문서명·조문·시행일을 인용한다. 기준 점수 미만이면 "찾지 못함"으로 답하고, 위반 여부는 판단하지 않는다.
- **결과물:** RAG 답변 기능

## Task 3. 브리핑

- **왜:** 담당자는 매번 질문하지 않고도 현황을 한 번에 보고 싶다.
- **어떤 방식으로:** 같은 Agent와 같은 도구로 현황·기간별·사업장별 브리핑을 만든다. 문단마다 근거를 붙이고, 실패하면 표와 숫자만 있는 템플릿 브리핑으로 바꾼다.
- **결과물:** 브리핑 3종

## Task 4. Agent·RAG 평가

- **왜:** "잘 된다"를 숫자로 보여 줘야 발표에서 설득할 수 있다.
- **어떤 방식으로**
  1. 단계별 처리 비율, 숫자 일치, 근거 표기, 범위 밖 답변 여부를 잰다.
  2. 평가 질문 세트로 키워드 분류기의 질문 유형 정확도를 잰다.
  3. Task 16~19를 만들었으면 같은 보고서에 따로 칸을 두고 잰다: 근거 표기율, 안내한 확인 항목·절차가 근거 조각에 실제로 있는지, 템플릿 답변으로 바뀐 비율.
  4. (선택) 같은 질문 세트를 GPT-6 Luna(`gpt-6-luna`)로도 돌려 GPT-6.1 Terra와 숫자 대조 통과율·템플릿 전환 비율을 비교한다. 모델을 바꿀지는 멘토와 협의한다.
  5. Task 20~22를 만들었으면 `model_infer` 평가 질의(지난주 Task 16)의 처리 결과(정상·되묻기·범위 밖·거절·다른 유형)와 0% 검증 통과 여부를 따로 적는다.
- **결과물:** Agent·RAG 평가 보고서, 키워드 분류기 정확도

## Task 5. n8n ① 기준치 초과 알림

- **왜:** 기준치를 넘은 순간은 사람이 바로 알아야 한다.
- **어떤 방식으로:** 경고 이력에서 새로 생긴 초과만 읽어 Slack 초과 채널로 한 번 보낸다. 합성 데이터에서 나온 초과는 합성임을 표시한다.
- **결과물:** 기준치 초과 알림 워크플로

## Task 6. n8n ② 수집·처리 현황 알림

- **왜:** 데이터가 잘 들어오고 처리되는지 운영자가 매일 확인할 수 있어야 한다.
- **어떤 방식으로:** 정해진 시각에 수집·처리 요약을 보내고, 장애·격리가 생기면 바로 Slack 운영 채널로 보낸다.
- **결과물:** 수집·처리 현황 알림 워크플로

## Task 7. n8n 알림 시험·정리

- **왜:** 같은 알림이 여러 번 가거나, 실패를 모르고 지나가면 알림을 믿을 수 없다.
- **어떤 방식으로:** 중복 방지와 실패 재시도를 시험하고, 워크플로를 비밀값 없이 저장소에 남기며, 실행 이력을 파이프라인 화면에서 볼 수 있게 잇는다.
- **결과물:** 시험 결과, 워크플로 파일

## Task 8. Kibana 화면 구현

- **왜:** 운영자가 데이터 흐름·판정·경고·모델 성능을 한눈에 봐야 한다.
- **어떤 방식으로:** 설계서의 필수 화면을 모두 만든다. 기본 화면은 실측만 보이게 하고, 합성은 따로 구분한다.
- **결과물:** Kibana 필수 화면

## Task 9. Streamlit 구현

- **왜:** 질문하고 답을 받는 화면, 경고를 자세히 보는 화면이 필요하다.

## Task 11. 통합 시연

  2. 목요일에 리허설하고, 끊긴 곳을 고쳐 금요일에 본 시연을 한다.

- **결과물:** 통합 시연 기록
- **고민할 점:** 한 단계가 실패하면 어디서 끊겼는지 바로 보이는가?

## Task 12. 최종 산출물 점검

- **어떤 방식으로:** 정본의 필수 검증 항목과 최종 결과물 목록으로 하나씩 점검하고, 빠진 것은 담당과 처리 방향을 적는다.
- **결과물:** 최종 점검표 → **기능 동결(12/11)**

## Task 13. Test 전체 최종 평가

- **왜:** 처음 보는 실측 12일에서의 성능이 이 프로젝트 모델의 최종 성적이다. 4일(Test-1)에는 주말이 없고 사건이 적었다.
- **어떤 방식으로**
  1. 12/7에 승인된 분류·회귀 모델을 Test 전체(11/23~12/4)로 한 번 평가한다. 11/27 Test-1 평가와 같은 스크립트를 쓴다. 채택하지 않은 실험 5개(B·B+E·+S × XGBoost·RF 중 나머지)의 Test 점수는 같은 스크립트로 계산해 **비교 행으로만** 적고, 그 결과로 채택을 바꾸지 않는다(정본 5.2).
  2. Validation, Test-1과 나란히 놓고 비교한다.
  3. 규칙만 쓸 때와 규칙 + ML을 쓸 때를 비교한다.
  4. 사건 수, 배출구 단위 신뢰 구간, Test 적정성 기준 충족 여부를 함께 적는다. 기준을 못 채운 항목은 "사건 부족 — 참고값"으로 표시한다.
- **결과물:** 분류·회귀 Test 결과표(최종), 규칙만 vs 규칙 + ML 비교표(최종)
- **고민할 점:** Test-1과 Test 전체의 차이가 크면 무엇 때문인가(주말, 특정 배출구, 장애 구간)?

## Task 14. 오류 분석·평가 보고서 확정

- **어떤 방식으로:** 1차 오류 분석을 Test 전체 사례로 보완하고, 평가 세 축 보고서의 ② 모델 성능을 최종 수치로 바꾼다. 모델 완료 항목을 PASS·FAIL로 점검한다.
- **결과물:** 오류 분석 기록(최종), 평가 세 축 보고서(최종), 모델 완료 점검표 → **분류·회귀 모델 평가 완성**

## Task 15. JEV 효과 평가

- **왜:** JEV가 Python 규칙보다 나은지 숫자로 보여 줘야 시연에 넣을지 정할 수 있다(정본 12.2).
- **어떤 방식으로**
  1. Test 구간(11/23~12/4)에서 불일치 표시가 붙은 행을 모은다. 정답은 미리 정한 규칙(정본 12.2)으로 만든다.
  2. A안(Python 규칙)과 B안(JEV)의 유형 정확도, 운영자 확인이 필요한 상황의 Recall·Precision, 불필요한 확인 표시 비율을 비교한다.
  3. JEV 호출 비율, 응답 시간, 실패율, 비용을 함께 적는다. 두 안이 다르게 판단한 행은 따로 표로 남긴다.
  4. JEV 키가 없었으면 A안 결과만 적고 그 사실을 밝힌다.
- **결과물:** JEV 효과 평가표
- **고민할 점:** 불일치 행이 적을 때 두 안의 차이를 어디까지 믿을 수 있는가?

## Task 16. (Should) 경고 대응 안내

- **왜:** 경고 설명이 "왜"에 답한다면, 대응 안내는 "그럼 뭘 확인하지?"에 답한다. 항목·사유·상태의 조합이 많아서 템플릿으로 미리 다 써 둘 수 없다.
- **어떤 방식으로**
  1. `response_guide` 유형 질문이면 조회 함수로 해당 Gold 행(항목, 현재 대비율, 예측값, 사전 경고 사유, 상태 문구)을 가져온다.
  2. 그 조건으로 `response_guide_v1`(지난주 Task 14)을 검색한다. 실습용 경고 대응 확인표를 먼저 찾는다.
  3. LLM이 검색된 조각에 있는 확인 항목만 골라 3~5줄로 정리하고, 줄마다 근거 문서·쪽·조문을 붙인다.
  4. 숫자는 대조 모듈로 확인한다. 검색 점수가 기준 미만이거나 대조에 실패하면 확인표 원문과 출처만 보여 주는 템플릿 답변으로 바꾼다.
- **결과물:** 대응 안내 기능, 고정 사례 테스트(NOx·SOx·먼지 × 사유별 1건 이상)
- **지키는 것:** 확인 항목만 안내하고 조치를 지시하지 않는다. "실제 조치는 사업장 환경기술인과 운영 절차를 따릅니다"를 붙인다.

## Task 17. (Should) 법령 절차 설명

- **왜:** "초과하면 어떻게 돼?" 같은 질문은 답이 조문 하나에 있지 않다. 원문만 나열하면 순서와 관계를 읽는 사람이 직접 맞춰야 한다.
- **어떤 방식으로**
  1. `regulation_qa` 질문에서 관련 조각이 두 개 이상 검색되면, LLM이 조문 2~4개를 절차 순서로 엮어 쉬운 말로 설명한다.
  2. 문장마다 법령명·조문·시행일을 붙이고, 인용이 검색된 조각과 맞는지 자동 대조한다.
  3. 조각이 하나뿐이거나 대조에 실패하면 Task 2의 원문 인용 답변으로 바꾼다.
- **결과물:** 절차 설명 기능, 고정 사례 테스트
- **지키는 것:** 위반 여부와 처분 수위는 판단하지 않는다. "법률 자문이 아니며 특정 사업장의 위반 여부를 판단하지 않습니다"를 붙인다.

## Task 18. (Could) 현황+규정 혼합 질문

- **왜:** 운영자는 "지금 상태"와 "규정상 의미"를 한 번에 묻는 경우가 많다.
- **어떤 방식으로:** 설계서에서 허용한 유형 조합(예: `current_status` + `regulation_qa`, `early_warning_list` + `response_guide`)만 두 도구를 함께 실행한다. LLM이 한 답변으로 엮되 [현황]과 [규정] 근거를 따로 표시한다. 허용하지 않은 다중 유형은 지금처럼 되묻는다.
- **결과물:** 혼합 질문 처리, 고정 사례 테스트

## Task 19. (Could) EPA 지식 카드 연결

- **왜:** EPA에서 확인한 패턴을 국내 경고 설명에 참고로 붙이면 EPA 지식 이전을 보여 줄 수 있다.
- **어떤 방식으로:** `alert_reason`·`epa_knowledge` 답변에서 국내 경고의 특성(항목·변화 패턴)으로 `epa_cards_v1`을 검색하고, 맞는 카드가 있으면 LLM이 `[EPA · 참고]` 문단을 따로 쓴다.
- **결과물:** EPA 참고 문단 기능
- **지키는 것:** 카드에 있는 숫자만 쓰고, 국내 수치와 같은 문장에 섞지 않는다. "가능한 패턴"으로만 쓰고 원인을 단정하지 않는다.

## Task 20. (Should) 모델 즉석 추론

- **왜:** 판정 흐름 밖에서 승인 모델을 직접 불러 보면, 모델이 실제로 어떻게 동작하는지와 판정 흐름과 같은 값을 내는지를 확인할 수 있다. Task 21·22의 기준점이기도 하다.
- **어떤 방식으로**
  1. `model_infer` 유형 질문(예: "3번 배출구 NOx 지금 예측해 줘")에서 배출구·항목을 뽑는다. 배출구가 없으면 되묻는다.
  2. Silver에서 해당 배출구 × 항목의 기준시각까지 3시간 창을 판정 흐름과 같은 `ingested_at` 조건으로 읽고, 공통 Feature Library로 Feature를 계산한다(판정 흐름과 같은 Feature 정의·버전). B+E가 채택됐다면 `epa_surge_score`도 다시 계산한다.
  3. 승인 모델 3개(분류 모델 `clf-v1`, XGBoost 회귀 모델 `reg-v1`, RF 회귀 모델 `rf-reg-v1`)로 진입 확률·XGBoost 예측 대비율·RF 예측 대비율을 낸다. 모델은 앱을 시작할 때 한 번만 읽기 전용으로 불러온다.
  4. 결과 카드에 즉석 추론 값과 같은 기준시각의 Gold 값을 나란히 보여 주고, 같으면 "일치"를 표시한다.
  5. 질문·기준시각·모델 버전·결과를 `ops.nl_query_log`에 남긴다.
- **결과물:** 즉석 추론 함수(예: `infer(stack_code, item_code, change_pct=0)`), 결과 카드, **0% 검증 테스트**(다시 계산한 Feature = `online_features`의 같은 키 행, 예측 = Gold 값)
- **지키는 것:** Gold·`ops.warning_history`·Slack에 쓰지 않는다. 카드에 `[즉석 추론 · 판정 아님]`과 모델 버전을 표시한다.
- **고민할 점:** 0% 검증이 실패하면 무엇이 다른가(늦게 들어온 값, Feature 버전, 모델 파일)?

## Task 21. (Could) 입력값 변화 예측 비교

- **왜:** "얼마나 오르면 경고에 들어가나"를 보면 운영자가 남은 여유를 알 수 있고, 모델이 입력 변화에 어떻게 반응하는지 설명할 수 있다.
- **어떤 방식으로**
  1. 예측 비교 페이지에 측정값 변화율 슬라이더를 둔다(범위는 지난주 Task 16에서 정한 값, 예: −30%~+50%).
  2. Task 20의 3시간 창 복사본에서 **기준시각 행의 `measure_value`만** 바꾸고 Feature를 다시 계산한다. Feature 값을 직접 고치지 않는다.
  3. 변화 전후 진입 확률·예측 대비율과 차이를 보여 주고, 사전 경고 기준을 넘는지 표시한다.
  4. (선택) 몇 개 변화율(예: −10%·0%·+10%·+30%)을 차례로 추론해 변화율별 진입 확률 꺾은선을 그린다.
- **결과물:** 슬라이더, 변화 전후 비교 카드, 고정 사례 테스트(0% = Task 20 결과)
- **지키는 것:** 카드에 `[가정 시뮬레이션 · 판정 아님]`과 "측정값 ×1.2"처럼 실제 적용한 배수를 표시한다. 범위 밖은 추론하지 않는다.

## Task 22. (Could) 자연어 What-if

- **왜:** 슬라이더를 몰라도 "20% 오르면 경고 들어가?"라고 물으면 답할 수 있어야 한다.
- **어떤 방식으로**
  1. 규칙으로 질문에서 변화율과 방향을 뽑는다(예: "20% 오르면" → +20%, "절반으로 줄면" → −50%). "20%p"처럼 포인트 표현은 되묻는다.
  2. 뽑은 값을 Task 21과 같은 함수에 넣는다. LLM은 쓰지 않는다.
  3. 범위 밖이면 "모델이 학습하지 않은 범위"로 안내하고, "판정 저장해 줘"·"Slack으로 보내 줘"는 거절한다.
- **결과물:** 변화율 추출 규칙, 고정 사례 테스트(지난주 평가 질의)
