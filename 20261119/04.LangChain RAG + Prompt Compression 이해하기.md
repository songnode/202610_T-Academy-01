# LangChain RAG + Prompt Compression 이해하기

## 1. 전체 개념 이해하기

이번 실습의 주제는 **Prompt Compression(프롬프트 압축)**입니다.

RAG를 사용하면 질문과 관련된 여러 문서를 검색해 LLM에 전달합니다. 그런데 검색된 문서가 너무 많거나 길면 다음과 같은 문제가 발생할 수 있습니다.

- LLM에 전달되는 입력 토큰이 많아집니다.
- API 사용 비용이 증가할 수 있습니다.
- 응답 시간이 길어질 수 있습니다.
- 질문과 관련 없는 정보까지 전달되어 핵심 내용을 찾기 어려워질 수 있습니다.

이러한 문제를 해결하기 위해 필요한 정보는 유지하면서 불필요한 내용을 줄이는 것이 Prompt Compression입니다.

### 전체 처리 흐름

```text
사용자 질문
    ↓
RAG: 관련 문서 검색
    ↓
Prompt Compression: 불필요한 문서 내용 축소
    ↓
Prompt: 압축된 문서와 질문 구성
    ↓
LLM: 답변 생성
    ↓
Output: 최종 답변
```

이번 실습은 압축 방법을 난이도별로 비교합니다.

| 단계 | 압축 방법 | 핵심 내용 |
|---|---|---|
| Easy | 정적 압축 | Python으로 일정 분량만 잘라내기 |
| Medium | 동적 압축 | LLM을 이용해 핵심 내용 요약 |
| Hard | 조건부 압축 | 문서 길이에 따라 압축 여부 결정 |
| Hard 추가 | 구조화 출력 | Pydantic으로 JSON 결과 관리 |

## 2. Prompt Compression이란?

Prompt Compression은 LLM에 전달하는 문서, 검색 결과, 대화 이력 등의 컨텍스트에서 불필요한 내용을 줄이고 중요한 정보만 남기는 방법입니다.

예를 들어 다음과 같은 세 문서가 있다고 가정하겠습니다.

| 문서 | 주요 내용 |
|---|---|
| doc1 | AI 교육 플랫폼과 개인 맞춤형 학습 |
| doc2 | RAG 기술과 외부 지식 검색 |
| doc3 | Prompt Compression과 토큰 절감 |

사용자가 다음과 같이 질문합니다.

> 세 문서의 공통 주제는 무엇인가요?

이 질문에 답하려면 세 문서의 모든 문장을 전달할 필요는 없습니다.

각 문서의 핵심 내용만 남겨 전달해도 답변에 필요한 정보를 충분히 제공할 수 있습니다.

### Prompt Compression의 목적

1. 불필요한 입력 토큰을 줄입니다.
2. 질문과 관련된 핵심 정보에 집중합니다.
3. 입력 비용과 응답 시간을 줄일 가능성이 있습니다.
4. 긴 문서를 처리할 때 모델의 컨텍스트 한도를 효율적으로 활용합니다.

다만 압축한다고 항상 답변 품질이 좋아지는 것은 아닙니다. 중요한 정보까지 제거하면 오히려 답변의 정확도가 떨어질 수 있습니다.

따라서 압축률뿐 아니라 정보 보존율도 함께 고려해야 합니다.

## 3. 정적 압축과 동적 압축

이번 실습에서는 압축 방법을 크게 두 가지로 나누어 설명합니다.

### 3.1 정적 압축(Static Compression)

정적 압축은 미리 정해진 기준에 따라 텍스트를 잘라내는 방법입니다.

예를 들어 Python의 슬라이싱을 이용해 처음 200개 단어만 남길 수 있습니다.

```python
docs = "긴 문서 내용..."
compressed_docs = " ".join(docs.split()[:200])
```

이 코드는 다음과 같이 작동합니다.

1. 문서를 공백 기준으로 나눕니다.
2. 앞에서부터 200개 단어만 선택합니다.
3. 선택한 단어를 다시 하나의 문자열로 연결합니다.

**장점**
- 구현이 간단합니다.
- 별도의 LLM 호출이 필요하지 않습니다.
- 처리 속도가 빠릅니다.

**단점**
- 문서의 중요도를 이해하지 못합니다.
- 문서 뒷부분에 중요한 정보가 있어도 제거됩니다.
- 질문과 관계없는 앞부분만 남을 수 있습니다.

특히 200개 단어를 남긴다고 해서 200토큰이 되는 것은 아닙니다.

단어 수와 토큰 수는 서로 다른 개념입니다.

### 3.2 동적 압축(Dynamic Compression)

동적 압축은 LLM을 사용하여 문서의 의미를 파악하고 핵심 내용을 요약하는 방법입니다.

단순히 앞부분을 자르는 것이 아니라 문서의 내용을 이해한 뒤 중요한 정보만 남기는 방식입니다.

```text
원본 문서
    ↓
요약용 LLM
    ↓
핵심 내용 추출
    ↓
압축된 문서
```

예를 들어 다음과 같은 문서가 있다고 가정하겠습니다.

**원본 내용**

- AI 교육 플랫폼은 학습자의 성향과 학습 패턴을 분석합니다.
- 개인별 학습 경로를 추천합니다.
- 학습자의 오답 유형을 분석합니다.
- NLP 기술을 활용해 강의 콘텐츠를 요약합니다.
- AI 챗봇이 학습자의 질문에 답변합니다.

**압축 결과**

> AI 교육 플랫폼은 학습자의 학습 패턴과 오답을 분석해 개인 맞춤형 학습을 지원하며, NLP 기반 콘텐츠 요약과 AI 챗봇을 통해 학습 효율성을 높입니다.

이처럼 문장의 길이는 줄이면서 핵심 의미를 유지하는 것이 목적입니다.

**장점**
- 문서의 의미를 고려할 수 있습니다.
- 질문에 필요한 핵심 내용을 남길 수 있습니다.
- 불필요한 설명과 중복 내용을 줄일 수 있습니다.

**단점**
- 요약을 위해 LLM을 추가 호출해야 합니다.
- 요약 과정에서 중요한 세부 정보가 누락될 수 있습니다.
- 요약에 사용한 토큰 비용까지 고려해야 합니다.

따라서 동적 압축이 항상 비용을 절감하는 것은 아닙니다. 압축에 들어간 비용보다 이후 답변 생성에서 절약되는 비용이 큰지 확인해야 합니다.

## 4. 난이도 하: 기본 요약 압축

### 4.1 실습 목적

가장 간단한 정적 압축 방법을 이해하는 단계입니다.

기존 문서를 하나로 합친 후 일정한 단어 수만큼 잘라내고, LLM에 전달하여 공통 주제를 요약합니다.

### 4.2 처리 과정

```text
doc1 + doc2 + doc3
        ↓
하나의 문서로 결합
        ↓
앞부분 200단어 선택
        ↓
PromptTemplate 구성
        ↓
LLM에 전달
        ↓
공통 주제 요약
```

### 4.3 핵심 코드

```python
from langchain_core.prompts import PromptTemplate
from langchain_openai import ChatOpenAI

docs = "\n\n".join(retrieved_docs)

# 앞부분 200개 단어만 선택
compressed_docs = " ".join(docs.split()[:200])

prompt = PromptTemplate.from_template(
    """
    다음 문서를 읽고 질문에 답변하세요.

    문서:
    {docs}

    질문:
    {question}
    """
)

llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0
)

chain = prompt | llm

result = chain.invoke({
    "docs": compressed_docs,
    "question": "세 문서의 공통 주제는 무엇인가요?"
})

print(result.content)
```

### 4.4 이해해야 할 부분

| 코드 | 역할 |
|---|---|
| `join()` | 여러 문서를 하나로 결합 |
| `split()` | 문서를 공백 기준으로 분리 |
| `[:200]` | 앞부분 200개 단어 선택 |
| `PromptTemplate` | 문서와 질문을 프롬프트로 구성 |
| `ChatOpenAI` | LLM 호출 |
| `prompt \| llm` | 프롬프트와 모델을 하나의 체인으로 연결 |
| `invoke()` | 체인 실행 |

**멘티가 기억할 점**

이 단계는 문서의 의미를 이해해서 압축하는 것이 아닙니다.

단순히 정해진 길이만큼 잘라내는 방식입니다. 따라서 구현은 쉽지만 중요한 정보가 뒤쪽에 있다면 놓칠 수 있습니다.

## 5. 난이도 중: 요약 기반 동적 압축

### 5.1 실습 목적

이번 단계에서는 LLM을 활용하여 문서의 핵심 내용을 요약합니다.

정적 압축은 일정한 길이만큼 잘라내지만, 동적 압축은 LLM이 문서의 내용을 이해하고 요약한다는 차이가 있습니다.

### 5.2 처리 과정

```text
원본 문서
    ↓
요약용 Prompt
    ↓
요약용 LLM
    ↓
압축된 요약문
    ↓
질문용 Prompt
    ↓
답변 생성 LLM
    ↓
최종 답변
```

여기서는 LLM을 두 번 사용합니다.

- 첫 번째 LLM: 문서 요약
- 두 번째 LLM: 요약 내용을 참고하여 질문에 답변

### 5.3 핵심 코드

```python
from langchain_core.prompts import PromptTemplate
from langchain_openai import ChatOpenAI

docs = "\n\n".join(retrieved_docs)

# 실습 입력을 제한하기 위한 예시용 전처리
source_text = " ".join(docs.split()[:300])

# 1. 문서 요약
summary_prompt = PromptTemplate.from_template(
    """
    다음 문서의 핵심 내용을 간결하게 요약하세요.
    중요한 개념과 관계는 유지하세요.

    문서:
    {docs}
    """
)

summarizer = (
    summary_prompt
    | ChatOpenAI(
        model="gpt-4o-mini",
        temperature=0
    )
)

summary_message = summarizer.invoke({
    "docs": source_text
})

summary = summary_message.content

# 2. 요약 내용을 이용한 질의응답
qa_prompt = PromptTemplate.from_template(
    """
    다음 요약 내용을 참고하여 질문에 답변하세요.

    요약:
    {summary}

    질문:
    {question}
    """
)

qa_chain = (
    qa_prompt
    | ChatOpenAI(
        model="gpt-4o-mini",
        temperature=0
    )
)

result = qa_chain.invoke({
    "summary": summary,
    "question": "세 문서의 공통 주제는 무엇인가요?"
})

print(result.content)
```

### 5.4 이해해야 할 부분

이번 단계의 핵심은 두 개의 LLM 역할을 구분하는 것입니다.

| 구분 | 역할 |
|---|---|
| 요약용 LLM | 원본 문서에서 핵심 내용 추출 |
| 답변용 LLM | 요약된 내용을 참고해 질문에 답변 |

또한 기존 자료의 `100토큰 이내 요약`이라는 프롬프트는 실제 토큰 수를 강제로 제한하는 기능이 아닙니다.

LLM에게 100토큰 이내로 작성하도록 요청하는 지시문일 뿐입니다. 실제 출력 길이를 제한하려면 모델의 출력 토큰 설정과 토큰 수 확인이 별도로 필요합니다.

**멘티가 기억할 점**

동적 압축은 의미를 고려해 요약할 수 있다는 장점이 있지만, 요약 과정에서 중요한 정보가 빠질 수 있습니다.

특히 숫자, 날짜, 기준값, 조건 등은 요약 과정에서 누락되지 않도록 주의해야 합니다.

## 6. 난이도 상: 조건부 압축 및 구조화된 JSON 응답

### 6.1 실습 목적

이번 단계에서는 두 가지 기능을 결합합니다.

1. 문서 길이에 따라 압축 여부를 결정합니다.
2. LLM의 최종 응답을 정해진 JSON 구조로 반환합니다.

문서가 짧다면 굳이 요약하지 않고 원문을 사용하고, 문서가 길다면 요약을 수행합니다.

이것을 조건부 압축(Conditional Compression)이라고 합니다.

### 6.2 조건부 압축의 처리 과정

```text
원본 문서
    ↓
문서 길이 확인
    ↓
임계치보다 긴가?
    ├─ 아니오 → 원문 그대로 사용
    │
    └─ 예 → 요약용 LLM으로 압축
                  ↓
             압축된 문서
                  ↓
             질문과 함께 LLM 전달
                  ↓
             Pydantic 구조화 출력
                  ↓
             최종 JSON 결과
```

### 6.3 최신 방식으로 변경한 핵심 코드

기존 자료는 `Runnable`을 직접 상속해 압축기를 구현했습니다.

최신 LangChain에서는 일반 Python 함수를 `RunnableLambda`로 감싸면 LCEL 체인에 쉽게 연결할 수 있습니다.

```python
from langchain_core.prompts import PromptTemplate
from langchain_core.runnables import RunnableLambda
from langchain_openai import ChatOpenAI

from pydantic import BaseModel, Field

# 1. LLM 준비
llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0
)

# 2. 요약용 체인
summary_prompt = PromptTemplate.from_template(
    """
    다음 문서의 핵심 내용을 요약하세요.
    중요한 개념과 정보는 유지하세요.

    문서:
    {docs}
    """
)

summarizer = summary_prompt | llm

# 3. 조건부 압축 함수
def conditional_compress(inputs):
    docs = inputs["docs"]
    threshold = 300

    words = docs.split()

    # 문서가 짧으면 원문 그대로 사용
    if len(words) <= threshold:
        return docs

    # 문서가 길면 요약 수행
    summary = summarizer.invoke({
        "docs": docs
    })

    return summary.content

# 4. Python 함수를 Runnable로 변환
compressor = RunnableLambda(conditional_compress)

# 5. 문서 압축
docs = "\n\n".join(retrieved_docs)

compressed_docs = compressor.invoke({
    "docs": docs
})

print(compressed_docs)
```

이 코드에서는 문서 전체를 요약용 LLM에 전달합니다.

기존 코드처럼 앞부분 300단어만 잘라서 요약하지 않으므로, 문서 뒷부분의 내용이 사전에 제거되는 문제를 줄일 수 있습니다.

다만 입력 문서가 모델의 컨텍스트 한도를 초과한다면 문서 분할이나 단계별 요약이 추가로 필요합니다.

### 6.4 Pydantic을 이용한 JSON 구조화 출력

기존 자료에서는 정규표현식으로 LLM의 응답에서 JSON 문자열을 추출했습니다.

하지만 최신 LangChain에서는 `with_structured_output()`을 활용하여 결과 구조를 미리 정의하는 방법을 사용할 수 있습니다.

먼저 결과 구조를 정의합니다.

```python
class AnswerSchema(BaseModel):
    answer: str = Field(
        description="질문에 대한 최종 답변"
    )
```

이제 모델에 해당 구조를 적용합니다.

```python
structured_llm = llm.with_structured_output(
    AnswerSchema
)
```

질문과 문서를 전달합니다.

```python
qa_prompt = PromptTemplate.from_template(
    """
    다음 문서를 참고하여 질문에 답변하세요.

    문서:
    {docs}

    질문:
    {question}

    문서에 근거가 없는 내용은 추측하지 마세요.
    """
)

qa_chain = qa_prompt | structured_llm

result = qa_chain.invoke({
    "docs": compressed_docs,
    "question": "세 문서의 공통 주제는 무엇인가요?"
})

print(result.answer)
```

### 6.5 구조화 출력의 장점

| 기존 방식 | 최신 권장 방식 |
|---|---|
| 정규표현식으로 JSON 추출 | Pydantic으로 결과 구조 정의 |
| 문자열에서 JSON 영역 검색 | 모델이 정해진 스키마에 맞춰 출력 |
| JSON 파싱 오류 별도 처리 | 구조화 출력 과정에서 검증 |
| 필드 누락 여부를 별도로 확인 | 스키마를 기준으로 관리 |

단, Pydantic으로 구조를 검증했다고 해서 답변 내용까지 사실이라는 의미는 아닙니다.

JSON 구조의 유효성과 답변의 사실 정확성은 별도로 검증해야 합니다.

---

## 7. 이번 실습에서 주의해야 할 기술적 사항

### 7.1 단어 수와 토큰 수는 다릅니다.

기존 코드의 다음 부분을 살펴보겠습니다.

```python
docs.split()[:300]
```

이 코드는 300개 단어를 선택하는 것이지, 300토큰을 선택하는 것이 아닙니다.

토큰은 모델이 텍스트를 처리하는 단위이며 단어와 일치하지 않습니다.

실제 서비스에서는 모델에 맞는 토크나이저를 이용해 토큰 수를 확인하는 것이 좋습니다.

### 7.2 문서 앞부분만 자르면 중요한 정보가 사라질 수 있습니다.

기존 실습은 세 문서를 합친 후 앞부분 200개 또는 300개 단어만 선택합니다.

이 경우 doc1의 일부만 남고 doc2와 doc3의 핵심 내용은 제거될 수 있습니다.

실제 RAG에서는 다음 방법을 고려하는 것이 좋습니다.

- 문서별로 압축한 뒤 다시 결합
- 질문과 관련된 문장만 추출
- 중요한 숫자와 조건은 별도로 보존
- 긴 문서는 일정 크기로 분할한 뒤 단계적으로 요약

### 7.3 요약은 정보 손실을 발생시킬 수 있습니다.

요약은 문서의 모든 내용을 보존하는 작업이 아닙니다.

따라서 다음과 같은 정보는 특별히 주의해야 합니다.

- 수치와 단위
- 날짜와 기간
- 업무 조건과 예외 사항
- 원인과 결과의 관계
- 부정 표현과 제한 조건

특히 업무용 RAG에서는 중요한 기준값이 요약 과정에서 사라지지 않도록 설계해야 합니다.

### 7.4 압축 비용도 함께 계산해야 합니다.

동적 압축은 요약용 LLM을 추가로 호출합니다.

따라서 실제 비용은 다음과 같이 계산해야 합니다.

```text
전체 비용
=
요약용 LLM 입력 비용
+ 요약용 LLM 출력 비용
+ 최종 답변용 LLM 입력 비용
+ 최종 답변용 LLM 출력 비용
```

압축으로 줄어든 토큰 비용이 요약에 추가로 사용한 비용보다 큰지 비교해야 합니다.

## 8. 실무에서 한 단계 더 발전시키기

실제 RAG 시스템에서는 단순히 문서를 짧게 만드는 것보다 질문에 필요한 정보를 정확히 남기는 것이 중요합니다.

따라서 다음과 같은 발전 방향을 고려할 수 있습니다.

| 기법 | 설명 | 활용 목적 |
|---|---|---|
| Truncation | 일정 길이만큼 자르기 | 간단한 입력 길이 제한 |
| Summarization | LLM으로 요약 | 문서 핵심 내용 유지 |
| Query-aware Compression | 질문과 관련된 내용만 추출 | 질문에 필요한 정보 집중 |
| Document Filtering | 관련성이 낮은 문서 제거 | 불필요한 문서 감소 |
| Reranking | 검색 문서의 관련도 재정렬 | 중요한 문서를 우선 전달 |

특히 Query-aware Compression은 사용자의 질문을 기준으로 문서에서 필요한 부분만 추출한다는 점에서 실무적으로 중요합니다.

예를 들어 다음과 같은 질문이 있다고 가정하겠습니다.

> AI 교육 플랫폼에서 개인 맞춤형 학습은 어떻게 구현되나요?

이 경우 RAG가 검색한 문서 중에서 다음 내용만 남길 수 있습니다.

- 학습자의 풀이 시간 분석
- 오답 유형 분석
- 학습 난이도 조절
- 개인별 학습 경로 추천

RAG가 검색한 문서 전체를 요약하는 것보다 질문에 필요한 정보에 집중할 수 있습니다.

LangChain에는 검색 결과를 압축하는 `ContextualCompressionRetriever`도 제공됩니다. 이 기능은 기본 Retriever와 문서 압축기를 결합하는 방식으로 사용할 수 있습니다.

## 9. 멘티가 반드시 이해해야 할 핵심

이번 실습의 내용을 네 가지로 정리하면 됩니다.

| 구분 | 핵심 질문 | 답변 |
|---|---|---|
| 정적 압축 | 어떻게 간단히 줄일까? | 일정한 길이만큼 잘라내기 |
| 동적 압축 | 어떻게 의미를 유지하면서 줄일까? | LLM으로 요약하기 |
| 조건부 압축 | 언제 압축할까? | 문서 길이에 따라 결정 |
| 구조화 출력 | 결과를 어떻게 관리할까? | Pydantic 스키마로 검증 |

### 최종 정리

Prompt Compression은 단순히 문장을 짧게 만드는 기술이 아닙니다.

**질문에 필요한 정보는 최대한 유지하면서 불필요한 입력을 줄이는 기술**입니다.

실제 RAG 서비스를 개발할 때는 다음 원칙을 기억해야 합니다.

1. 무조건 압축하지 말고 문서 길이와 필요성을 먼저 확인합니다.
2. 단순 슬라이싱보다 질문과 관련된 정보를 보존하는 방법을 우선 고려합니다.
3. 요약 과정에서 중요한 수치와 조건이 누락되지 않도록 합니다.
4. 압축 전후의 토큰 수와 비용을 비교합니다.
5. 최종 답변은 검색된 원본 근거와 비교해 정확성을 검증합니다.

결국 좋은 압축은 문서를 가장 짧게 만드는 것이 아니라, **답변에 필요한 정보를 잃지 않으면서 효율적으로 전달하는 것**입니다.
