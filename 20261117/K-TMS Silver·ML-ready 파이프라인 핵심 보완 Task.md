# K-TMS Silver·ML-ready 파이프라인

- 검토일: 2026-11-17

## 1. 한 줄 결론

구조는 그대로 둔다. 보완할 것은 하나다.

> **잡은 성공했는데 데이터가 틀린 상황을 알아차리고, 틀린 결과가 정상 데이터를 덮어쓰지 못하게 한다.**

지금 파이프라인은 잡이 **실패했을 때만** 메일을 보낸다. 그래서 아래 같은 일은 아무도 모른 채 지나간다.

| 이런 일이 생기면 | 지금은 | 보완 후 |
|---|---|---|
| 수집 Lambda가 새벽에 2시간 멈췄다 | Silver 잡은 있는 데이터로 계산하고 "성공" | 수집 공백 알림 (T1) |
| 중복 행이 섞인 결과가 나왔다 | 그대로 커밋되어 어제의 정상 데이터를 대체 | 커밋 전에 막힘, 테이블은 어제 상태 유지 (T2) |
| 11-10 하루만 다시 계산했다 | 11-11 새벽의 Feature는 옛 값으로 남음 | 앞뒤 날짜까지 함께 다시 계산 (T3) |
| 한 달 뒤 "그때 학습한 데이터"를 다시 읽고 싶다 | 어떤 버전인지 기록이 없음 | `train_meta.json`으로 그대로 재현 (T4) |

## 3. 핵심 보완 Task

### T1. 수집 누락과 배치 미실행 감지

**왜 중요한가**

API는 지금 시점의 값만 준다. 수집이 멈춘 동안의 데이터는 나중에 다시 받을 수 없다. 그래서 빨리 알아야 한다.

**할 일**

1. 날짜별로 10분 슬롯 144개 중 몇 개가 실제로 수집됐는지 센다. 같은 슬롯이 두 번 수집되면 하나로 센다.
2. 가장 긴 수집 공백(분)을 실행 기록 JSON에 남긴다.
3. 공백이 30분을 넘으면 경고 메일을 보낸다.
4. 03:00 배치는 따로 감시한다. 정해진 시각까지 성공 기록이 없으면 알림을 보낸다. 배치가 아예 안 돌면 배치 안에서는 알릴 수 없기 때문이다.

**됐다는 기준**

- 수집을 1시간 멈추면 수집 누락 알림이 온다.
- Scheduler를 끄면 배치 미실행 알림이 온다.
- 두 알림이 서로 구분된다.

### T2. 커밋 전 품질 검사

**왜 중요한가**

Iceberg는 커밋하는 순간 그 결과가 "현재 테이블"이 된다. 틀린 결과도 마찬가지다. 검사는 커밋 **전에** 해야 의미가 있다.

**할 일**

계산이 끝나고 Iceberg에 쓰기 전에 검사한다.

| 대상 | 검사 | 결과 |
|---|---|---|
| Silver | 키(지역, 사업장, 굴뚝, 측정 시각, 항목) 중복 | 있으면 FAIL |
| Silver | 날짜별 행 수, 사업장·굴뚝 수가 평소보다 크게 줄었는지 | WARN |
| Silver | `status = other`(처음 보는 문구), 음수 측정값 | WARN |
| ML-ready | 키(`stack_code`, `item_code`, `measured_at`) 중복 | 있으면 FAIL |
| ML-ready | 학습 가능 행 수, 양성 행 수의 큰 변화 | WARN |
| ML-ready | `data_source`가 기대한 값(`ktms`)이 아님 | FAIL |

- **FAIL:** 커밋하지 않고 잡을 실패시킨다. 테이블은 어제 상태 그대로다.
- **WARN:** 커밋하고, 실행 기록 JSON과 메일에 사유를 남긴다.
- "크게 줄었다"의 기준은 지금까지 쌓인 날짜별 분포를 보고 정한다.

**됐다는 기준**

- 중복 행을 일부러 넣고 돌리면 커밋되지 않고, `snapshot_id`가 실행 전과 같다.
- 검사 결과와 FAIL·WARN 사유가 실행 기록 JSON에 남는다.

### T3. 재실행 시 ML-ready 범위를 앞뒤로 넓히기

**왜 중요한가**

ML-ready의 한 행은 혼자 계산되지 않는다. 과거 150분 값으로 Feature를, 미래 60분 값으로 Label을 만든다. 그래서 Silver 값 하나가 바뀌면 그 앞뒤 행도 바뀌어야 한다.

```text
                바뀐 Silver 값 (시각 t)
                         │
   t-60 ─────────────── t ─────────────────────────── t+150
   └─ 이 행들의 Label ─┘  └─ 이 행들의 Feature(lag·3시간 통계) ─┘
```

- 3시간 이동 통계는 30분 칸 6개(t-150 ~ t)라서, Feature가 보는 과거 범위는 150분이다.
- 매일 실행은 날짜가 이어져 있어서 문제가 없다. 문제는 `rerun --from X --to X`로 **특정 날짜만** 다시 돌릴 때다.

**할 일**

1. X일을 재실행하면 ML-ready 쓰기 범위를 X-1일 ~ X+1일로 넓힌다. 분 단위로 자르는 것보다 단순하고, 날짜 파티션 단위 교체와도 맞는다.
2. 넓힌 범위를 계산할 수 있도록 Silver 읽기 범위도 앞뒤로 넓힌다.

**됐다는 기준**

X일 Silver 값을 하나 바꾸고 재실행하면 다음이 새 값으로 바뀐다.

- X-1일 23:00 ~ 23:30 행의 Label
- X+1일 00:00 ~ 02:30 행의 Feature

### T4. 학습 데이터 버전 기록

**왜 중요한가**

Iceberg를 쓴 가장 큰 이유가 "학습 당시 데이터를 다시 읽는 것"이다. 그런데 어떤 버전을 썼는지 적어 두지 않으면 이 기능을 쓸 수 없다. 테이블은 매일 바뀐다.

**할 일**

학습할 때마다 모델 파일 옆에 `train_meta.json`을 남긴다.

| 구분 | 기록 항목 |
|---|---|
| 데이터 버전 | 테이블 이름, `snapshot_id` |
| 데이터 범위 | cutoff(D-2 기준 시각), 학습 시작일·종료일 |
| 데이터 구성 | 국내 실측, 대만, 합성 각각의 행 수 |
| 분할 | Train·Validation·Test 기간 |
| 규칙 버전 | `feature_version`, `label_version`, `quality_policy_version` |
| 코드·설정 | Git commit, 알고리즘, 주요 하이퍼파라미터, seed |

- **대만 데이터는 따로 챙긴다.** 대만 ML-ready는 Iceberg가 아닌 일반 Parquet이라 `snapshot_id`가 없다. 파일 목록과 체크섬을 함께 남긴다. 국내와 대만을 합쳐 학습(B+T)하기로 했으므로 이 기록이 빠지면 재현이 안 된다.
- 이 규칙이 자리 잡기 전에는 스냅샷 만료(옛 버전 삭제)를 실행하지 않는다. 지우면 되돌릴 수 없다.

**됐다는 기준**

기록한 `snapshot_id`와 cutoff로 다시 읽은 행 수·양성 수가, 매일 실행 3번이 지난 뒤에도 처음과 같다.

## 4. 함께 확인할 것

구현이 아니라 한 번 확인하고 문서에 적으면 되는 항목이다.

| 번호 | 확인할 것 | 왜 |
|---|---|---|
| C1 | 정기 실행 중에 같은 범위로 `rerun`을 걸면 실제로 어떻게 되는가 (대기, 거부, 재시도) | Glue 동시 실행 수 1이 "기다렸다가 성공"을 보장하지는 않는다. `rerun`·`backfill`이 같은 상태 머신을 거치는지도 확인한다 |
| C2 | Silver는 성공하고 ML-ready가 실패하면 다음 날 실행으로 저절로 맞춰지는가 | 그 사이 두 테이블의 기준 날짜가 다르다. 학습은 두 테이블의 처리 날짜가 같을 때만 시작한다 |
| C3 | `ts_kst`, `measured_at`의 시간대와 `days()` 파티션 날짜가 KST 날짜와 같은가 | 시간대가 붙은 타입이면 파티션이 UTC 날짜로 잘려 "하루 단위 교체"가 어긋난다 |
| C4 | `stack_code`가 Silver에서는 굴뚝 번호, ML-ready에서는 `지역\|사업장\|굴뚝번호`다 | 이름은 같은데 뜻이 달라 조인할 때 실수하기 쉽다 |

## 6. 멘토링 때 던질 질문

1. 어젯밤 수집이 2시간 멈췄다면, 우리는 언제 어떻게 알게 되나요? (T1)
2. 오늘 결과에 중복 행이 섞였다면, 그 결과는 어제의 정상 데이터를 덮어쓰나요? (T2)
3. 11-10 하루만 다시 계산하면 11-11 00:30 행의 Feature는 어떤 값인가요? (T3)
4. 한 달 뒤 "11/18에 학습한 모델이 본 데이터"를 똑같이 다시 읽을 수 있나요? 대만 데이터도요? (T4)
