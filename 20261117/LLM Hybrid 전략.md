
# LLM Hybrid 전략: 질문마다 알맞은 모델을 선택하는 방법

## 1. LLM Hybrid 전략이란?

### 한 줄 요약

> **모든 질문을 가장 비싼 모델 하나에 보내지 않는다. 질문의 특성과 보안 수준을 먼저 판단해 어디서, 어떤 모델로 처리하고, 기존 답변을 재사용할 수 있는지 결정하는 전략이다.**

LLM 하나로 모든 질문을 처리하면 구현은 간단하지만, 실제 서비스에서는 다음과 같은 문제가 발생할 수 있다.

| 문제 | 예시 | 발생할 수 있는 문제 |
|---|---|---|
| 개인정보 유출 | 고객 이름, 계좌번호가 포함된 질문 | 민감한 정보가 외부 API로 전송될 수 있음 |
| 불필요한 비용 | "Python이 뭐야?" | 간단한 질문에도 고성능 모델의 비용 발생 |
| 반복 호출 | 어제 했던 질문을 다시 입력 | 같은 질문에 API 비용과 응답 시간 재발생 |

LLM Hybrid 전략은 질문을 처리하기 전에 세 가지를 판단하여 이러한 문제를 줄인다.

| 구성 요소 | 해결하려는 문제 | 핵심 역할 |
|---|---|---|
| ① Provider 선택 | 개인정보 보호 | 외부 API 또는 내부 로컬 모델 중 처리 위치 결정 |
| ② Model Tiering | 모델 사용 비용 | 질문 난이도에 따라 작은 모델 또는 큰 모델 선택 |
| ③ Cache | 반복 호출 비용과 응답 시간 | 이전에 처리한 질문의 결과를 재사용 |

여기서 Provider는 모델을 제공하거나 실행하는 환경을 의미한다.

- 외부 Provider: OpenAI API 등 외부에서 제공하는 LLM 서비스
- 로컬 Provider: 회사 내부 서버에서 실행하는 Ollama 등의 모델 환경

**중요한 점은 세 가지 기술을 단순히 사용하는 것이 아니라, 질문의 특성에 맞게 조합하는 것이다.**

## 2. 전체 처리 흐름

LLM Hybrid 전략은 다음과 같은 순서로 구성할 수 있다.

```text
                  사용자 질문
                       │
                       ▼
             ① 개인정보(PII) 검사
                       │
              ┌────────┴────────┐
              │                 │
          개인정보 있음      개인정보 없음
              │                 │
              ▼                 ▼
       로컬 Provider 사용    ③ Cache 조회
              │                 │
              │           ┌─────┴─────┐
              │           │           │
              │         Cache Hit  Cache Miss
              │           │           │
              │           ▼           ▼
              │        저장된 답변   ② 질문 난이도 판단
              │           │           │
              │           │      ┌────┴────┐
              │           │      │         │
              │           │     쉬움      어려움
              │           │      │         │
              │           │      ▼         ▼
              │           │    작은 모델  큰 모델
              │           │      │         │
              │           │      └────┬────┘
              │           │           │
              │           │           ▼
              │           │        답변 생성
              │           │           │
              │           │           ▼
              │           │       Cache 저장
              │           │           │
              └───────────┴───────────┘
                          │
                          ▼
                       사용자 응답
```

### 왜 이 순서로 처리할까?

**개인정보 검사가 가장 먼저 이루어져야 한다.**

개인정보가 포함된 질문을 캐시에서 먼저 검색하거나 저장하면 다음과 같은 문제가 발생할 수 있다.

1. 개인정보가 포함된 질문이 캐시 저장소에 남을 수 있다.
2. 다른 사용자가 비슷한 질문을 했을 때 개인정보가 포함된 답변이 반환될 수 있다.
3. 개인정보가 포함된 질문이 외부 LLM API로 전달될 가능성이 생긴다.

따라서 개인정보가 포함된 질문은 캐시 조회와 저장을 모두 건너뛰고, 허용된 내부 처리 경로로 보내는 것이 안전하다.

단, 로컬 모델을 사용한다고 해서 자동으로 개인정보가 보호되는 것은 아니다. 모델 서버의 접근 권한, 로그, 저장소, 네트워크 정책도 함께 관리해야 한다.

## 3. ① Provider 선택: 개인정보는 외부로 보내지 않는다

### 3.1 개념

질문에 개인정보(PII, Personally Identifiable Information)가 포함되어 있는지 확인하고, 결과에 따라 처리 위치를 결정한다.

- 개인정보가 포함된 질문: 내부 로컬 모델로 처리
- 개인정보가 없는 질문: 외부 API 또는 내부 모델 중 적절한 경로 선택

예를 들어 Ollama를 이용하면 회사 내부 서버에서 LLM을 실행할 수 있다.

| 사용자 질문 | 개인정보 포함 여부 | 처리 경로 |
|---|---|---|
| 홍길동(45세) 고객의 상담 이력을 요약해 줘 | 이름, 나이 등 | 로컬 모델 |
| 계좌번호 110-123-456789의 거래 내역을 분석해 줘 | 계좌번호 | 로컬 모델 |
| Python이 무엇인지 설명해 줘 | 없음 | 외부 API 또는 로컬 모델 |
| 최근 LLM 기술 동향을 정리해 줘 | 일반 정보 | 외부 API 또는 로컬 모델 |

### 3.2 개인정보 감지 방법

개인정보를 감지하는 방법은 여러 가지가 있다.

| 방법 | 설명 | 특징 |
|---|---|---|
| 정규식(Regex) | 전화번호, 이메일, 계좌번호 등의 패턴 검사 | 구현이 간단하지만 이름 등은 탐지하기 어려움 |
| NER | 문장에서 사람 이름, 기관명, 위치 등 개체 탐지 | 문맥을 활용할 수 있지만 오탐과 누락 가능 |
| 개인정보 탐지 모델 | 개인정보 탐지에 특화된 모델 사용 | 다양한 패턴을 처리할 수 있지만 별도 검증 필요 |

실제 서비스에서는 하나의 방법에만 의존하기보다 정규식과 NER 등을 조합하는 것이 좋다.

### 3.3 조심해야 할 점

| 항목 | 고려 사항 |
|---|---|
| 개인정보 감지 정확도 | 이름이나 문맥에 포함된 개인정보를 놓칠 수 있다. 애매한 경우에는 보수적으로 내부 처리 경로를 선택한다. |
| 로컬 모델 품질 | 작은 로컬 모델은 외부 고성능 모델보다 복잡한 질문에 대한 답변 품질이 낮을 수 있다. |
| 로컬 모델 장애 | 개인정보가 포함된 질문은 로컬 모델이 실패하더라도 외부 API로 자동 전환하면 안 된다. |
| 데이터 보호 | 로컬 모델을 사용하더라도 로그, 접근 권한, 저장 데이터에 대한 보안 관리가 필요하다. |

**가장 중요한 원칙**

> 개인정보가 포함된 질문은 로컬 모델이 실패하더라도 외부 API로 보내지 않는다.

실패하면 다음과 같은 방법을 선택한다.

1. 다른 내부 로컬 모델로 재시도한다.
2. 개인정보를 안전하게 마스킹한 후 외부 전송이 허용되는지 정책을 확인한다.
3. 처리가 불가능하면 사용자에게 안내한다.

반대로 개인정보가 없는 질문은 외부 API가 실패했을 때 내부 모델로 전환할 수 있다. 단, 회사의 데이터 처리 정책에서 허용하는 경우에 한한다.

## 4. ② Model Tiering: 질문 난이도에 맞는 모델을 선택한다

### 4.1 개념

모든 질문에 동일한 모델을 사용할 필요는 없다.

간단한 질문은 작은 모델로 처리하고, 복잡한 추론이나 분석이 필요한 질문은 큰 모델로 처리한다.

이처럼 질문의 난이도에 따라 모델을 선택하는 방식을 Model Tiering이라고 한다.

| 모델 구분 | 특징 | 적합한 질문 |
|---|---|---|
| Small Model | 상대적으로 빠르고 비용이 낮음 | 간단한 설명, 요약, 분류, 단순 질의 |
| Large Model | 복잡한 추론과 분석에 적합 | 다단계 분석, 비교, 코드 검토, 복합적인 추천 |

예를 들어 다음과 같이 구분할 수 있다.

| 질문 | 난이도 | 모델 선택 |
|---|---|---|
| Python이 무엇인가? | 낮음 | 작은 모델 |
| Kafka와 RabbitMQ의 차이는? | 중간 | 작은 모델 또는 큰 모델 |
| 여러 조건을 고려해 데이터 아키텍처를 설계해 줘 | 높음 | 큰 모델 |
| 이 코드의 오류 원인을 분석하고 개선안을 제시해 줘 | 높음 | 큰 모델 |

### 4.2 난이도 판단 기준

질문 난이도를 판단할 때 다음과 같은 요소를 활용할 수 있다.

| 판단 요소 | 난이도가 높아지는 신호 |
|---|---|
| 질문 길이 | 여러 조건과 요구사항이 포함됨 |
| 전문성 | 반도체 공정, 법률, 의료 등 전문 용어가 많음 |
| 코드 및 수식 | 코드 분석, 디버깅, 수학적 계산이 필요함 |
| 추론 단계 | 여러 정보를 비교하고 결론을 도출해야 함 |
| 요구 작업 | 단순 설명이 아닌 설계, 평가, 추천 등이 필요함 |

간단한 예시로 질문 난이도를 점수화할 수도 있다.

```text
질문 난이도 점수 = 각 판단 요소의 가중치 합계

0 ~ 39점  → Small Model
40 ~ 100점 → Large Model
```

위 점수는 이해를 돕기 위한 예시이며, 실제 서비스에서는 질문 데이터와 모델별 성능을 측정해 기준값을 정해야 한다.

### 4.3 왜 효과가 있을까?

모든 질문을 큰 모델에 보내면 불필요한 비용이 발생한다.

실제 서비스에서는 단순 조회나 짧은 설명처럼 작은 모델로 충분히 처리할 수 있는 질문도 많다.

이러한 질문을 작은 모델로 보내면 전체 LLM 호출 비용을 줄일 수 있다.

다만 모델별 비용 차이는 모델 종류, 입력·출력 토큰 수, 제공 업체의 가격 정책에 따라 달라진다. 실제 적용 전에는 공식 가격표를 확인해야 한다.

### 4.4 조심해야 할 점

| 항목 | 고려 사항 |
|---|---|
| 잘못된 난이도 판단 | 질문이 짧더라도 어려울 수 있다. 예를 들어 "P=NP인가?"는 짧지만 복잡한 질문이다. |
| 모델 품질 차이 | 작은 모델은 응답이 빠르고 저렴하지만 복잡한 질문에서 정확도가 떨어질 수 있다. |
| 기준값 설정 | 처음 설정한 40점 같은 기준은 실제 질문 기록을 바탕으로 조정해야 한다. |
| 모델 선택 실패 | 작은 모델이 답변하기 어려운 질문이라면 큰 모델로 재요청하는 전략도 고려할 수 있다. |

### 4.5 한 단계 더 나아가기: 답변 품질 기반 재시도

질문 난이도만으로 모델을 선택하는 방법 외에, 작은 모델의 답변 품질을 확인한 뒤 큰 모델로 넘기는 방법도 있다.

```text
사용자 질문
     │
     ▼
 작은 모델 호출
     │
     ▼
 답변 품질 확인
     │
 ┌───┴────┐
 │        │
충분함   부족함
 │        │
 ▼        ▼
응답     큰 모델 재호출
```

이 방식을 사용하면 처음부터 모든 질문을 큰 모델로 보내지 않으면서도 답변 품질을 보완할 수 있다.

단, 답변 품질을 판단하는 기준도 필요하다. 예를 들어 필수 항목 누락, 근거 부족, 형식 오류, 신뢰도 부족 등을 검사할 수 있다.

## 5. ③ Cache: 같은 질문은 다시 처리하지 않는다

### 5.1 개념

사용자가 이전에 했던 질문과 같거나 충분히 유사한 질문을 다시 입력하면 LLM을 다시 호출하지 않고 저장된 답변을 반환하는 방식이다.

캐시를 사용하면 다음과 같은 효과가 있다.

- LLM API 호출 횟수 감소
- 응답 시간 단축
- 반복 질문에 대한 비용 절감

### 5.2 캐시 처리 방법

캐시는 크게 정확 매칭과 의미 매칭으로 나눌 수 있다.

| 구분 | 정확 매칭(Exact Match) | 의미 매칭(Semantic Match) |
|---|---|---|
| 처리 방식 | 질문을 정규화한 후 해시값으로 검색 | 질문을 임베딩 벡터로 변환해 유사도 검색 |
| 비교 기준 | 문자열이 동일한가? | 질문의 의미가 유사한가? |
| 예시 | "Python이란?"과 동일한 질문 | "Python이란?"과 "Python이 뭐야?" |
| 장점 | 빠르고 결과가 명확함 | 표현이 달라도 기존 답변 활용 가능 |
| 단점 | 표현이 조금만 달라도 매칭되지 않음 | 의미가 다른 질문을 잘못 매칭할 수 있음 |

### 5.3 캐시 동작 흐름

```text
사용자 질문
     │
     ▼
질문 정규화
(공백, 대소문자 등)
     │
     ▼
정확 매칭 검색
     │
 ┌───┴────┐
 │        │
Hit      Miss
 │        │
 ▼        ▼
답변 반환  의미 매칭 검색
             │
         ┌───┴────┐
         │        │
       유사함    유사하지 않음
         │        │
         ▼        ▼
      답변 반환  LLM 호출
                    │
                    ▼
                 답변 생성
                    │
                    ▼
                 캐시 저장
```

실제 구현에서는 정확 매칭을 먼저 확인하고, 정확히 일치하는 결과가 없을 때 의미 매칭을 수행할 수 있다.

### 5.4 의미 매칭의 유사도 기준

의미 매칭에서는 임베딩 벡터 간 코사인 유사도(Cosine Similarity)를 사용할 수 있다.

예를 들어 유사도 기준을 0.95로 설정했다고 가정해 보자.

| 질문 A | 질문 B | 유사도 예시 | 판단 |
|---|---|---:|---|
| Python이란? | Python이 뭐야? | 0.97 | 의미가 유사할 가능성이 높음 |
| Python이란? | Java란? | 0.78 | 다른 질문일 가능성이 높음 |
| NOx 기준치는? | SOx 기준치는? | 0.96 | 유사도는 높아도 답변은 다를 수 있음 |

여기서 반드시 알아야 할 점이 있다.

> **유사도 0.95는 답변의 정확도가 95%라는 의미가 아니다. 두 문장의 임베딩 벡터가 얼마나 가까운지를 나타내는 값이다.**

따라서 0.95라는 기준을 모든 서비스에 동일하게 적용하면 안 된다. 실제 질문과 정답을 가지고 오매칭 사례를 확인하면서 조정해야 한다.

### 5.5 캐시 사용 시 주의할 점

| 문제 | 설명 | 대응 방법 |
|---|---|---|
| 잘못된 의미 매칭 | 질문은 비슷하지만 답이 다른 경우 | 핵심 대상, 숫자, 조건 등을 추가 비교 |
| 오래된 답변 | 과거 답변이 현재 상황과 맞지 않는 경우 | TTL 설정 및 데이터 변경 시 캐시 무효화 |
| 개인정보 노출 | 개인정보가 포함된 질문이나 답변이 캐시에 저장되는 경우 | 개인정보 질문은 조회와 저장 모두 제외 |
| 사용자 간 정보 공유 | 다른 사용자의 답변이 반환되는 경우 | 사용자 권한, 조직, 데이터 접근 범위를 캐시 키에 반영 |
| 저장 공간 증가 | 질문과 임베딩 데이터가 누적되는 경우 | TTL, 용량 제한, 주기적인 정리 |

### 5.6 TTL(Time To Live)이란?

TTL은 캐시에 저장된 데이터가 유효한 시간을 의미한다.

예를 들어 1주일로 설정하면 캐시에 저장된 답변을 7일 동안 재사용하고 이후에는 다시 생성하도록 할 수 있다.

하지만 모든 질문에 동일한 TTL을 적용하는 것은 적절하지 않다.

| 질문 유형 | 캐시 정책 |
|---|---|
| Python이란? | 비교적 긴 TTL 가능 |
| 회사의 업무 규정은? | 문서 변경 시 캐시 무효화 |
| 오늘의 배출량은? | 캐시하지 않거나 매우 짧은 TTL |
| 현재 경고 중인 굴뚝은? | 캐시하지 않거나 데이터 기준 시각을 포함 |
| 특정 굴뚝의 과거 분석 결과는? | 조회 조건과 데이터 버전을 포함해 캐시 가능 |

**핵심은 답변이 시간이나 데이터 변경에 영향을 받는 질문인지 먼저 판단하는 것이다.**

## 6. 세 가지 전략을 함께 사용하면?

세 가지 전략은 각각 독립적으로 동작하는 것이 아니라 하나의 질문 처리 과정에서 함께 사용된다.

| 단계 | 판단 내용 | 처리 결과 |
|---|---|---|
| ① Provider 선택 | 개인정보가 포함되어 있는가? | 로컬 또는 외부 처리 경로 결정 |
| ② Cache | 이전에 처리한 질문인가? | 기존 답변 재사용 여부 결정 |
| ③ Model Tiering | 질문 난이도는 어느 정도인가? | 작은 모델 또는 큰 모델 선택 |
| ④ 답변 생성 | 선택된 모델이 답변 생성 | 사용자에게 응답 |
| ⑤ Cache 저장 | 재사용할 수 있는 답변인가? | 조건에 따라 캐시 저장 |

여기서 ① Provider 선택은 보안 정책에 해당하므로 가장 먼저 수행한다.

Cache와 Model Tiering의 순서는 설계에 따라 달라질 수 있지만, 캐시 적중 시 모델을 다시 호출하지 않는 구조라면 일반적으로 Cache를 먼저 확인하는 것이 효율적이다.

## 7. 실무 적용 사례

| 서비스 | 적용 방식 | 기대 효과 |
|---|---|---|
| 고객 상담봇 | 개인정보 감지 후 로컬 모델 처리, FAQ는 캐시 활용 | 개인정보 보호 및 반복 비용 절감 |
| 사내 업무 도구 | Provider 선택, Model Tiering, Cache 모두 적용 | 보안과 비용 효율성 확보 |
| 의료·금융 시스템 | 민감 정보 처리 경로를 내부로 제한하고 접근 권한 관리 | 민감 데이터 외부 전송 위험 감소 |
| 문서 검색(RAG) | 검색 결과와 모델 선택, 캐시를 함께 활용 | 반복적인 문서 질의의 응답 속도 개선 |

RAG와 함께 사용하는 경우에는 문서가 변경되었을 때 이전 답변이 계속 반환되지 않도록 주의해야 한다.

예를 들어 문서 버전이나 데이터 기준 시각을 캐시 키에 포함하거나, 문서가 갱신되면 관련 캐시를 무효화하는 방법을 사용할 수 있다.

## 8. TMS 대시보드에 적용한다면?

### 8.1 먼저 역할을 구분해야 한다

우리 TMS 프로젝트에서는 LLM이 배출 상태를 직접 판정하거나 사전 경고 여부를 결정하지 않는다.

현재 역할은 다음과 같이 구분된다.

| 구성 요소 | 담당 역할 |
|---|---|
| Rule Engine | 기준값과 업무 규칙에 따른 상태 판정 |
| ML 모델 | NOx·SOx 농도 예측 및 위험도 예측 |
| Python 최종 판단 로직 | Rule Engine과 ML 결과를 종합해 최종 결과 결정 |
| LLM | 판정 결과 설명, 자연어 조회, 요약 및 사용자 질의 지원 |
| 대시보드 | 판정 결과와 예측 결과를 사용자에게 시각적으로 제공 |

**LLM은 판정 결과를 설명하는 역할이지, 판정 결과를 변경하는 역할이 아니다.**

예를 들어 Rule Engine에서 특정 굴뚝을 경고 상태로 판정했다면 LLM은 그 결과를 이해하기 쉽게 설명할 수 있다. 하지만 LLM이 정상이라고 답변하더라도 기존 판정 결과는 변경되지 않는다.

### 8.2 TMS 대시보드 질문 예시

| 사용자 질문 | 처리 방향 | 캐시 적용 |
|---|---|---|
| 오늘 NOx 경고가 발생한 굴뚝은? | 실시간 데이터 조회 후 결과 요약 | 적용하지 않거나 짧은 TTL |
| 특정 굴뚝의 최근 24시간 NOx 변화는? | DB 조회 후 LLM이 결과 설명 | 조회 조건과 데이터 기준 시각 포함 |
| NOx와 SOx의 차이는? | 일반적인 기술 설명 | 캐시 가능 |
| 어제 발생한 주요 경고를 요약해 줘 | 과거 경고 이력 조회 후 요약 | 데이터 버전과 조회 기간 포함 |
| 특정 담당자의 연락처를 알려줘 | 권한 확인 후 내부 정보 조회 | 개인정보 정책에 따라 처리 |
| 왜 이 굴뚝이 경고 상태인가? | Rule Engine과 ML 결과의 근거를 조회해 설명 | 결과 변경 시 캐시 무효화 |

### 8.3 TMS에 적용할 때 특히 주의할 사항

**① 개인정보 및 내부 운영 정보 보호**

- 담당자 연락처 등 민감 정보가 포함된 질문은 내부 처리 경로를 우선한다.
- 사용자별 조회 권한을 확인한다.
- LLM에 전달하는 데이터는 필요한 항목만 제공한다.

**② 실시간 데이터는 무조건 캐시하지 않는다**

예를 들어 "현재 경고 중인 굴뚝은?"이라는 질문은 30분 단위 데이터 갱신에 따라 답변이 달라질 수 있다.

따라서 실시간 조회 결과를 무조건 캐시하면 이전 경고 상태를 반환할 수 있다.

가능하면 캐시를 사용하지 않고, 사용하더라도 데이터 기준 시각이나 스냅샷 ID를 함께 관리해야 한다.

**③ 대상과 조건이 다르면 다른 질문이다**

다음 항목은 캐시 검색 시 구분해야 한다.

- 굴뚝 번호(stack_code)
- 측정 항목(item_code: NOx, SOx)
- 조회 기간
- 데이터 기준 시각
- 사용자 권한 및 조회 범위

예를 들어 "A 굴뚝의 NOx 상태"와 "A 굴뚝의 SOx 상태"는 문장 구조가 비슷해도 서로 다른 결과를 반환해야 한다.

**④ LLM이 최종 판정 결과를 변경하지 않도록 한다**

LLM이 설명을 생성할 때는 Python 최종 판단 결과와 근거 데이터를 입력으로 제공한다.

LLM의 역할은 다음과 같다.

- 판정 결과를 자연어로 설명
- 주요 변화 구간 요약
- 경고 발생 원인과 관련 데이터 안내
- 사용자의 추가 질문에 대한 조회 지원

반면 다음 작업은 기존 판정 로직에서 처리한다.

- 경고 여부 결정
- 위험도 계산
- Rule Engine 결과 변경
- ML 예측값 변경
- 최종 판정 결과 확정

### 8.4 TMS 적용 아키텍처 예시

```text
                   사용자
                     │
                     ▼
                TMS Dashboard
                     │
                     ▼
               LLM 요청 처리
                     │
                     ▼
              ① 개인정보 검사
                     │
             ┌───────┴────────┐
             │                │
          민감 정보          일반 질문
             │                │
             ▼                ▼
         Local LLM         Cache 조회
                              │
                       ┌──────┴──────┐
                       │             │
                     Cache Hit   Cache Miss
                       │             │
                       ▼             ▼
                    답변 반환    ② Model Tiering
                                     │
                               ┌─────┴─────┐
                               │           │
                            Small       Large
                             LLM          LLM
                               │           │
                               └─────┬─────┘
                                     │
                                     ▼
                                  답변 생성
                                     │
                                     ▼
                                Cache 저장
                                     │
                                     ▼
                                사용자 응답

       ─────────────────────────────────────
       LLM이 조회할 수 있는 데이터
       ─────────────────────────────────────

             TMS DB / 조회 API
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
       Rule 결과   ML 예측 결과  경고 이력
          │          │          │
          └──────────┼──────────┘
                     │
                     ▼
                LLM 설명 생성
```

실제 구현에서는 LLM이 데이터베이스에 직접 접근하도록 하기보다, 권한과 조회 조건을 검증하는 API를 통해 필요한 데이터를 전달하는 구조를 권장한다.

또한 개인정보가 포함된 질문은 캐시 조회와 저장을 모두 건너뛰도록 별도 분기해야 한다.

## 9. 실제 구현 시 추가로 고려할 사항

세 가지 전략을 구현했다고 해서 바로 안정적인 서비스가 되는 것은 아니다. 운영 환경에서는 다음 항목도 함께 고려해야 한다.

| 구분 | 고려 사항 | 이유 |
|---|---|---|
| 보안 | 사용자 인증 및 데이터 조회 권한 | 다른 사용자의 데이터가 노출되는 문제 방지 |
| 보안 | 개인정보 검사 및 로컬 처리 정책 | 민감 정보의 외부 전송 방지 |
| 모델 | 모델별 품질 평가 | 작은 모델로 처리해도 충분한지 확인 |
| 모델 | 실패 시 재시도 및 대체 경로 | 모델 장애에 대한 대응 |
| Cache | TTL 및 캐시 무효화 | 오래된 답변 반환 방지 |
| Cache | 사용자·조직·데이터 버전 구분 | 다른 사용자나 다른 데이터의 답변이 섞이는 문제 방지 |
| 모니터링 | 모델별 호출 횟수와 비용 | 비용 절감 효과 측정 |
| 모니터링 | Cache Hit Rate | 캐시 활용 효과 측정 |
| 모니터링 | 응답 시간과 오류율 | 사용자 경험과 서비스 안정성 확인 |

특히 다음 지표를 대시보드나 운영 모니터링 화면에 표시하면 Hybrid 전략의 효과를 확인하기 좋다.

| 지표 | 의미 |
|---|---|
| Provider별 호출 비율 | 외부 API와 로컬 모델의 사용 비중 |
| Small/Large 모델 호출 비율 | 질문 난이도에 따른 모델 사용 비중 |
| Cache Hit Rate | 전체 요청 중 캐시로 처리한 비율 |
| 평균 응답 시간 | 질문 처리에 걸린 평균 시간 |
| 평균 호출 비용 | 질문 한 건당 평균 LLM 비용 |
| 모델 재시도율 | 작은 모델에서 큰 모델로 재요청한 비율 |

## 10. 최종 정리

| 전략 | 얻는 효과 | 고려해야 할 대가 | 반드시 지킬 원칙 |
|---|---|---|---|
| Provider 선택 | 개인정보 보호 및 데이터 통제 | 로컬 모델의 성능과 운영 부담 | 민감 정보는 외부로 보내지 않는다 |
| Model Tiering | LLM 사용 비용 절감 | 잘못된 모델 선택으로 인한 품질 저하 | 실제 질문 데이터로 모델 선택 기준을 검증한다 |
| Cache | 반복 호출 감소 및 응답 속도 개선 | 오래된 답변이나 잘못된 답변 반환 위험 | 개인정보와 시간 의존 데이터는 신중하게 처리한다 |

### 발표 때 멘티들에게 던질 질문

**질문 1.** 개인정보가 포함된 질문을 로컬 모델이 처리하다 실패했습니다. 외부 API로 다시 보내도 될까요?

- 생각할 점: 개인정보 보호 정책과 실패 시 대체 경로

**질문 2.** 개인정보 검사를 하기 전에 캐시부터 조회하면 어떤 문제가 생길까요?

- 생각할 점: 개인정보가 캐시에 저장되거나 다른 사용자에게 노출될 가능성

**질문 3.** "NOx 기준치는?"과 "SOx 기준치는?"의 유사도가 0.96으로 나왔습니다. 캐시된 답변을 그대로 반환해도 될까요?

- 생각할 점: 문장 유사도와 실제 질문의 의미는 다를 수 있음

**질문 4.** "현재 경고 중인 굴뚝은?"이라는 질문에 30분 전 캐시된 답변을 반환해도 될까요?

- 생각할 점: 데이터 갱신 주기와 캐시의 유효 기간

**질문 5.** 작은 모델이 답변을 생성했지만 근거가 부족합니다. 어떻게 처리하는 것이 좋을까요?

- 생각할 점: 답변 품질 검증과 큰 모델 재호출

> **LLM Hybrid 전략의 핵심은 모델을 여러 개 사용하는 것이 아니다. 질문마다 어디로 보내도 되는지, 어느 정도 성능의 모델이 필요한지, 기존 답변을 재사용해도 되는지를 먼저 판단하는 것이다.**

TMS 대시보드에서는 한 가지 원칙을 더 기억해야 한다.

> **Rule Engine과 ML이 판정하고, Python이 최종 결과를 통제하며, LLM은 그 결과를 이해하기 쉽게 설명한다.**
